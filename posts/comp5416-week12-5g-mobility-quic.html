COMP5416 Week 12 讲课总结：5G 移动网络 + QUIC

课程：COMP5416/COMP4416 — Advanced Network Technologies，Semester 2 2026 讲师：Professor Vincent Gramoli 来源：讲义 W12-Mobile+QUIC-final.pdf（54 页）+ tutorial W12-Mobility.pdf / W12-Mobility-solution.pdf（Lab 9: Mobile networks）。本周没有转录稿。 教材：Kurose & Ross 9th ed. —— 第 7 章（5G、移动性、蓝牙、卫星）、第 3.8 节（QUIC）

本周覆盖：5G 架构 → 加入 5G 网络 → 移动性与切换 → 蓝牙、卫星、IoT → QUIC。 前置：Week 11 的蜂窝架构、移动性术语、Mobile IP；Week 06 的 TCP 可靠传输与拥塞控制（QUIC 部分）。

第一部分：5G 架构

一、5G 的两大部分（讲义 p2）

二、5G RAN（讲义 p3）

RAN：把设备连到基站的边缘网络。

要点 说明
作用 提供链路层服务，作为设备与更大网络之间的第一跳
范围 地理范围有限；由单个服务提供商控制
类比 有点像 WiFi LAN
组成 许多设备（UE：User Equipment） + 无线信道（NR：New Radio） + 一个基站（gNodeB / gNB：Next Generation Node B）

三、5G 核心网（讲义 p4）

要点 说明
位置 位于 RAN 与其他端点（其他核心网、更大的 Internet）之间
结构 一个核心，多个 RAN
组成 链路、路由器、服务器，为设备和基站提供服务
性质 「全 IP」核心，但提供的服务和传统 Internet 应用很不一样
关键设计 控制面与用户面清晰的逻辑分离：CUPS（Control-Plane and User-Plane Separation）

四、5G 核心功能组件（讲义 p5–8）

5G 核心（主要）是关于控制面服务的。

用户面

功能 职责
UPF（User Plane Function） 每个设备被分配到一个 UPF，作为中继在 UE 与 Internet 之间转发流量；负责策略执行、合法监听、流量用量计量、QoS 监管；负责在 N3 接口上对到/来自基站的流量做隧道（封装/解封装）

控制面

功能 全称 职责
AMF Access and Mobility Management Function 连接与可达性管理、移动性管理、接入授权、位置服务
SMF Session Management Function 管理每个 UE 的会话：IP 地址分配、选择关联的 UPF、QoS 控制、用户面路由的控制
AUSF Authentication Server Function 认证设备
UDM Unified Data Management 管理用户身份，包括生成认证凭据
UDR Unified Data Repository 管理用户静态签约信息
UDSF Unstructured Data Storage Function 存非结构化数据，类似键值存储
PCF Policy Control Function 策略控制
NEF Network Exposure Function 对第三方应用暴露网络能力
NRF Network Repository Function 网络功能注册/发现
AF Application Function 应用功能
SEPP Security Edge Proxy 与其他运营商控制面之间的安全边界

记忆分组： - 存数据的：UDR、UDSF（「data storage」） - 认证/身份：AUSF（认证）、UDM（身份与凭据） - 管连接的：AMF 管「接入和移动」，SMF 管「会话」 - 唯一的用户面：UPF

五、接口与 CUPS（讲义 p9）

平面 特点
控制面 强调功能与服务；服务之间有明确定义的接口（N1、N2、N4、N7、N8、N10、N11、N12、N13 …）
数据面 5 层 Internet 数据面；大量使用隧道

几个关键接口：

接口 两端
N1 UE ↔︎ AMF
N2 基站 ↔︎ AMF
N3 基站 ↔︎ UPF（用户面隧道）
N4 SMF ↔︎ UPF（SMF 控制 UPF）
N6 UPF ↔︎ Internet（数据网络）

六、用户面隧道：GTP-U（讲义 p10）

协议栈（基站 ↔︎ UPF 之间）：

例子：设备地址 ，基站地址 ，UPF 地址 ，Internet 上的发送方地址 。

段 外层源 → 目的 内层源 → 目的
Internet → UPF —
UPF → 基站（回传网，隧道）
基站 → 设备（无线） —

和 Week 11 Mobile IP 的「分组中的分组」完全同一思路：UPF 像归属代理，把发往 的数据报封装后送到当前基站 。 设备移动时只需要改隧道端点（见第十一节切换），设备的 IP 地址 不变。

第二部分：身份与入网

七、身份：你是谁？（讲义 p11）

4G/5G Internet 方式
你是某个无线服务商（你付钱的那家，即归属蜂窝网络）的客户 你是一个名字 + 密码（不同应用、服务用不同的名字和密码）
你有 SIM（Subscriber Identity Module）卡或 vSIM 你是一个名字 + 公钥证书（服务器常有公钥，用户大多还没有）
SIM 向全球所有蜂窝网络标识你和你的归属网络
SIM 里有归属网络也知道的密钥信息

八、加入 5G 网络的两个阶段（讲义 p12）

阶段 内容
1. 注册（Registration） 设备向网络认证自己，网络也向设备认证自己（双向）
2. PDU 会话建立 核心网功能给设备分配 IP 地址，建立设备与其 UPF 之间的数据面路径；PDU = 协议数据单元，即「分组」

AMF 在把新设备接入网络中起关键作用。

九、入网详细步骤（讲义 p13）

阶段 步骤 涉及
注册 RRC 连接建立（请求/响应） 设备 ↔︎ 基站
注册请求 设备 → AMF
身份请求/响应 AMF ↔︎ 设备
认证与安全（可能需要远端/归属网络的 AUSF） AMF ↔︎ AUSF
更新设备连接数据 AMF ↔︎ UDM
注册接受 AMF → 设备
PDU 会话建立 PDU 会话建立请求 设备 → AMF
会话创建请求/响应 AMF ↔︎ SMF
获取/更新设备签约 SMF ↔︎ UDM
会话建立请求/响应 SMF ↔︎ UPF
会话信息（如设备 IPv4 地址、隧道） → 设备、基站
RAN 会话请求/响应（数据面配置） AMF ↔︎ 基站
第一个上行数据报进入数据面 设备 → UPF

第三部分：移动性

十、移动性的谱（讲义 p15）

无移动 → → → 高移动
设备在网络之间移动，但移动时关机 设备在同一 WLAN/RAN 内移动 设备在一个提供商网络内的多个 WLAN/RAN 之间移动 设备在多个提供商网络之间移动，同时保持正在进行的连接

讲义标注「我们关心这些」 —— 中间两档（同一提供商内的移动）。

WiFi 中的移动（讲义 p16）

要点 说明
802.11 是链路层标准，用链路层方法处理移动 —
ESS（扩展服务集） 多个 BSS，在同一个三层子网里，SSID 相同
ESS 内 BSS 之间的移动 快速重新认证；AP 可以向设备推荐新的 AP
增强移动性 厂商的专有方案

为什么同一子网内移动不需要 Mobile IP：IP 地址不变，只需交换机（自学习）更新「这个 MAC 现在在哪个端口」。

十一、5G 切换（讲义 p17–20）

切换（handover）：移动设备改变其网络接入点；到设备的数据流从源基站改为目标基站。

为什么切换：目标基站信号更强；目标基站设备更少、流量更少（负载均衡）。

七个步骤

步 动作
1 当前（源）基站选择目标基站，向它发 Handover Request
2 目标基站预分配无线时隙，回 HR ACK，附带给移动设备的信息
3 源基站通知移动设备新基站的信息 → 移动设备现在可以经新基站发送 —— 对移动设备来说切换看起来已完成
4 源基站停止向移动设备发数据报，改为转发给新基站（新基站再经无线信道转给移动设备）
5 目标基站通知 AMF、SMF：它是该移动设备的新基站；SMF 指示 UPF 把隧道端点改为（新的）目标基站
6 目标基站向源基站 ACK：切换完成，源基站可释放资源
7 移动设备的数据报现在经新隧道从目标基站流向 UPF

第 4 步的「转发」是为了不丢包：在 UPF 改隧道之前（第 5 步），下行数据还在发往源基站，源基站把它们转给目标基站，目标基站先缓存。 UPF 是固定锚点 —— 和 Week 11 的「锚点外地代理」、GSM 的锚点 MSC 一个思路。

时序要点（讲义 p20）

  • RAN 内的切换：测量 → 切换决策 → 切换请求 → 接纳控制（accept?）→ 请求 ACK → RRC 重配置 → 状态转移 → 设备从源基站脱离、附着到目标基站 → 目标基站缓存来自源基站的设备数据 → RRC 重配置完成
  • 核心网内的切换：路径切换请求 → PDU 会话更新 → 会话修改 → end marker（结束标记） → 路径切换请求 ACK → 设备上下文释放

end marker：UPF 在旧隧道上发出最后一个标记包，告诉源基站「后面不会再有了」，目标基站据此知道何时可以按序交付缓存数据。

第四部分：蓝牙、卫星、IoT

十二、蓝牙概述（讲义 p22–24）

无线 ad hoc 网络的例子：设备没有任何「基础设施」（AP、基站）可连。蓝牙设备必须从零开始互相发现、组织成网络：

  • 链路层连接设备，提供信道分配
  • 地址分配
  • 服务发现
  • 蓝牙网络上的应用到应用通信
  • 安全

需要一套全新的架构和协议栈（不同于 Internet）！

Piconet

要点 说明
网络单位 piconet
覆盖 一般直径 < 10 m
设备数 每个 piconet 不超过 8 个设备：首先组网的设备是 central 角色，最多再 7 个 peripheral
通信 只在 central 与 peripheral 之间；peripheral 之间不能直接通信
地址 每个蓝牙设备有唯一 48 位地址
频段 免许可 ISM 频段 2.4 GHz

无线信道

经典蓝牙（Classic） BLE
每信道带宽 1 MHz 2 MHz
信道数 79 40（3 个广播 + 37 个数据）
最大速率 2.1 Mbps —
  • 蓝牙信道：TDM，时隙长 625 μs
  • 信道访问靠轮询（polling）：central 设备通告，授予 peripheral 信道访问权
  • 使用跳频（frequency hopping，一种扩频）传输

十三、跳频（讲义 p25）

  • 蓝牙网络中的发送方在 79 个频率/信道之间「跳」：每个时隙换一个频率
  • 跳频序列对同一 piconet 的所有设备已知
  • 跳频序列不同的多个 piconet 可以在同一空间共存

为什么要跳频：降低干扰的影响 —— ISM 频段里可能有很多干扰源；如果某干扰设备占用信道 x，x 在跳频序列中只偶尔出现；在 x 上发的帧被干扰没收到，下一个时隙在另一个频率上重传。

十四、蓝牙协议栈（讲义 p26–28）

特点 说明
与 Internet 栈完全不同 反映蓝牙的特殊用途
没有「网络层」「传输层」 经典蓝牙没有路由（BLE 加入了 managed flooding）
分层不如 Internet、5G 清晰 host / controller 结构深嵌在架构里
经典与 BLE 有各自的控制器 —

L2CAP：创建和管理两设备间的端到端 L2CAP 信道（用于端到端应用数据或更高层服务），提供可靠性、流量控制、分段。

L2CAP 信道类型 用途
面向连接、异步（ACL） —
无连接、异步（ACL） —
同步（eSCO） 如周期性音频应用

讲义 p28 的例子：手机（central）同时连 MP3 音乐设备和远程键盘（两个 peripheral），各有端到端 L2CAP 连接和服务发现。

十五、卫星（讲义 p29–34）

应用：

感知 广播 Internet
环境（天气、土地利用、人类活动）；分辨率约 m/像素 消费者直播电视/广播；一次发送到达众多用户；GPS 覆盖无服务地区；长距离低时延；飞机上的接入

GEO vs LEO（必考对比）

GEO（地球同步） LEO（低地球轨道）
相对地面 静止 移动：约 27,000 km/h
高度 约 35,768 km（讲义数字；常见值 35,786 km） 550–1200 km
RTT 约 800 ms 约 30 ms（实际）
每颗覆盖 大范围 小范围；需要多颗组成星座
可见时间 一直 在地面站视线内只有 5–15 分钟
星间链路 — ISL（inter-satellite links）

为什么 GEO 的 RTT 约 800 ms：单程上下各 ~36,000 km，往返 4 段约 144,000 km，光速下约 480 ms，加上处理和地面路径就到了 600–800 ms 级别 —— 对 VoIP（< 400 ms）太大（Week 08）。

LEO 星座（讲义 p32，2025 数据）

星座 已部署 计划 ISL？
Starlink 7,239 12,000–42,000 是
EutelSat OneWeb 648 716–6,372 否
Kuiper（Amazon） 27 3,236 ?
Telesat 1 298–1,671 是

LEO 网络组成：运动中的 LEO 卫星、星间链路、卫星信道（下行广播/多播，上行单播）、地面站、移动用户终端（Starlink 天线 "Dishy McFlatface"）。

链路还是网络？（讲义 p34）

天上的链路（bent pipe） 天上的网络
基站之间只有单个卫星跳 基站之间有多个卫星跳
卫星只做「弯管」转发 卫星之间需要路由

Starlink（讲义 p35）：2025 年 4 月约 7,239 颗在轨（计划 12K、申请 30K）；2019 年首发；三层轨道壳 525、530、535 km；2024 年 9 月 400 万用户；在乌克兰提供服务；2024 年测试直连手机（用 T-Mobile 的蜂窝频谱）。

十六、IoT（讲义 p36–38）

用例：压力/振动/温湿度监测、资产定位追踪、环境监测、智能抄表、农业、安防…… 数量：IoT 设备数量远超 PC/笔记本/平板/手机，且持续增长（讲义 Statista 图，2014–2028）。

通信需求：

维度 范围
无线 必须
距离 几米到几公里
速率 活跃时几百 bps（抄表）到约 1 Mbps（视频监控）
能耗 始终要考虑：无外部电源工作约 10 年；本地能量收集

技术权衡：

类型 技术
短距 WiFi、BLE、Zigbee
低功耗广域 LoRaWAN、LTE-M
传统广域 蜂窝 4G/5G

第五部分：QUIC（Quick UDP Internet Connections，RFC 9000）

十七、为什么需要演进传输层（讲义 p40）

TCP、UDP 作为主要传输协议已经 40 年。针对特定场景发展出了各种 TCP「flavor」：

场景 挑战
长肥管道（大数据传输） 许多分组「在途」；一次丢包就让流水线停下来
无线网络 噪声链路和移动造成的丢包；TCP 把它当成拥塞丢包
长时延链路 极长的 RTT
数据中心网络 对时延敏感
后台流量 低优先级的「后台」TCP 流

趋势：把传输层功能搬到应用层，跑在 UDP 之上 —— HTTP/3：QUIC。

十八、QUIC 是什么（讲义 p41–42）

要点 说明
定位 应用层协议，跑在 UDP 之上
目的 提升 HTTP 性能
部署 许多 Google 服务器和应用（Chrome、移动 YouTube 应用）

协议栈对比：

层 HTTP/2 over TCP HTTP/3 over UDP
应用 HTTP/2 HTTP/2（精简）= HTTP/3

QUIC 采用了本章（传输层）学过的方法：

方面 说明
差错与拥塞控制 QUIC 规范原话：「熟悉 TCP 丢包检测和拥塞控制的读者会发现这里的算法与知名的 TCP 算法相似」
连接建立 可靠性、拥塞控制、认证、加密、状态 —— 在一个（甚至零个）RTT 内建立
多个应用层「流」复用在一个 QUIC 连接上 各流独立的可靠数据传输和安全；共用拥塞控制

握手对比：TCP + TLS 1.2 需要 TCP 三次握手 1 RTT + TLS 2 RTT；QUIC 把传输握手和加密握手合在一起，1-RTT，曾连过的服务器可 0-RTT。

十九、流：并行、无队头阻塞（讲义 p43、p47）

(a) HTTP/1.1 (b) HTTP/2 over TCP (c) HTTP/2 with QUIC
多个 HTTP GET 各自 TLS + TCP 连接 多个 GET 复用一个 TLS + 一个 TCP 连接 每个 GET 一个 QUIC 流，各自的 RDT，共享一个 QUIC 拥塞控制，跑在 UDP 上
— 一个分组出错 → TCP 按序交付 → 所有流都被阻塞（HOL blocking） 一个流出错只影响该流

队头阻塞（Head-of-line blocking）：TCP 是单一有序字节流，某个段丢了，后面所有字节（哪怕属于别的 HTTP 请求）都得等它重传。 QUIC 让多个数据流独立到达各端点，独立于其他流的丢包；UDP 本身不管顺序和丢包，QUIC 负责处理某个特定流里的丢包。

二十、QUIC 分组结构（讲义 p48–50）

连接 ID（Connection ID）

怎么标识一个连接
TCP 四元组（源 IP、目的 IP、源端口、目的端口）
UDP 二元组（目的 IP、目的端口）
QUIC Connection ID

设备迁移（如从 4G 切到 WiFi）时会发生什么？ TCP：IP 变了 → 四元组变了 → 连接断开。 QUIC：Connection ID 不变 → 连接平滑迁移（smooth handover）。 这把本周前半的「移动性」和后半的「传输层」联系起来了。

包号与偏移

字段 作用
Packet number 单调递增、永不重复（即使是重传也用新包号）
Offset + Length（在 stream frame 中） 保证流内数据的顺序
  • 分组丢了：由应用决定是否重传丢失的 frame
  • 丢包检测与丢包恢复分离：包号负责「检测」，stream offset 负责「重组」

对比 TCP：TCP 的序号同时承担「检测」和「排序」，重传段与原段序号相同，导致 RTT 采样歧义（不知道 ACK 对应哪次发送，Week 06 说「忽略重传段的 SampleRTT」就是因为这个）。QUIC 重传用新包号，没有这种歧义。

其他帧类型（讲义 p50）

帧 讲义写法 说明
MAX_STREAM_DATA 讲义写「connection level flow control」 ⚠️ 按 RFC 9000 应是「流级」流控（限制单个流上可发的数据量）
MAX_DATA 讲义写「stream level flow control」 ⚠️ 按 RFC 9000 应是「连接级」流控（限制整个连接的数据总量）
PING / PONG 验证对端是否存活 （RFC 9000 中只有 PING 帧，对端用 ACK 响应）
CONNECTION_CLOSE 连接正在关闭 —

⚠️ 讲义把 MAX_DATA 和 MAX_STREAM_DATA 的层级写反了。从名字就能看出：带 STREAM 的是流级。 要点不变：QUIC 同时有连接级和流级两层流量控制（TCP 只有一层 rwnd）。

二十一、QUIC 拥塞控制（讲义 p51–52）

与 TCP 相似但更先进；单调包号 → 丢包时没有 RTT 估计歧义。

超时（PTO）：

符号 含义
平滑 RTT（≈ TCP 的 EstimatedRTT）
RTT 偏差（≈ TCP 的 DevRTT）
kGranularity 定时器粒度，1 ms
max_ack_delay 接收方打算延迟确认的最长时间

对照 TCP： 。QUIC 多了两项：定时器粒度下限（防止 rttvar 太小导致超时过短）和对端的最大延迟 ACK 时间（TCP 的延迟 ACK 最长 500 ms 却没算进超时里）。

机制：

机制 对应 TCP
慢启动 同
拥塞避免（线性增） 同
恢复期（窗口减半） ≈ 快速恢复
丢包检测：靠 ACK（类似 3 个重复 ACK） ≈ 快速重传
丢包检测：靠超时 同
丢包触发恢复 —
持续拥塞（persistent congestion）→ 慢启动（RFC 9002） ≈ TCP 超时回到 cwnd = 1

持续拥塞的定义：发送方确认在足够长的一段时间内发出的所有在途分组都丢失了，就认为网络处于持续拥塞。

Exercise 1：4G LTE 下行时隙分配

Exercise 2：Mobile IP —— 两个移动设备能否用同一转交地址？

官方答案：可以。

如果转交地址就是外地代理的地址，那两个移动设备的 COA 自然相同。 外地代理解封装隧道过来的数据报后，看内层数据报的目的地址（各自的永久地址），就能分别发给不同的移动设备。

对照 Week 11 的「分组中的分组」：外层目的 = COA（外地代理，共享）；内层目的 = 永久地址（各不相同） —— 区分靠内层。 （如果用的是「同址转交地址」(co-located COA，移动设备自己从访问网络拿到的地址），那就不能共享。）

易错点

  1. AMF ≠ SMF：AMF 管「接入与移动」，SMF 管「会话（含 IP 分配）」。
  2. 5G 切换中设备 IP 不变，变的是 UPF 到基站的隧道端点。
  3. 蓝牙 peripheral 之间不能直接通信。
  4. LEO 要星座，单颗覆盖小、可见时间只有 5–15 分钟。

  7. TCP 的 HOL 阻塞来自「单一有序字节流」，HTTP/2 的多路复用解决不了，QUIC 才解决。
