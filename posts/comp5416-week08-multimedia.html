第一部分：多媒体基础

一、三类多媒体应用（讲义 p4）

类型 特点 例子
流式存储音视频 可以边下边播（不必下载完整文件）；存在服务器上，所以能以快于播放的速度传输（意味着客户端要缓存） YouTube、Netflix、Hulu
会话式 IP 语音/视频 人与人交互，对时延容忍度很低 Skype
流式直播音视频 实时产生 体育赛事直播

三者对时延的要求递增：存储视频可以缓冲好几秒；直播允许几秒延迟；会话式要求 < 150 ms 级别。

二、音频的数字化（讲义 p5）

步骤 说明
采样 模拟信号按固定速率采样：电话 8000 次/秒；Spotify 音乐 44100 次/秒
量化 每个样本四舍五入到有限个值，例如 个值
编码 每个量化值用比特表示，256 个值需要 8 bit
量化误差 原始模拟值与量化值之差

码率 = 采样率 × 每样本比特数：

三、视频的码率（讲义 p6–7）

视频 = 以恒定速率显示的图像序列（如 24 帧/秒）；每帧是像素阵列（如 480×640）；每像素 RGB 三色，每色 8 bit。

所以必须编码压缩：利用图像内部和图像之间的冗余减少比特数。

编码类型 原理 讲义例子
空间编码（帧内） 一行 N 个相同颜色像素，不发 N 个值，只发「颜色值 + 重复次数 N」 类似游程编码
时间编码（帧间） 不发完整的第 帧，只发它与第 帧的差异 运动补偿
标准 用途 码率
MPEG-1 CD-ROM 1.5 Mbps
MPEG-2 DVD 3–6 Mbps
MPEG-4 常用于 Internet < 1 Mbps

码率分类：CBR（恒定码率） 和 VBR（可变码率）。讲义后面的缓冲模型都假设 CBR 播放。

第二部分：流式存储视频

四、流的基本过程与挑战（讲义 p9–10）

视频录制（如 30 帧/秒）→ 发送 → 经网络时延 → 接收 → 播放。流式：客户端在播前面的同时，服务器还在发后面的。

挑战：

挑战 说明
连续播放约束 一旦开始播放，播放时序必须与原始时序一致
网络时延可变（jitter） 所以需要客户端缓冲来满足播放要求
客户端交互 暂停、快进、跳转
丢包与重传 视频分组可能丢失、被重传

五、客户端缓冲与播放时延（讲义 p11–13）

客户端缓冲 + 播放时延：补偿网络附加的时延和时延抖动。

情况 后果
播放时延太小 某个分组在该播放时还没到 → 缓冲下溢（buffer underflow），无法按时播放
增大播放时延 下溢更少
权衡 初始播放时延越大越稳，但用户要等越久才能开始看

过程： 1. 开始前先填缓冲，直到 2. 开始播放 3. 之后 随 变化而变化， 保持恒定

七、三种流媒体传输方式（讲义 p17–21）

UDP 流

要点 说明
发送速率 服务器以适合客户的速率发送，通常发送速率 = 编码速率 = 恒定
拥塞 发送速率可以无视拥塞程度
播放时延 短（2–5 秒），用于消除网络抖动
差错恢复 应用层做，时间允许才做
协议 RTP（讲义写 RFC 2326，那其实是 RTSP；RTP 是 RFC 3550，讲义 p46 也写了 3550）
缺点 UDP 可能过不了防火墙

HTTP 流

要点 说明
获取方式 HTTP GET 取多媒体文件
发送速率 TCP 下能达到的最大速率
填充速率 因 TCP 拥塞控制和重传（按序交付）而波动
播放时延 更大，用来平滑 TCP 交付速率
优点 HTTP/TCP 更容易穿过防火墙
新趋势 YouTube 在 HTTP/3 下也使用 QUIC（见 Week 12）

数据路径：视频文件 → TCP 发送缓冲 → 网络 → TCP 接收缓冲 → 应用播放缓冲 → 播放。

DASH：Dynamic, Adaptive Streaming over HTTP

端 做什么
服务器 把视频切成多个块（chunk）；每块以多种码率编码存储；manifest 文件给出各块的 URL
客户端 周期性测量服务器到客户端的带宽；查 manifest，一次请求一块；选当前带宽能承受的最高码率；不同时间可选不同码率

「智能在客户端」—— 客户端决定三件事：

决定 目的
何时请求块 避免缓冲饥饿（starvation）
请求什么码率 带宽多时要高质量
向哪里请求 选「近」的或可用带宽高的 URL 服务器

八、CDN（讲义 p22–25）

挑战：如何把（从数百万视频中选出的）内容同时流给数十万用户？

方案 问题 / 做法
方案 1：单个超大服务器 单点故障；网络拥塞点；到远处客户路径长；同一视频的多个副本挤在出口链路上 → 不可扩展
方案 2：CDN 在地理上分布的多个站点存储/服务视频的多个副本

CDN 访问流程（讲义 p24：Bob 看 netcinema 的视频）

步 动作
0 视频预先存进 CDN（KingCDN.com/NetC6y&B23V）
1 Bob 从 netcinema.com 网页拿到视频 URL http://netcinema.com/6Y7B23V
2 Bob 的本地 DNS 解析该 URL
3 netcinema 的权威 DNS 不返回 IP，而是返回一个 KingCDN 的 URL（CNAME 式重定向）
4–5 本地 DNS 再去问 KingCDN 的权威 DNS，它返回「最佳」KingCDN 服务器的 IP
6 Bob 向该 KingCDN 服务器请求视频，经 HTTP 流式传输

核心技巧：用 DNS 做重定向。内容提供商把「解析权」交给 CDN，CDN 的 DNS 根据请求来源挑节点。（与 Week 04 DNS 的权威服务器概念直接相关。）

节点选择策略（讲义 p25）

策略 说明
地理上最近 最简单
时延最短 / 跳数最少 CDN 节点定期 ping 接入 ISP，把结果报告给 CDN DNS
让客户端决定 给客户一个 CDN 服务器列表，客户 ping 后自己挑最好的 —— Netflix 的做法

九、Netflix 案例（讲义 p26–27）

  • 2011 年占美国下行流量的 30%
  • 自己几乎没有基础设施，用第三方服务：
    • 自有：注册、计费服务器
    • Amazon 云：生成电影的多个编码版本；把版本上传到 CDN；托管 Netflix 网页
    • 三家 CDN：Akamai、Limelight、Level-3

流程：① Bob 管理账户 → ② 浏览选视频 → ③ 返回 manifest 文件 → ④ DASH 流式播放。

（讲义描述的是 2011 年左右的架构；如今 Netflix 已改用自建的 Open Connect CDN，考试按讲义答即可。）

第三部分：Voice over IP

十、VoIP 的要求（讲义 p29）

要求 值
端到端时延 < 150 ms：好；> 400 ms：差（包含应用层播放时延和网络时延）
会话初始化 被叫怎么公布 IP、端口、编码算法？（→ SIP，Week 10）
增值服务 呼叫转移、筛选、录音
紧急服务 911 / 000

十一、VoIP 流量特征（讲义 p30）

  • 说话者音频：讲话段（talk spurt）与静默期交替
  • 讲话时 64 kbps；只在讲话时产生块
  • 每 20 ms 一块：
  • 每块加应用层首部，块 + 首部封装进 UDP 或 TCP 段
  • 讲话期间每 20 ms 往 socket 里写一个段

十二、两种「丢失」（讲义 p31）

类型 原因
网络丢失 IP 数据报因拥塞（路由器缓冲溢出）丢失
时延丢失 数据报到得太晚，赶不上播放 —— 对接收方来说等于丢了
  • 典型最大可容忍时延：400 ms
  • 丢包容忍度：取决于语音编码和丢包隐藏技术，1% 到 10% 的丢包率可以容忍

十三、固定播放时延（讲义 p33–34）

接收方尝试在每块「生成后恰好 q 毫秒」播放它：时间戳为 的块在 播放； 之后才到的块 = 丢失。

优点 缺点
大 丢包少 交互差
小 交互体验好 丢包多

怎么判断「讲话段的第一个分组」（讲义 p39–40）

情况 判断规则
无丢包 相邻时间戳之差 > 20 ms ⇒ 新讲话段开始
可能丢包 时间戳之差 > 20 ms 且序号连续（无空缺）⇒ 新讲话段开始

讲义 p40 的例子：时间戳 0, 20, 40, 100, 120。 - 无丢包时：40 → 100 差 60 ms，序号连续 → 100 是新讲话段第一个。 - 若序号是 1, 3, 4, 5（时间戳 0, 40, 100, 120）：0 → 40 差 40 ms 但序号跳了（2 丢了），所以这只是丢包，不是新讲话段；40 → 100 差 60 ms 且序号 3→4 连续 → 新讲话段。

为什么要看序号：只看时间戳会把「丢了一个包」误判为「静默」。

方案 2：捎带低质量流

  • 把低分辨率的音频流作为冗余信息一起发
  • 例：正常流 64 kbps，冗余流 13 kbps
  • 实现上通常是第 个分组携带第 块的低质量版本：丢了一个，就用下一个分组里的低质版本顶上

方案 3：交织（interleaving）

  • 把每个 20 ms 音频块切成更小单元（如 4 个 5 ms 单元）
  • 每个分组装的是来自不同块的小单元
  • 丢一个分组时，每个原始块仍保有大部分内容

讲义 p44 的对比：

不交织 交织
丢一个分组 = 整个单词丢失 丢一个分组 = 每个单词缺一个音节，主观感受可接受
优点 缺点
交织 无冗余开销 时延性能更差（要等几个分组凑齐才能重组）

三种方案对比

方案 带宽开销 额外时延 恢复质量
XOR FEC 等一组 完全恢复（最多丢 1）
低质量冗余流 冗余流码率（如 13/64） 一个分组 降质恢复
交织 0 较大 隐藏（缺小片段）

第四部分：RTP

十六、RTP 是什么（讲义 p46–49）

要点 说明
作用 规定承载音视频数据的分组结构（RFC 3550）
提供 载荷类型标识、分组序号、时间戳
运行位置 端系统
封装 RTP 分组封装在 UDP 段里
互操作 两个 VoIP 应用都用 RTP，就可能互通

RTP 在 UDP 之上扩展了：端口号、IP 地址（已有）+ 载荷类型、序号、时间戳（新增）。

RTP 与 QoS（讲义 p49，易错）： - RTP 不提供任何保证及时交付或其他 QoS 的机制 - RTP 封装只在端系统可见，中间路由器看不到 - 路由器提供尽力而为服务，不会为 RTP 分组特殊处理

RTP 例子（讲义 p48）

发送 64 kbps PCM μ-law 语音：采样 8000 次/秒、8 bit/样本；每 20 ms 收集 160 字节为一块；音频块 + RTP 首部 = RTP 分组，封装进 UDP 段。

  • RTP 首部指明每个分组的音视频编码类型 → 发送方可在会话中途更换编码
  • RTP 首部还包含序号、时间戳

十七、RTP 首部字段（讲义 p50–52）

字段 位数 作用
payload type 7 当前使用的编码类型；中途换编码就通过这个字段告知接收方
sequence # 16 每发一个 RTP 分组加 1；检测丢包、恢复顺序
timestamp 32 该分组第一个字节的采样时刻
SSRC 32 标识 RTP 流的来源；同一会话中每个流的 SSRC 不同

Exercise 1：滑动窗口与序号空间

图 1（即 Kurose 教材 SR 困境图）：序号空间 {0, 1, 2, 3}，窗口大小 3。 - (a) 无问题：pkt0–2 正常到达并被确认，接收窗口移到 {3, 0, 1}，发送方之后发的 pkt0 是新分组 → 正确接受。 - (b) 出问题：pkt0–2 到达，但 3 个 ACK 全丢了；发送方超时重传旧 pkt0；接收窗口此时是 {3, 0, 1}，把旧 pkt0 当作新分组接受了！

第 8 题的通用算法：慢启动阶段第 轮结束时累计发送 个段； ，所以第 70 个落在第 7 轮；但第 7 轮已进入拥塞避免，cwnd = 33（不是 64），发的是第 64–96 个段。

易错点

  1. 缓冲必然被抽空； 还需要足够的初始时延。
  2. DASH 的智能在客户端，服务器只存块和 manifest。
  3. CDN 靠 DNS 重定向，内容提供商的权威 DNS 返回的是 CDN 的名字。
  4. Netflix（讲义版本）让客户端自己 ping 挑 CDN 节点。
  5. 时延丢失也是丢失 —— 到得太晚等于没到。
  6. 自适应播放时延只在讲话段开始时调整，段内不调。
  7. 判断新讲话段要同时看时间戳和序号。
  8. XOR FEC 一组只能救 1 个；交织无冗余但时延大。
  9. RTP 不提供 QoS，路由器看不到 RTP 首部。
  10. RTP 跑在 UDP 之上，属于应用层库提供的「类传输层」接口。
