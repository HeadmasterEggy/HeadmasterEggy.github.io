COMP5416 W08：多媒体网络（大白话版）

一句话：音视频数据量大、又要按节奏播，可网络只管「尽力送」，时快时慢还会丢。这周讲怎么在这种网络上看视频、打网络电话：视频靠先缓冲、按带宽选画质、就近取（CDN）；网络电话靠算好播放时延、丢了不重传而是提前多发冗余；再用 RTP 给每个分组打上编码类型、序号和时间戳。

考什么（讲义标的是 Weeks 7 and 8）：码率怎么算；流媒体客户端缓冲和播放时延（W13 复习课重点，W9 tutorial 也考它）；UDP 流、HTTP 流、DASH 的区别；CDN 怎么用 DNS 把你引到近的服务器；VoIP 的时延要求和两种丢失；固定 / 自适应播放时延；怎么判断新讲话段；三种丢包恢复（XOR FEC、低质量冗余流、交织）；RTP 首部和时间戳。期末全是选择题（单选 + 多选，多选勾错一个抵掉勾对的一个）。

读法：每节先用例子讲道理，术语第一次出现时解释，节末有「怎么做题」。最后是做题速查和 30 道带答案的练习。W8 tutorial 的两道 TCP 题在 W06 第十一、十二节。

一、三类多媒体应用

类型 大白话 例子
流式存储音视频 视频早就存在服务器上。边下边播，不用等下完。因为是现成的，服务器可以比播放速度更快地发，多出来的就存在客户端缓冲里 YouTube、Netflix
会话式 IP 语音 / 视频 人和人实时对话。对时延最敏感：你说完要等很久对方才听到，就没法聊了 Skype、微信电话
流式直播 内容是现场实时产生的，只能产生一点发一点 体育直播

对时延的要求从松到紧：存储视频（可以先缓冲几秒）→ 直播（晚几秒也能接受）→ 会话（要 150 ms 级别）。

怎么做题

  • 「可以比播放速度更快地传」「需要客户端缓存」→ 存储视频（直播做不到，内容还没产生）。
  • 「对时延容忍度最低」→ 会话式。

二、码率怎么算

2.1 音频：采样 × 比特数

声音是连续的波形，要变成比特得走三步：

  1. 采样：每隔固定时间量一次波形的高度。电话每秒 8000 次；音乐（讲义写 Spotify）每秒 44100 次。
  2. 量化：量出来的值可能是任意小数，把它四舍五入到有限几个档位，比如 2⁸ = 256 档。四舍五入造成的误差叫量化误差。
  3. 编码：每个档位用一串比特表示，256 档要 8 比特。

所以每秒的比特数就是：

  • 音乐：44100 × 8 = 352 800 bps（约 353 kbps）
  • 电话：8000 × 8 = 64 000 bps = 64 kbps。后面 VoIP、RTP 里反复出现的 64 kbps 就是它。

2.2 视频：先算有多大，再看怎么压

视频就是按固定速率播放的一串图片（比如每秒 24 张，叫帧）。每张图是一个像素方阵，每个像素有红绿蓝（RGB）三种颜色，每种颜色 8 比特。

讲义例子：480 × 640 像素、24 帧/秒：

太大了，家里网络扛不住，必须压缩。压缩靠的是冗余，也就是「重复的东西不用发两遍」：

编码 利用什么冗余 例子
空间编码（一张图里面） 一张图里很多相邻像素颜色一样 一行 N 个紫色像素，不发 N 个「紫」，只发「紫色 × N」两个值
时间编码（前后两张图之间） 相邻两帧大部分画面一样 不发完整的第 i+1 帧，只发它和第 i 帧不一样的地方

常见标准（MPEG = 动态图像专家组）：

标准 用途 码率
MPEG-1 CD-ROM 1.5 Mbps
MPEG-2 DVD 3–6 Mbps
MPEG-4 互联网常用 < 1 Mbps

码率还分 CBR（恒定码率）：每秒比特数固定；VBR（可变码率）：画面复杂时多给、简单时少给。

怎么做题

  • 音频码率 = 采样率 × 比特数。电话 8000 × 8 = 64 kbps。
  • 视频码率 = 比特/颜色 × 3 种颜色 × 宽 × 高 × 帧率。注意别漏乘 3。
  • 空间 = 一帧内部；时间 = 帧与帧之间。MPEG-4 码率最低（< 1 Mbps）。

三、流媒体的客户端缓冲（复习课重点）

3.1 为什么要缓冲

服务器匀速发视频，可网络时延一直在变（抖动，jitter）：有的分组走得顺早到，有的被堵晚到。而视频一旦开播，就必须按原来的节奏连续播，讲义叫连续播放约束。

办法：客户端缓冲 + 播放时延。 收到数据先别急着播，等一会儿、攒一段再开播。这段等待就是播放时延（playout delay）。开播后，就算网络卡了一下，缓冲里还有存货顶着。

打个比方：一根忽大忽小的水管往桶里灌水，桶底龙头要匀速出水。先攒半桶再开龙头，水管小一阵也不会断流。

情况 后果
播放时延太小 某块到了该播的时刻还没到，缓冲空了，缓冲下溢（buffer underflow），画面卡住（转圈）
加大播放时延 下溢更少
代价 用户要等更久才开始看。讲义叫「初始播放时延的权衡」

存储视频还有别的麻烦：用户会暂停、快进、跳转；分组可能丢失、要重传。

3.2 缓冲的数学模型

符号：

  • ：网络往缓冲里填数据的速率，会变；
  • ：播放速率（视频码率），恒定（CBR）；
  • ：此刻缓冲里存了多少数据；：缓冲的容量；
  • ：开始播放的时刻。

t 规则 计算 Q(t+1)
0 t ≤ t_p，只进 0 + 2 2

4 边进边出 0 + 3 − 2 1
5 边进边出 1 + 2 − 2 1

  • 递推题：列表逐行算。先看 是否 ≤ 决定减不减 ；每行检查 是否 < 0。
  • 「为什么要缓冲」→ 抵消网络时延的抖动。
  • 「加大播放时延」→ 下溢少，但等得久。
  • 「 」→ 必卡；「 」→ 还要初始时延够大才不卡。只说「 一定不卡」的选项错。

四、三种流媒体传输方式

4.1 UDP 流

  • 服务器按适合客户的速率发，通常发送速率 = 编码速率，恒定；
  • 不管网络拥不拥塞（UDP 没有拥塞控制，也就不会被它拖慢）；
  • 所以收到的速率比较稳，播放时延短，2–5 秒就够消除抖动；
  • 丢了的数据，应用层有空就补，没空就算了；
  • 用 RTP 封装（第九节）；
  • 最大的问题：很多防火墙会挡 UDP，挡了就什么都看不了。

4.2 HTTP 流

  • 用一个 HTTP GET 把视频文件要过来，服务器以 TCP 能跑到的最快速度发；
  • TCP 会因为拥塞控制（W06）忽快忽慢，丢包还要重传，而且必须按顺序交付（前面一个没到，后面的都得等），所以填充速率波动大；
  • 于是播放时延要更长，用来抹平 TCP 的波动；
  • 数据路径：视频文件 → TCP 发送缓冲 → 网络 → TCP 接收缓冲 → 应用的播放缓冲 → 播放；
  • 好处：HTTP / TCP 很容易穿过防火墙；
  • YouTube 在 HTTP/3 下用 QUIC（W12）。

4.3 DASH（基于 HTTP 的动态自适应流）

HTTP 流有个问题：码率固定，网速一慢就卡。DASH 的想法是：准备好几种画质，网速好就看高清，网速差就自动换标清，宁可糊一点也不卡。

端 做什么
服务器 把视频切成很多小块（chunk），每块几秒；每块都用好几种码率各编一份存起来；再写一个 manifest 文件（清单），列出每块每种码率的 URL
客户端 定期测量服务器到自己的带宽；查 manifest，一次请求一块；每次选当前带宽撑得住的最高码率；所以不同时间可以选不同码率

「聪明」在客户端。客户端决定三件事：

决定 目的
什么时候请求下一块 别让缓冲饿死（starvation，就是下溢），也别撑爆
请求什么码率 带宽够就要高画质
从哪里请求 选离自己近、或可用带宽高的服务器

你看视频时清晰度自己跳来跳去，就是 DASH 在干活。

4.4 三种对比

UDP 流 HTTP 流 DASH
传输层 UDP TCP TCP
发送速率 恒定 = 编码速率 TCP 能到的最大速率 按客户端选的码率
播放时延 短（2–5 s） 较长 较长
防火墙 可能被挡 容易通过 容易通过
谁决定码率 服务器 固定一种 客户端

怎么做题

  • 「2–5 秒」「防火墙可能挡」「不管拥塞」→ UDP 流。
  • 「TCP 最大速率」「填充速率波动」「播放时延更大」「容易过防火墙」→ HTTP 流。
  • 「manifest」「多码率」「客户端测带宽、选码率」→ DASH。说「服务器决定码率」的选项错。

五、CDN

5.1 为什么要 CDN

问题：几百万个视频，同时有几十万人在看，怎么供得上？

方案 1：建一个超级大服务器。 不行，因为：

  • 单点故障：它一挂，全世界都看不了；
  • 网络拥塞点：所有流量都挤到它门口；
  • 离远处用户太远：悉尼用户看美国的服务器，路又长又堵；
  • 同一个热门视频要从同一条出口链路重复发很多份。

一句话：不可扩展。

方案 2：CDN（内容分发网络）。 在世界各地很多地方放视频的副本，谁离得近就由谁服务。像连锁便利店，不用每个人都跑去总仓库。

5.2 怎么把用户引到 CDN 节点：DNS 重定向

讲义例子：Bob 在 netcinema 网站看视频，视频实际存在 KingCDN 的服务器上。

步 发生了什么
0 netcinema 事先把视频放进 KingCDN
1 Bob 在 netcinema 网页上点到视频链接 http://netcinema.com/6Y7B23V
2 Bob 的本地 DNS 去解析这个名字
3 netcinema 的权威 DNS 不给 IP，而是给一个 KingCDN 的名字：「去问 KingCDN」
4–5 本地 DNS 再问 KingCDN 的权威 DNS，它返回离 Bob 最合适的那台 KingCDN 服务器的 IP（Bob 在悉尼，就给澳洲的服务器）
6 Bob 向那台服务器要视频，用 HTTP 流式传输

核心：内容商把「这个名字解析到哪」交给 CDN（就是 W04 讲的 CNAME 别名），CDN 的 DNS 看请求从哪来，挑一个节点。

5.3 CDN 选哪个节点

策略 做法
地理上最近 最简单，但近不一定快
时延最短 / 跳数最少 CDN 节点定期 ping 各个接入 ISP，结果报给 CDN 的 DNS
让客户端自己选 给客户端一份服务器列表，客户端挨个 ping，挑最快的。讲义说这是 Netflix 的做法

5.4 Netflix 案例（讲义描述的 2011 年左右）

  • 当时占美国下行流量的 30%；
  • 自己几乎没有基础设施，大量用第三方：
    • 自己只管注册和计费服务器；
    • Amazon 云：把母版转成多种编码版本、上传到 CDN、托管供浏览的网页；
    • 内容放在三家 CDN：Akamai、Limelight、Level-3；
  • 用户流程：管理账户 → 浏览选片 → 拿到 manifest 文件 → DASH 播放。

怎么做题

  • 「超级大服务器的问题」：单点故障、拥塞点、路径长、重复发。选项里「不能用 HTTP」之类是干扰项。
  • CDN 重定向靠 DNS：内容商的权威 DNS 返回 CDN 的名字，CDN 的权威 DNS 返回具体服务器的 IP。不是改路由，也不是 HTTP 重定向。
  • Netflix（讲义版）：客户端 ping 后自己选；播放用 DASH + manifest。

六、VoIP（网络电话）

6.1 要求

要求 内容
端到端时延 < 150 ms 好，> 400 ms 差。这个时延包括网络时延和应用层的播放时延
会话初始化 被叫怎么告诉别人自己的 IP、端口、编码（→ SIP，W10）
增值服务 呼叫转移、来电筛选、录音
紧急服务 000 / 911

为什么卡在 150 ms 和 400 ms：超过这个，对话就会出现「你一句我一句撞车」「等半天才回话」的感觉。

6.2 流量长什么样

  • 人说话是讲话段（talk spurt）和静默期交替的：说一句，停一下，等对方。
  • 讲话时 64 kbps，只在讲话时产生数据，静默时什么都不发（省带宽）。
  • 每 20 ms 打一个包：64 kbps = 8 KB/s，8000 B/s × 0.02 s = 160 字节。
  • 每块加上应用层首部，放进 UDP（或 TCP）段，讲话期间每 20 ms 发一个。

6.3 两种丢失

类型 原因
网络丢失 路由器缓冲满了，IP 数据报被丢（拥塞）
时延丢失 数据报到得太晚，已经过了该播的时刻，对接收方来说跟丢了一样
  • 典型的最大可容忍时延 400 ms；
  • 能容忍多少丢包，看编码和丢包隐藏技术，大约 1%–10%。

怎么做题

  • 数字题：150 ms / 400 ms；64 kbps、20 ms、160 字节。
  • 「到得太晚也算丢」→ 时延丢失；「路由器缓冲溢出」→ 网络丢失。

七、播放时延：固定和自适应

网络电话也有抖动，所以也要「等一会儿再播」。问题是等多久：等太短，很多包赶不上（时延丢失）；等太长，对话不顺。

7.1 固定播放时延

接收方给每个包定一个死规矩：它在发送端生成后恰好 q 毫秒播放。时间戳为 的块在 播； 之后才到的，就当丢了。

讲义的图：第一个包在时刻 到达。方案一从较早的 开始播，后面有个包晚到，赶不上就丢了；方案二从较晚的 开始播，所有包都赶上了，代价是多等了 。

q 好处 坏处
大 丢得少 对话有延迟感
小 对话顺 丢得多

7.2 自适应播放时延

目标：播放时延尽量低，迟到丢失也尽量少，两头都要。

办法：持续估计网络时延，在每个讲话段开始时按估计值调整播放时延。讲话段之间的静默期被拉长或压短一点，人耳听不出来；可讲话段中间不能动，否则一句话会被拉变形。

估计平均时延（EWMA，指数加权移动平均，就是 W06 TCP 估 RTT 的同一招）：

  • ：第 个包的接收时刻；：它的发送时间戳； ：这个包实测的时延；
  • ：很小的常数，比如 0.01。意思是「新估计 = 99% 旧估计 + 1% 这次的实测」，不会被一个异常值带偏。

估计时延的波动（偏差）：

讲话段第一个包的播放时刻：

  • 、 每收到一个包都更新，但只在讲话段开头才拿来用。 同一讲话段内的其他包，按和第一个包的相对时间播放。

7.4 怎么判断「讲话段的第一个包」

讲话时每 20 ms 一个包，所以相邻包的时间戳正常相差 20 ms。差得更多，说明中间有一段没发东西。可「没发」有两种可能：静默了，或者发了但丢了。

情况 规则
不会丢包 相邻时间戳差 > 20 ms → 新讲话段
可能丢包 时间戳差 > 20 ms 且序号连续 → 新讲话段；序号跳了说明是丢包

讲义例子：

  • 时间戳 0、20、40、100、120，不丢包：40 到 100 差 60 ms → 100 是新讲话段的第一个。
  • 序号 1、3、4、5，时间戳 0、40、100、120：0 到 40 差 40 ms，但序号 1 到 3 跳了，说明 2 号包丢了，不是静默；40 到 100 差 60 ms，序号 3 到 4 连续，说明发送方确实没发，100 是新讲话段。

道理：序号是每发一个包加 1，静默时不发包，序号就不涨；丢包时包发了，序号涨了，只是没收到。

怎么做题

  • 固定播放时延：每个包算「生成时刻 + q」，和到达时刻比，晚到的就丢。q 大丢得少、交互差。
  • EWMA：新 = × 旧 + × 实测； 用新的 。
  • 「每个包都调整播放时刻」→ 错；只在讲话段开头调整。
  • 判断新讲话段：时间戳差 > 20 ms 且序号连续。只看时间戳会把丢包当成静默。

八、丢包恢复

难点：通话只能容忍几百毫秒的时延，而「发现丢了 → 发 NAK → 重传」至少要一个 RTT，来不及。所以思路反过来：提前多发一点冗余，丢了自己就能补出来，这叫前向纠错（FEC）。

8.1 简单 XOR FEC

XOR（异或，⊕）的规则：相同得 0，不同得 1。它有个好性质： ，所以一串数异或起来，知道其中任意一个以外的全部，就能反推出那一个。

  • 每 n 个块额外生成一个冗余块：
  • 发 n + 1 个块，带宽多出 1/n（n = 4 就多 25%）。
  • 这 n + 1 个里最多丢 1 个，都能补回来。

讲义例子（n = 3，逐位看）： ， ， 丢了，冗余块 ：

代价：

  • n 越大，带宽开销 1/n 越小；
  • 但要等一整组 n + 1 个都到了才能补，播放时延变大；
  • 一组里丢 2 个就补不回来。

8.2 捎带低质量流

  • 每个包里除了正常的高质量数据，再顺带一份上一块的低质量版本。例：正常流 64 kbps（PCM），冗余流 13 kbps（GSM）。
  • 第 n 个包丢了，第 n+1 个包里有它的低质量版本，用低质量的顶上，听起来糊一点，但不断。
  • 额外时延只有一个包的时间。

8.3 交织（interleaving）

不加任何冗余，而是把数据打散了再装包：

  • 把每个 20 ms 的块切成 4 个 5 ms 的小单元；
  • 每个包装的是来自不同块的小单元：比如 4 个块共 16 个单元（块 1 是单元 1–4，块 2 是 5–8……），第 1 个包装单元 1、5、9、13，第 2 个包装 2、6、10、14，依此类推；
  • 丢了一个包，每个原始块只缺一小片（比如每个块都少了第 3 个单元），大部分还在。
不交织 交织
丢一个包 = 一整个词没了 丢一个包 = 每个词缺一个音节，听感好得多

代价：没有冗余开销，但时延更大，要等几个包都到了才能拼回原来的块。

8.4 三种方案对比

方案 带宽开销 额外时延 恢复效果
XOR FEC 1/n 等一组 n + 1 个 完全恢复（一组最多丢 1 个）
低质量冗余流 冗余流码率（如 13/64） 一个包 降质恢复
交织 0 较大 隐藏（缺小片段，听不太出来）

怎么做题

  • 为什么不重传：重传至少要一个 RTT，来不及。
  • XOR 补数：把收到的全部（包括 y）异或起来，就是丢的那个。开销 1/n；一组只能丢 1 个。
  • 「没有冗余开销」→ 交织；「降质恢复」→ 低质量冗余流；「完全恢复」→ XOR。

九、RTP（实时传输协议）

9.1 是什么

  • 规定装音视频数据的分组长什么样（RFC 3550）；
  • 给每个分组提供三样东西：载荷类型（用的什么编码）、序号、时间戳；
  • 跑在端系统上（你的电脑、手机），RTP 分组装在 UDP 段里；
  • 两个 VoIP 应用都说 RTP，就有可能互通。

可以把 RTP 理解成「给 UDP 加了几个音视频专用的字段」：UDP 本来就有端口号和 IP，RTP 再补上编码类型、序号、时间戳。

RTP 不提供 QoS（易错）：

  • RTP 没有任何机制保证及时送达或其他服务质量；
  • RTP 首部只有两端看得到，中间路由器只看到一个普通 UDP 包；
  • 路由器照样尽力而为，不会优待 RTP 分组。

讲义例子：发 64 kbps 的 PCM μ-law 语音（8000 次/秒采样，每样本 8 比特），每 20 ms 攒 160 字节一块，加 RTP 首部，再装进 UDP。因为每个包的 RTP 首部都写明了编码类型，发送方可以在通话中途换编码，接收方看首部就知道。

9.2 首部字段

字段 位数 作用
payload type 7 这个包用的编码类型。中途换编码就靠它通知接收方
sequence number 16 每发一个 RTP 包加 1。用来发现丢包、把乱序的包排回来
timestamp 32 这个包里第一个字节的采样时刻
SSRC 32 标识这条 RTP 流是谁发的（同步源）。同一会话里每条流的 SSRC 都不同

常见 payload type：0 = PCM μ-law（64 kbps），3 = GSM（13 kbps），7 = LPC（2.4 kbps），26 = Motion JPEG，31 = H.261，33 = MPEG2 视频。

9.3 时间戳怎么算（必会）

时间戳不是用秒计，而是用采样次数计：

  • 音频：每采样一次，时间戳加 1。8 kHz 采样，就是每 125 μs 加 1；
  • 每块 20 ms，含 20 ms ÷ 125 μs = 160 个样本 → 每个 RTP 包时间戳加 160；
  • 静默时不发包，但时间戳的时钟照样走。

讲义例子：连续收到时间戳 X、X + 160、X + 480 的包。X + 160 到 X + 480 差 320 = 2 × 160，说明中间空了 2 块（40 ms）；X 到 X + 480 一共是 480 × 125 μs = 60 ms。

序号 + 时间戳一起看：

时间戳 序号 说明
跳了 也跳了 丢包（包发了，没收到）
跳了 连续 静默后新讲话段开始（那段时间根本没发包）

怎么做题

  • 「RTP 保证时延 / 路由器优先转发 RTP」→ 错。
  • 字段位数：payload type 7、序号 16、时间戳 32、SSRC 32。
  • 时间戳增量 = 采样率 × 每块时长。8 kHz × 20 ms = 160。空了几块 = 时间戳差 ÷ 160 − 1。
  • 区分流的来源 → SSRC；中途换编码 → payload type；发现丢包 → 序号。

做题速查

  1. ★★★ 客户端缓冲：播放时延太小会下溢；加大时延下溢少但等得久； 必卡； 还要初始时延够大；会用递推式列表算。
  2. ★★★ DASH：服务器切块、每块多码率、manifest；客户端测带宽、选码率、决定何时和向谁请求。
  3. ★★ UDP 流 vs HTTP 流：UDP 恒速、2–5 s、可能被防火墙挡；HTTP 走 TCP 最大速率、波动大、时延长、易过防火墙。
  4. ★★ CDN：大服务器四个问题；DNS 重定向（内容商 DNS 返回 CDN 名字，CDN DNS 返回服务器 IP）；Netflix 让客户端 ping 后自己选。
  5. ★★ 码率：采样率 × 比特数；电话 64 kbps；未压缩视频约 177 Mbps；空间 / 时间编码；MPEG-1/2/4 = 1.5 / 3–6 / < 1 Mbps。
  6. ★★ VoIP：< 150 ms 好、> 400 ms 差；20 ms 一块、160 字节；网络丢失和时延丢失；1%–10% 可容忍。
  7. ★★ 播放时延：固定 q 大丢少交互差；自适应 ，每包更新、只在讲话段开头用；新讲话段 = 时间戳差 > 20 ms 且序号连续。
  8. ★★ 丢包恢复：XOR 开销 1/n、一组最多丢 1 个；低质量流降质顶上；交织零开销、时延大。
  9. ★★ RTP：装在 UDP 里、不提供 QoS、字段位数 7/16/32/32；8 kHz 下每包时间戳加 160；时间戳跳 + 序号连续 = 新讲话段。

Q30（讲义） 8 kHz 采样、每块 20 ms 的音频，连续收到时间戳 X、X + 160、X + 800 的三个包，且序号连续。说明什么？
A. X + 160 之后丢了 3 个包
B. X + 160 之后静默了 60 ms，X + 800 是新讲话段的第一个
C. 换了编码
D. 时钟出错

B。每包加 160，800 − 160 = 640 = 4 × 160，中间空了 3 块（60 ms）；序号连续说明是静默不是丢包。区分来源用 SSRC，字段位数见 9.2。
