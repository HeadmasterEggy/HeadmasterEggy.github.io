COMP5416 W08：多媒体网络（知识点 + 题型）

这一周考什么（讲义标的是 Weeks 7 and 8）：音频、视频的码率计算；流媒体客户端缓冲和播放时延（复习课重点）；UDP 流、HTTP 流、DASH；CDN 怎么用 DNS 重定向；VoIP 的时延要求和两种丢失；固定 / 自适应播放时延；判断新讲话段；三种丢包恢复（XOR FEC、低质量冗余流、交织）；RTP 首部和时间戳。

期末题型：全是选择题，有单选也有多选，多选题勾错一个会抵消勾对的一个。计算题主要是码率、缓冲递推、XOR 恢复、自适应时延估计、RTP 时间戳增量。W8 tutorial 的两道 TCP 题放在 W06 第十一、十二节。

读法：从上往下读。每节先讲它要解决什么问题，再给结论和算例。

一、三类多媒体应用

类型 特点 例子
流式存储音视频 边下边播，不用下载完；内容存在服务器上，可以比播放速度更快地传（所以客户端要缓存） YouTube、Netflix
会话式 IP 语音 / 视频 人和人交互，对时延容忍度很低 Skype
流式直播 实时产生 体育直播

对时延要求从松到紧：存储视频（可以缓冲几秒）→ 直播（几秒延迟可接受）→ 会话式（150 ms 级别）。

二、码率计算

2.1 音频

模拟信号变成比特，三步：

  1. 采样：按固定速率取样。电话 8000 次/秒；音乐（讲义写 Spotify）44100 次/秒。
  2. 量化：每个样本四舍五入到有限个值，比如 2⁸ = 256 个。原值和量化值之差叫量化误差。
  3. 编码：每个量化值用比特表示，256 个值要 8 比特。

  • 音乐：44100 × 8 = 352 800 bps
  • 电话：8000 × 8 = 64 kbps（PCM 语音的 64 kbps 就是这么来的）

2.2 视频

视频是按固定速率显示的一串图像（比如 24 帧/秒），每帧是像素阵列，每个像素 RGB 三色、每色 8 比特。

太大，必须压缩，利用图像内部和图像之间的冗余：

编码 原理
空间编码（帧内） 一行 N 个同色像素，不发 N 个值，只发「颜色 + 重复次数 N」
时间编码（帧间） 不发完整的第 i+1 帧，只发它和第 i 帧的差别
标准 用途 码率
MPEG-1 CD-ROM 1.5 Mbps
MPEG-2 DVD 3–6 Mbps
MPEG-4 互联网常用 < 1 Mbps

码率还分 CBR（恒定码率） 和 VBR（可变码率）。

三、流媒体的客户端缓冲（复习课重点）

3.1 为什么要缓冲

服务器按固定节奏发视频，但网络时延是变化的（抖动，jitter），到达客户端的时间参差不齐。而视频一旦开始播放，必须按原来的节奏连续播。

办法：客户端缓冲 + 播放时延。先攒一段再开始播，吸收网络时延和抖动。

情况 后果
播放时延太小 某块到了播放时刻还没到 → 缓冲下溢（buffer underflow），卡顿
加大播放时延 下溢更少
代价 用户要等更久才开始看

其他挑战：客户端交互（暂停、快进、跳转），分组丢失和重传。

3.2 缓冲的数学模型

符号：

  • ：网络送来的填充速率，会变。
  • ：播放速率，恒定（CBR）。
  • ：缓冲里有多少数据；：缓冲大小。
  • ：开始播放的时刻。

就是下溢。

必考结论：

条件 结果
平均填充速率 E(x) < r 缓冲迟早被抽空，视频卡住，等缓冲重新填满
E(x) ≥ r 缓冲不会空，前提是初始播放时延足够大，能吸收 x(t) 的波动

3.3 带你算一遍

r = 2 单位/秒，Q(0) = 0，x(t) 在 t = 0, 1, …, 5 依次为 2, 2, 1, 0, 3, 2（平均 5/3，略小于 2，但短时间内看开播时刻的影响）。

t_p = 2（晚开播）：

  • Q(1) = 0 + 2 = 2，Q(2) = 2 + 2 = 4，Q(3) = 4 + 1 = 5（t = 2 ≤ t_p，还只进不出）
  • Q(4) = 5 + 0 − 2 = 3，Q(5) = 3 + 3 − 2 = 4，Q(6) = 4 + 2 − 2 = 4
  • 没有下溢

t_p = 0（马上开播）：

  • Q(1) = 0 + 2 = 2，Q(2) = 2 + 2 − 2 = 2，Q(3) = 2 + 1 − 2 = 1
  • Q(3) + x(3) − r = 1 + 0 − 2 < 0 → 下溢，Q(4) = 0，卡顿
  • Q(5) = 0 + 3 − 2 = 1，Q(6) = 1 + 2 − 2 = 1

同样的网络，晚开播 2 秒就不卡了。这就是「加大播放时延减少下溢」。

四、三种流媒体传输方式

4.1 UDP 流

  • 服务器按适合客户的速率发，通常发送速率 = 编码速率，恒定。
  • 不管网络拥不拥塞（UDP 没有拥塞控制）。
  • 播放时延短，2–5 秒，用来消除抖动。
  • 差错恢复在应用层做，时间允许才做。
  • 用 RTP 封装。
  • 缺点：UDP 可能被防火墙挡住。

4.2 HTTP 流

  • 用 HTTP GET 取多媒体文件，以 TCP 能达到的最大速率发。
  • 填充速率因 TCP 拥塞控制和重传（按序交付）而波动，所以播放时延要更大。
  • 数据路径：视频文件 → TCP 发送缓冲 → 网络 → TCP 接收缓冲 → 应用播放缓冲 → 播放。
  • 优点：HTTP / TCP 容易穿过防火墙。
  • YouTube 在 HTTP/3 下用 QUIC（W12）。

4.3 DASH（Dynamic, Adaptive Streaming over HTTP）

端 做什么
服务器 把视频切成块（chunk）；每块用多种码率编码存起来；manifest 文件列出每块各码率版本的 URL
客户端 定期测带宽；查 manifest，一次请求一块；选当前带宽撑得住的最高码率；不同时间可以选不同码率

智能在客户端。客户端决定三件事：

决定 目的
什么时候请求下一块 不让缓冲饿死（starvation），也不溢出
请求什么码率 带宽多时要高画质
从哪里请求 选近的、或可用带宽高的服务器

4.4 对比

UDP 流 HTTP 流 DASH
传输层 UDP TCP TCP
发送速率 恒定 = 编码速率 TCP 能到的最大速率 按客户端选的码率
播放时延 短（2–5 s） 较长 较长
防火墙 可能被挡 容易通过 容易通过
谁决定码率 服务器 固定 客户端

五、CDN

5.1 为什么要 CDN

问题：把几百万个视频同时流给几十万用户。

方案 1：一个超大服务器。问题：单点故障；网络拥塞点；到远处用户路径长；同一个视频的多个副本挤在出口链路上。不可扩展。

方案 2：CDN。在地理上分布的很多站点存放视频的多个副本，就近服务。

5.2 CDN 怎么把用户引到节点：DNS 重定向

讲义例子：Bob 看 netcinema 的视频，视频实际存在 KingCDN。

步 动作
0 视频预先存进 KingCDN
1 Bob 从 netcinema 网页拿到视频 URL http://netcinema.com/6Y7B23V
2 Bob 的本地 DNS 解析这个名字
3 netcinema 的权威 DNS 不返回 IP，而是返回一个 KingCDN 的名字
4–5 本地 DNS 再去问 KingCDN 的权威 DNS，它返回「最好」的 KingCDN 服务器的 IP
6 Bob 向那台服务器请求视频，通过 HTTP 流式传输

核心：内容提供商把解析权交给 CDN（W04 的 CNAME），CDN 的 DNS 按请求来源挑节点。

5.3 选哪个节点

策略 做法
地理上最近 最简单
时延最短 / 跳数最少 CDN 节点定期 ping 各接入 ISP，结果报给 CDN 的 DNS
让客户端自己选 给客户一份 CDN 服务器列表，客户 ping 一遍挑最好的。Netflix 的做法（讲义版本）

5.4 Netflix（讲义描述的 2011 年左右架构）

  • 占美国下行流量的 30%。
  • 自己几乎没有基础设施：自己只管注册和计费服务器；Amazon 云负责生成多种编码版本、上传到 CDN、托管网页；内容放在三家 CDN（Akamai、Limelight、Level-3）。
  • 流程：管理账户 → 浏览选片 → 返回 manifest 文件 → DASH 播放。

六、VoIP

6.1 要求

要求 内容
端到端时延 < 150 ms 好，> 400 ms 差（含应用层播放时延和网络时延）
会话初始化 被叫方怎么告诉别人自己的 IP、端口、编码（→ SIP，W10）
增值服务 呼叫转移、筛选、录音
紧急服务 000 / 911

6.2 流量特征

  • 讲话时讲话段（talk spurt）和静默期交替。
  • 讲话时 64 kbps，只在讲话时产生数据块。
  • 每 20 ms 一块：8 KB/s × 20 ms = 160 字节。
  • 每块加上应用层首部，封装进 UDP 或 TCP 段，讲话期间每 20 ms 发一个段。

6.3 两种丢失

类型 原因
网络丢失 IP 数据报因为拥塞（路由器缓冲溢出）被丢
时延丢失 数据报到得太晚，赶不上播放，对接收方来说等于丢了
  • 典型最大可容忍时延 400 ms。
  • 丢包容忍度：取决于编码和丢包隐藏技术，1%–10% 可以接受。

七、播放时延：固定和自适应

7.1 固定播放时延

接收方在每块生成后恰好 q 毫秒播放它：时间戳 t 的块在 t + q 播放，t + q 之后才到的就算丢了。

q 好处 坏处
大 丢得少 交互感差
小 交互好 丢得多

7.2 自适应播放时延

目标：播放时延低，迟到丢失也少。

办法：估计网络时延，在每个讲话段开始时调整播放时延。静默期被压缩或拉长，人耳听不出来。

时延估计（EWMA，和 TCP 估 RTT 同一个思路）：

  • ：接收时刻；：发送时间戳； ：第 i 个分组的实测时延。
  • ：小常数，比如 0.01。

偏差估计：

讲话段第一个分组的播放时刻：

  • 、 每个分组都更新，但只在讲话段开始时用。同一讲话段内不调整，后面的分组按和第一个分组的相对时间播放。
  • 和 TCP 的 EstimatedRTT + 4·DevRTT 是同一个「均值 + K 倍偏差」思想。

7.4 怎么判断「讲话段的第一个分组」

情况 规则
不会丢包 相邻时间戳差 > 20 ms → 新讲话段
可能丢包 时间戳差 > 20 ms 且序号连续 → 新讲话段；序号跳了说明是丢包

讲义例子：时间戳 0、20、40、100、120。

  • 不丢包：40 到 100 差 60 ms → 100 是新讲话段的第一个。
  • 如果序号是 1、3、4、5，时间戳是 0、40、100、120：0 到 40 差 40 ms，但序号 1 到 3 跳了（2 丢了），只是丢包；40 到 100 差 60 ms 且序号 3 到 4 连续 → 新讲话段。

为什么要看序号：只看时间戳会把「丢了一个包」当成「静默」。

八、丢包恢复

难点：可容忍时延很小，ACK / NAK 来回要一个 RTT，来不及重传。所以用前向纠错（FEC）：多发冗余，丢了不用重传也能恢复。

  • n + 1 个里最多丢 1 个，都能恢复。

代价：n 越大带宽开销越小，但要等一组 n + 1 个都到才能恢复，播放时延更大；一组里丢 2 个就救不回来。

8.2 捎带低质量流

  • 把低分辨率的音频流作为冗余一起发。例：正常流 64 kbps，冗余流 13 kbps。
  • 一般是第 n 个分组带上第 n − 1 块的低质版本。丢了一个，就用下一个分组里的低质版本顶上。

8.3 交织（interleaving）

  • 把每个 20 ms 的块切成更小的单元（比如 4 个 5 ms）。
  • 每个分组装的是来自不同块的小单元。
  • 丢一个分组时，每个原始块只缺一小片，大部分还在。
不交织 交织
丢一个分组 = 一整个单词没了 丢一个分组 = 每个单词缺一个音节，听起来还行

交织没有冗余开销，但时延更大（要等几个分组凑齐才能拼回来）。

8.4 三种方案对比

方案 带宽开销 额外时延 恢复效果
XOR FEC 1/n 等一组 n + 1 个 完全恢复（一组最多丢 1 个）
低质量冗余流 冗余流码率（如 13/64） 一个分组 降质恢复
交织 0 较大 隐藏（缺小片段）

九、RTP

9.1 是什么

  • 规定承载音视频数据的分组格式（RFC 3550）。
  • 提供：载荷类型标识、分组序号、时间戳。
  • 跑在端系统上，RTP 分组封装在 UDP 段里。
  • 两个 VoIP 应用都用 RTP，就有可能互通。

RTP 不提供 QoS（易错）：

  • RTP 没有任何保证及时交付或其他服务质量的机制。
  • RTP 封装只有端系统看得到，中间路由器看不到。
  • 路由器照样尽力而为，不会特殊对待 RTP 分组。

讲义例子：发 64 kbps PCM μ-law 语音，8000 次/秒采样、每样本 8 比特，每 20 ms 收集 160 字节一块，加上 RTP 首部封装进 UDP。RTP 首部写明编码类型，所以发送方可以在会话中途换编码。

9.2 首部字段

字段 位数 作用
payload type 7 当前用的编码类型；中途换编码就靠它告诉接收方
sequence number 16 每发一个 RTP 分组加 1；用来发现丢包、恢复顺序
timestamp 32 这个分组第一个字节的采样时刻
SSRC 32 标识 RTP 流的来源；同一会话里每个流的 SSRC 不同

常见 payload type：0 = PCM μ-law（64 kbps），3 = GSM（13 kbps），7 = LPC（2.4 kbps），26 = Motion JPEG，31 = H.261，33 = MPEG2 视频。

9.3 时间戳怎么算（必会）

  • 音频：每个采样周期时间戳加 1。8 kHz 采样 → 每 125 μs 加 1。
  • 每块 20 ms，含 20 ms / 125 μs = 160 个样本 → 每个 RTP 分组时间戳加 160。
  • 源静默时，时间戳时钟照样按恒定速率走。

讲义例子：时间戳 X、X + 160、X + 480。X + 160 到 X + 480 差 320，说明中间跳过了 2 块（40 ms 静默或丢失）。

序号 + 时间戳一起判断：

  • 时间戳跳了、序号也跳了 → 丢包
  • 时间戳跳了、序号连续 → 静默后新讲话段开始

考点小结

  1. ★★★ 客户端缓冲：播放时延太小会下溢；E(x) < r 必然抽空；E(x) ≥ r 还需要足够的初始时延；会用递推式算。
  2. ★★★ DASH：服务器切块、多码率、manifest；客户端测带宽、选码率、决定何时和向谁请求。
  3. ★★ CDN 用 DNS 重定向；Netflix 让客户端自己选节点。
  4. ★★ 码率：采样率 × 比特数；电话 64 kbps；未压缩视频约 177 Mbps。
  5. ★★ VoIP：< 150 ms 好、> 400 ms 差；20 ms 一块、160 字节；网络丢失和时延丢失。
  6. ★★ 自适应播放时延： ，只在讲话段开头调整；判断新讲话段要同时看时间戳和序号。
  7. ★★ 丢包恢复三种方案的开销、时延、效果。
  8. ★★ RTP：封装在 UDP 里、不提供 QoS、字段位数、8 kHz 下时间戳每包加 160。
  9. ★ UDP 流 vs HTTP 流：防火墙、播放时延、发送速率。

题目

格式照期末：大多是单选；标「（多选）」的可能不止一个对（真题靠题干的复数措辞提示），勾错倒扣，但每题最低 0 分。答题技巧见样卷解析：考试题型与答题技巧。

Q1（讲义） 采样率 8000 次/秒、每样本 8 比特的语音，码率是？
A. 8 kbps　B. 64 kbps　C. 352.8 kbps　D. 1.5 Mbps

B。

Q2（讲义） 480 × 640 像素、每像素 24 比特、24 帧/秒的未压缩视频，码率约为？
A. 7.4 Mbps　B. 22 Mbps　C. 177 Mbps　D. 1.4 Gbps

C。

Q3（讲义） 关于视频压缩，正确的是？（多选）
A. 空间编码只发颜色值和重复次数
B. 时间编码只发和前一帧的差别
C. MPEG-2 用于 DVD，约 3–6 Mbps
D. MPEG-4 码率一般高于 MPEG-1

A、B、C。MPEG-4 < 1 Mbps，MPEG-1 是 1.5 Mbps。

Q4（复习课） 流媒体客户端的播放时延设得太小，最可能出现什么？
A. 缓冲上溢　B. 缓冲下溢，播放卡顿　C. 码率下降　D. 丢包率上升

B。

Q5（讲义） 平均填充速率 E(x) 小于播放速率 r 时会怎样？
A. 只要初始播放时延够大就不会卡
B. 缓冲迟早被抽空，视频卡住
C. 缓冲会溢出
D. 客户端会自动降低 r

B。只有 E(x) ≥ r 时，足够大的初始时延才能防止卡顿。（D 是 DASH 的思路，但这个模型里 r 是恒定的。）

Q6（自拟） r = 2，Q(0) = 0，x(0..3) = 2, 2, 1, 0，t_p = 0。哪个时刻第一次出现下溢（Q(t) + x(t) − r < 0）？
A. t = 1　B. t = 2　C. t = 3　D. 不会下溢

C。Q(1) = 2，Q(2) = 2，Q(3) = 1，1 + 0 − 2 < 0。

Q7（讲义） 关于 DASH，正确的是？（多选）

C. 由服务器根据网络状况决定发哪个码率

Q8（讲义） 和 UDP 流相比，HTTP 流的特点是？（多选）

B. 填充速率因 TCP 拥塞控制和重传而波动

Q9（讲义） CDN 一般怎么把用户引到合适的服务器？

Q14（讲义） 关于 VoIP 的丢失，正确的是？（多选）
