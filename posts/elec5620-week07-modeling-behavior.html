一、基本行为概念

1.1 UML 的因果模型（事情是怎么发生的）

  • 离散事件驱动的计算模型：一个相互通信的对象网络
  • 所有行为都源于对象（All behaviours stem from objects）
  • UML 既描述单个对象的行为（如对象内部的状态机 s1→s2），也描述对象间（系统）行为（对象之间的消息交互）

事情如何发生：

  1. 一个动作由一个对象执行
  2. 动作可能改变一个或多个变量或槽的内容
  3. 如果是通信（消息）动作，它可能：调用另一个对象的操作，或向另一个对象发送信号
  4. 然后执行后继动作——由控制流或数据流决定

1.2 主动对象 vs 被动对象

Active object：一旦被创建就开始执行其分类器行为，直到行为完成或被外部对象终止才停止。它在何时响应其他对象发来的消息，完全由它自己的行为规格决定。记号：类框左右两边画双竖线。

Passive object Active object
何时响应 每当其操作（或接收）被调用时 只在执行 “receive” 动作时
并发 调用可能并发 ⇒ 可能冲突！ 并发运行；消息先进消息队列，按调度策略选择事件
例子 obj:C 被 a1 调 setA(1)、被 a2 调 getA() 同时发生 active:A 的队列里有 reqA、reqB，一次处理一个

1.3 UML 通信类型

Synchronous（call and wait） Asynchronous（send and continue）
形式 同步调用操作 向 reception 发送信号；异步调用操作（丢弃任何回复）
发送方 等待方法执行完、收到 reply 发送后立即继续
顺序图记号 实线 + 实心箭头；返回为虚线 实线 + 开放箭头

二、Actions（动作）

Action：一个命名元素，表示活动中的单个原子步骤，在该活动中不再分解。
Activity：由动作组成的行为。
记号：圆角矩形，名字通常是动词或动作名词。

用途：建模细粒度的行为现象，操作和访问 UML 实体（对象、链接、属性、操作），如 create link、write attribute、destroy object。UML 标准定义了：一组动作及其语义；把动作组合成更复杂行为的方法。

类别 例子
Communication actions send、call、receive
Object actions create、destroy、reclassify、start
Link actions create、destroy、read、write
Structural feature actions read、write、clear
Variable actions read、write、clear
Exception actions interrupt、error

三、Activities（活动图）

3.1 定义

Activity：参数化的行为，表示为动作的协调流；包含活动节点（action、object、control），由活动边连接。

3.2 讲义例子：Order Processing（讲义第 22 页，复习课又讲了一遍）

flowchart LR
    I[/order: input param/] --> R[Receive order] --> D{决策}
    D -- 接受订单 --> F[Fill order] --> FK[fork ━━]
    FK --> S[Ship order] --> J[join ━━]
    FK --> SI[Send invoice] --> INV[/Invoice/] --> MP[Make payment] --> AP[Accept payment] --> J
    D -- 不接受 --> M{合并}
    J --> M --> C[Close order] --> E((activity final))
    X>Order cancel request] -. 可中断区域内任何时候 .-> CO[Cancel order] --> E2((activity final))

按讲义原图读一遍：

  1. 输入参数 Order 进来，执行 Receive order。
  2. 接着是一个决策（菱形）：要么去 Fill order，要么直接绕到后面的合并（菱形）去 Close order。两条分支只走一条。
  3. Fill order 之后是一个 fork（粗横线）：Ship order 和 Send invoice → [Invoice] → Make payment → Accept payment 两条分支同时进行，到 join 处等两边都完成。
  4. join 之后进入合并节点，然后 Close order，到活动终点。
  5. 整个过程画在一个可中断区域（虚线圆角框）里：区域内任何时候收到 Order cancel request（凹角五边形，accept event），就沿闪电形边跳到 Cancel order，结束整个活动。
  6. 契约：«precondition» Order entered、«postcondition» Order complete，写在活动框顶部。

老师在复习课上就是拿这张图讲选择和并行的：这里的选择意味着下一个动作要么是 fill order，要么是 close order，“They do not go in parallel”；而 fork 后面的两条分支要并行。

3.3 基本记号

元素 记号 含义
Activity / Action 圆角矩形 一组动作 / 一个任务
Control/Data Flow 箭头 执行顺序 / 对象流
Initial Node 实心圆 开始
Activity Final 牛眼（圆中实心圆） 终止整个活动的所有流
Flow Final 圆中叉 只终止这一条流
Decision / Choice 菱形，一入多出 带守卫，只走一条
Merge 菱形，多入一出 合并不同的决策路径
Fork 粗横线，一入多出 分成并行流
Join 粗横线，多入一出 并行流汇合（等全部到达）
Object Node 矩形（可含状态 [state]） 对象
Pin 动作边上的小方块 动作的输入/输出对象

Activity final vs flow final 是常考易错点：前者结束整个活动（包括其他并行分支），后者只结束到达它的那条分支。

3.4 选择 vs 并行（复习课重点）

选择（Decision / Merge） 并行（Fork / Join）
记号 空心菱形 粗实线条（横或竖）
出口走几条 只走一条（看守卫） 所有出口同时走
出边上要写什么 守卫 [条件]，互斥且覆盖所有情况（可用 [else]） 不写守卫
收口用什么 merge（菱形，多入一出）：任意一条到达就往下走 join（粗线，多入一出）：全部到达才往下走
场景里的信号词 如果 / 否则 / 根据…决定 / 是否 / 批准还是拒绝 同时 / 与此同时 / 一边…一边… / 两件事都要做完才…
Order Processing 里 Receive order 之后：Fill order 或 直接 Close order Fill order 之后：Ship order 和 Send invoice…

画的时候按这个顺序检查：

  1. 每个菱形出边都有守卫，守卫之间不重叠、不遗漏。
  2. decision 配 merge，fork 配 join，不要混用：
    • 用 join 收 decision 的分支 → join 永远等不到另一条，死锁。
    • 用 merge 收 fork 的分支 → 后面的动作会被执行两次。
  3. 并行的两条分支之间没有先后依赖；如果有（必须先开票才能收款），就画在同一条分支上。
  4. 结束：要停掉所有分支用 activity final（牛眼）；只结束某一条分支用 flow final（圆中叉）。

3.5 泳道（Activity Partitioning）

  • 活动分区：把具有共同特征的动作分组
  • 通常对应组织单元或业务参与者
  • 分区准则由建模者决定，可以多维：讲义例子横向分 Sydney / Newcastle，纵向分 Company（OrderDepartment、Accounting）/ Customer

3.6 Agentic 例子：智能健康 agent 预约（活动图）

泳道：Patient / Agent / Scheduling System

flowchart TD
    subgraph Patient
        P1[Request appointment]
        P2[Select preferred time slot]
    end
    subgraph Agent
        A1[Analyze symptoms]
        A2[Suggest self-care advice]

四、Interactions（交互）

4.1 概念

  • 交互关注协作实例之间通过消息的通信
  • 需要事先定义协作结构作为交互的上下文（Week 6 的协作/角色就是这个上下文）
  • 三种具体记号：顺序图、通信图、交互概览图

4.2 顺序图

顺序图捕获消息从一个对象到另一个对象的时间顺序。

先定参与者：复习课上老师强调，画交互图第一步是确定谁在通信，它们应该是对象、组件或 stakeholder，不能是函数或状态。生命线上的对象最好和类图/对象图里的类或对象对得上，消息对应那个类的操作。

元素 说明
Interaction Frame sd ATM-transaction 外框
Lifeline 一个对象或一个 part；顶部方框 + 向下的虚线
Message 从发送者到接收者的箭头；垂直位置表示顺序
Interaction Occurrence ref CheckPin：引用另一张图里定义的交互
Combined (in-line) Fragment alt [chk = OK] … [else] …

ATM 例子：

sequenceDiagram
    participant client
    participant atm
    participant dbase
    client->>atm: insertCard
    Note over client,dbase: ref CheckPin
    alt chk = OK
        Note over client,dbase: ref DoTransaction
    else
        atm->>client: error("badPIN")
    end

其中 sd CheckPin：atm → client: askForPIN；client → atm: data(PIN)；atm → dbase: check(PIN)；dbase → atm: result(chk)；atm → client: result(chk)。

4.3 通信图

  • 用带序号的消息显示对象之间的交互；强调结构关系而非时间轴
  • 例：RedundantSystem 中 client --1: query--> arbiter --2a/2b: get--> backup1 / backup2（2a、2b 表示并发）
顺序图 通信图
强调 时间顺序 对象之间的链接结构
顺序表示 垂直位置 消息序号（1、2a、2b…）

复习课上老师的说法：通信图让开发者一眼看出谁和谁能通信、谁和谁不通信，但时间顺序只能靠序号看出来。

练习：把上面 ATM 顺序图里的 CheckPin 画成通信图

flowchart LR
    client[":client"] -- "1: insertCard()<br/>3: data(PIN)" --> atm[":atm"]
    atm -- "2: askForPIN()<br/>6: result(chk)" --> client
    atm -- "4: check(PIN)" --> dbase[":dbase"]
    dbase -- "5: result(chk)" --> atm

画法：对象框里写 名字 : 类（带下划线），对象之间画链接（实线），消息写在链接旁边，形如 序号: 消息名(参数) 加一个指向接收者的小箭头。并发消息用 2a、2b，嵌套调用用 1.1、1.2。

4.4 交互概览图

  • 提供控制流的概览，流的节点是交互（ref Authorization、内联的 sd 片段、ref DoMore）
  • 包含初始节点、流终止、活动终止、决策、合并、fork、join 节点——即“活动图的外壳 + 交互作为节点”
  • 复习课的说法：整体是一个流程，里面每个节点又是一张顺序图

练习：ATM 取款的交互概览图

flowchart TD
    S((start)) --> A["ref CheckPin"]
    A --> D{决策}
    D -- "[chk = OK]" --> T["ref DoTransaction"]
    D -- "[else]" --> E["sd Error<br/>atm → client: error(badPIN)"]
    T --> M{合并}
    E --> M
    M --> F((end))

画法：节点用 ref 名字 框（引用别处定义的顺序图），或者直接把一小段 sd 顺序图画在框里；节点之间用活动图的箭头、菱形、粗线连起来。

4.5 Agentic 例子：智能健康 agent 预约（顺序图）

sequenceDiagram
    participant patient
    participant agent as agent: booking
    participant system as system: booking
    patient->>agent: Provide symptoms & request
    agent->>agent: Analyze symptoms
    alt chk = need doctor
        Note over patient,system: ref Make booking
    else chk = mild
        agent-->>patient: Provide self-care advice
    end

sd Make booking：agent → system: Request appointment / available slots；system → agent: Return slots；agent → patient: Present slots；patient → agent: Select slot；agent → system: Confirm booking；system → agent: Send Confirmation；agent → patient: Notify patient。

五、State Machines（状态机）

5.1 事件

  • 状态图通过有限状态转移展示设计系统某部分的离散行为；用于描述事件驱动的行为
  • Event = 系统中瞬时的状态变化：
    • message event：对象收到操作调用或信号
    • change event：系统配置变化（如 when(temp > 30)）
    • time event：在指定时间发生（如 after(1sec)）
  • Event occurrence = 事件的实例，发生在某个时刻，没有持续时间

5.2 基本记号

元素 记号
Initial pseudostate 实心圆
State 圆角矩形（如 Ready）
Transition 箭头，标签 trigger [guard] / behavior（如 stop / ctr := 0）
Final state 牛眼

5.3 Entry / Exit 动作与执行顺序

  • entry/ lamp.on(); exit/ lamp.off(); —— 一种动态断言机制：只要处于 LampOn，灯就一定亮
  • 顺序规则：exit 动作在转移动作之前，entry 动作在转移动作之后

讲义例子：LampOn { entry/lamp.on(); exit/printf("exiting"); }，LampOff { entry/lamp.off(); exit/printf("exiting"); }，转移 LampOn --off/printf("to off")--> LampOff，以及 LampOff 上的自转移 off/printf("needless")。

情况 动作序列
LampOn 收到 off printf("exiting") → printf("to off") → lamp.off()
LampOff 再收到 off（外部自转移） printf("exiting") → printf("needless") → lamp.off()

自转移也会先退出再进入，所以 exit 和 entry 都会执行。

5.4 状态机答题模板（复习课重点：entry/exit）

老师在复习课上讲了三件事：

  1. 状态机和活动图都用圆角矩形，很容易混。状态机里的节点不是对象，也不是函数，而是系统的状态。
  2. 要会这些记号：转移、触发事件、动作、初始状态、终态。
  3. 每个状态要定义 entry 和 exit 动作，每个事件都要有对应的动作。系统的行为就是事件触发的动作序列：离开一个状态执行 exit，进入下一个状态执行 entry。

画题步骤：

  1. 定对象：这张状态机描述的是哪一个对象的生命周期（订单、预约、agent 的一次运行）。
  2. 列状态：用“一段持续的情况”命名，如 WaitingForPayment、Shipped，不要写成动作（“付款”“发货”是动作，属于转移或 entry）。
  3. 起点和终点：实心圆指向第一个状态；有结束的话画牛眼。
  4. 每个状态写 entry/ 和 exit/：进入时做什么、离开时做什么。
  5. 每条转移写 事件 [守卫] / 动作：同一状态、同一事件的多条转移，守卫要互斥。
  6. 有共同出口的几个状态（比如都能被取消）→ 包进一个复合状态，从边界画一条组转移。
  7. 自查：挑一个事件，按 exit（由内向外）→ 转移动作 → entry（由外向内） 写出动作序列，看是否符合场景。

例：网上订单 Order

stateDiagram-v2
    [*] --> AwaitingPayment
    AwaitingPayment --> Paid : paymentReceived / issueReceipt()
    AwaitingPayment --> Cancelled : cancel / notifyCancelled()
    Paid --> Shipped : dispatched / sendTracking()
    Paid --> Cancelled : cancel / refund()
    Shipped --> Closed : delivered / closeOrder()
    Cancelled --> [*]
    Closed --> [*]
状态 entry/ exit/
AwaitingPayment startPaymentTimer() stopPaymentTimer()
Paid reserveStock() logPaid()
Shipped notifyCustomer() logShipped()
Cancelled releaseStock() —
Closed archiveOrder() —

在 Paid 收到 cancel：logPaid() → refund() → releaseStock()。

5.5 守卫

  • 转移的条件执行；守卫是布尔谓词，必须无副作用
  • 例：Selling 状态收到 bid：[value < 100]/reject → Unhappy；[value >= 200]/sell → Happy；[(value >= 100) & (value < 200)]/sell → Unhappy
  • 守卫应互斥且完备，否则可能出现多个转移同时使能或没有转移可走

5.6 Junction vs Choice（常考）

Junction（静态条件分支） Choice（动态条件分支）
记号 实心小圆点 空心菱形
守卫何时求值 在转移被执行之前全部求值 到达 choice 点时才求值
用途 只是画决策树的图形捷径 守卫可以依赖转移前半段动作计算出的结果
例子 bid 后按 value 分支 bid / gain := calculatePotentialGain(value) 之后按 gain 分支

判断：守卫用到的变量是不是在这条转移的前半段才被计算出来？ 是 → 必须用 choice。

5.7 层次状态机

逐级应对复杂度：状态可以分解为子状态机。

stateDiagram-v2
    [*] --> LampOff
    LampOff --> LampOn : on/
    LampOn --> LampOff : off/
    LampOff --> LampFlashing : flash/
    state LampFlashing {
        [*] --> FlashOn
        FlashOn --> FlashOff : 1sec/
        FlashOff --> FlashOn : 1sec/
    }
    LampFlashing --> LampOn : on/
    LampFlashing --> LampOff : off/
  • LampOff { entry/lamp.off() }，LampOn { entry/lamp.on() }，FlashOn { entry/lamp.on() }，FlashOff { entry/lamp.off() }
  • Group transition（组转移）：从复合状态 LampFlashing 边界出发的 off/、on/ 转移，无论当前处在 FlashOn 还是 FlashOff 都会触发——避免为每个子状态各画一条
  • 默认转移：进入 LampFlashing 时走向内部初始伪状态 → FlashOn
  • 触发规则：两条或多条转移可以有同一个触发器（例如子状态里的 on/ 和外层的 on/）——内层（更深的）转移优先

5.8 完成转移

  • 由完成事件触发，当直接嵌套的状态机终止时自动产生
  • 例：Committing { Phase1 → Phase2 → final } 结束后，没有标触发器的转移自动走到 CommitDone（隐式触发器）

5.9 复杂动作顺序例题（必会）

问题 答案（讲义） 解释
处于 S1::S11，发生 E1 exS11 → exS1 → act1 → enS2 → enS21 先由内向外退出（S11 再 S1）→ 转移动作 → 由外向内进入（S2 再其默认子状态 S21）
处于 S2::S21，发生 E3 exS21 → act3 → enS2 → enS21 退出 S21；S2 没有定义 exit 动作；转移动作 act3；重新进入 S2 和 S21

5.10 正交区域

  • 用来捕获同一实体的不同并发视角：Person 的 age（Child → Adult → Retiree）和 financialStatus（Poor ↔︎ Rich）是同时成立的两个描述
  • 如果不用正交区域，就要做状态笛卡尔积： 个状态（Child-Poor、Child-Rich…）；用正交区域只需 个
  • 语义：区域并发执行；所有正交区域检测相同的事件并同时响应（实践中通常是某种交错）。例：legalStatus 区域 LawAbiding --robBank/--> Outlaw，financialStatus 区域 Poor --robBank/--> Rich——一个 robBank 事件同时触发两个区域的转移

⚠️ 正交区域的并发是“不同视角”的并发，不应该用来建模并发对象！ 对象并发的语义与区域并发不同。讲义原话：“不幸的是，大多数建模者都是这么用的——不要掉进这个陷阱。”

六、小结与综合例题

6.1 四种行为形式

形式 用途
Actions 细粒度操作
Activities 控制流和数据流的计算模型
State machines 事件驱动的计算模型（单个对象）
Interactions 事件驱动的系统行为（对象间）

尽管不同，它们共享共同的语义基础：面向对象——所有行为源于对象的动作。
Tutorial 6 的说法：Actions 和 Activities 用于微观行为，State Machines 和 Interactions 捕获宏观行为。

6.2 综合例题：Smart Financial Advisor Agent

场景：agent 帮客户规划投资组合——收集财务目标和风险偏好 → 分析当前市场数据 → 生成投资建议 → 用户批准后通过 Brokerage System 执行交易 → 跟踪组合表现并发通知 → 处理异常（市场崩盘、交易被拒）。

为什么比健康例子复杂：持续监控（循环）、集成多个外部系统（Market API、Brokerage）、分支（批准/拒绝/替代方案）、异常处理。

解答要点（讲义给出的关键信息 + 展开）：

活动图：泳道 Client / Smart Financial Advisor Agent / Market Data API / Brokerage System

状态机（Agent）：Idle → CollectingProfile → Analysing → Recommending → AwaitingApproval；AwaitingApproval --approve--> Executing --tradeOK--> Monitoring；--reject--> Recommending；Executing --tradeRejected--> HandlingException；Monitoring 中 after(period)/checkPerformance() 自转移，marketCrash 事件 → HandlingException。

讲义强调：状态机关键是“define correct states”——状态应该是一段持续的条件（等待批准、监控中），而不是一个动作（“分析”这类瞬时动作更适合放在 entry 或转移上）。

七、Tutorial 7 要点与解答思路

7.1 活动图用来做什么

  • 描述活动如何协调以提供服务（可在不同抽象层次）
  • 适合：需要协调的操作、单个 use case 内事件之间的关系（尤其是活动可能重叠需要协调的）、多个 use case 协调组成业务工作流
  • 使用步骤：通过业务工作流识别候选 use case → 识别 use case 的前后置条件 → 建模 use case 之间/内部的工作流 → 建模对象操作中的复杂工作流 → 在高层活动图中详细建模复杂活动

7.2 例题：Process Order（必练）

收到订单后分成两组并行活动：一边 Fill Order 并发货，另一边处理账单。Fill Order 一侧按条件决定配送方式：Overnight Delivery 或 Regular Delivery。最后并行活动汇合，关闭订单。

flowchart TD
    S((start)) --> R[Receive Order] --> F[fork ━━]
    F --> FO[Fill Order] --> D{delivery?}
    D -- overnight --> OD[Overnight Delivery]
    D -- regular --> RD[Regular Delivery]
    OD --> M[merge ━━]
    RD --> M
    F --> SI[Send Invoice] --> RP[Receive Payment]
    M --> J[join ━━]
    RP --> J
    J --> CO[Close Order] --> E((end))

关键得分点：fork/join 用于并行；decision/merge 用于条件；不要用 join 去合并 decision 的分支（会死锁——join 要等所有入边都到达，而 decision 只走一条）。

7.5 组合片段（常考）

操作符 含义
alt 多个备选片段，只执行条件为真的那个
opt 条件为真才执行；等价于只有一个分支的 alt
par 各片段并行执行
loop 可执行多次，守卫给出迭代依据
critical 临界区，同一时刻只能有一个线程执行
neg 表示无效的交互
ref 引用另一张图中定义的交互；框覆盖所涉生命线，可带参数和返回值
sd 包围整张顺序图
（还有 break、assert）

7.6 例题：Place Order（顺序图）

基础版：Customer、Order、Stock 三个对象——1–2 Customer 创建 Order；3 添加商品；4–5 对每个商品检查库存（loop）；6–8 若有货则加入订单（opt/alt）；9 返回；10–11 保存并销毁 Order。

扩展版：会员下单，按会员状态（VIP → courier，Ordinary → ordinary mail）选择配送——用 alt [VIP] / [else]；如果会员选择了通知选项，商店可选地发送确认——用 opt [notification requested]。

判断 alt 还是 opt：有两条及以上互斥分支 → alt；只有“做或不做” → opt。

八、本周考点速记 / 易错点

  1. UML 因果模型：离散事件驱动、对象网络、所有行为源于对象；动作由对象执行。
  2. 主动 vs 被动对象：被动对象一被调用就响应（可能冲突）；主动对象只在 receive 时响应（消息队列）。
  3. 选择 vs 并行：菱形 decision 只走一条（出边写守卫），配 merge；粗线 fork 全部同时走，配 join（全部到达才继续）。Order Processing：Receive order 后“fill 或 close”是选择，Fill order 后“ship 和 invoice”是并行。
  4. 状态机每个状态写 entry/exit，转移写 event [guard] / action；状态是系统的状况，不是对象或函数。
  5. 同步 = call and wait（实心箭头）；异步 = send and continue（开放箭头）。
  6. 六类动作：communication、object、link、structural feature、variable、exception。
  7. 活动图记号：activity final（全停）vs flow final（一条停）；decision/merge vs fork/join；泳道。
  8. 交互需要协作结构作为上下文；先定参与者（对象/组件/stakeholder，不是函数或状态）；三种图：顺序（时间顺序）、通信（链接结构 + 序号）、交互概览（活动图外壳 + ref 节点）。
  9. 组合片段：alt、opt、par、loop、critical、neg、ref、sd（+break、assert）。
  10. 事件三类：message、change、time；事件发生没有持续时间。
  11. 动作顺序：exit（由内向外）→ 转移动作 → entry（由外向内）；自转移也会 exit 再 entry。
  12. Junction（静态、预先求值）vs Choice（动态、到达时求值）。
  13. 组转移、完成转移、默认转移；内层转移优先。
  14. 正交区域 = 同一实体的不同视角，不要用来建模并发对象；避免状态笛卡尔积爆炸。
  15. 易错：用 join 合并 decision 分支；守卫有副作用；状态命名为动作；顺序图里的对象与类图对不上。
