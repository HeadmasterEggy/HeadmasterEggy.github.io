Codex Subagent 逆向笔记：从 spawn_agent 到父子线程协作

Posted on 2026-10-13 In AI Agent Word count in article: 35k Reading time ≈ 2:06
结合 ChatGPT 桌面版内置 codex-cli、客户端 JavaScript 与公开 Codex 源码，拆解 子 Agent 的创建、上下文继承、协作消息、等待、完成回传和界面状态，并标注版本与证据边界。

Codex 的 subagent 看起来像“主 Agent 派出几个小 Agent 并行工作”。从实现证据看，更准确的模型是：父 Agent 通过协作工具请求创建一个有独立线程身份的子 Agent；共享的 Agent 控制器负责登记、调度、通信和回收父子关系；客户端再把这些状态呈现成活动列表。

本文结合本机 ChatGPT 桌面应用内置 codex-cli 的静态分析、应用资源中的 UI JavaScript，以及 OpenAI codex 仓库与本机版本号一致的源码 tag 交叉整理。版本号相同提高了源码对照的可信度，但没有签名构建清单证明本机二进制确由该 commit 构建；因此我仍把本机观察和源码解释分开说明。

先看整条链路

图中是几条相互关联但不等价的路径：工具返回、活动事件、父线程 mailbox、thread 状态/history 和 Work 面板的 final-response query 各有自己的数据契约。wait_agent 不是等待一个“child 对象 join 完成”的单一同步点；child 完成也不意味着每个 UI 查询已经拿到 final answer。控制器与 mailbox 的语义来自匹配版本源码，事件映射和 UI/query 路径来自本机桌面 bundle 静态分析；箭头表示代码中的数据/调用关系，不表示一次实测请求的严格时间顺序。

上图中从工具处理器到子线程创建、持久化关系和首条输入的步骤，来自版本 tag 源码；本机二进制中也能找到相应符号和校验字符串，但静态反汇编没有独立证明所有异步分支的具体运行顺序。

1. 工具调用不是直接启动一个 shell 子进程

该版本源码中的 V2 spawn handler 会把模型给出的 agent 描述整理成 SpawnRequest，其中包含发起者、配置、初始消息、父子关系及 fork 选项，然后交给 agent_control.spawn(...)。初始消息被指定为触发 child 新一轮执行的输入。可对照 V2 spawn handler。

spawn 成功后的模型可见工具结果也不是 child 的 thread id：结果 JSON 返回规范化的 task_name，并按 hide_spawn_agent_metadata 决定是否附加 nickname；内部控制器和 Started 活动则仍持有真实 agent_thread_id。所以工具结果里的任务名是 agent path 标识，不能当作可传给 V1 wait 或其他 thread-id 参数的值。这里描述的是工具输出结构和协议字段，不代表 UI 一定向用户显示了同一组值。见 V2 spawn 结果构造、V2 默认配置 和 活动协议字段。

对照 V1 handler，工具结果的身份契约不同：它返回 agent_id（child thread ID 字符串）和可选 nickname。V1 还在 spawn 前后发出 CollabAgentToolCall turn item，携带 sender/receiver thread IDs、prompt、模型、reasoning effort 与 agent 状态；成功后再把 thread ID 写进模型可见的 agent_id。因此旧版 wait_agent.targets 可以直接使用 spawn 返回的 ID；V2 的 task_name 则不能这样用。见 V1 spawn handler 和 V1 wait handler。这是匹配版本源码中的协议差异；它不证明桌面 UI 怎样渲染该 turn item。

时序上，控制器先等待 spawn edge 写入，再提交 child 的首条输入，提交 residency/registry 预留并返回 LiveAgent；V2 handler 收到成功结果后才发 Started 活动。因此这个 Started 表示创建与输入 admission 已成功到达控制层，不是 child 已经开始推理或完成任务的证明。输入被接纳后何时实际获得执行 permit，属于后续调度路径。见 控制器 spawn 顺序 与 handler 的 Started 发射。

控制器的 spawn_agent_internal 随后会：

  • 取得 agent-tree membership，并确定 parent thread；
  • 计算适用的 multi-agent 版本并检查执行容量；
  • 向 registry 预留 slot；
  • 解析继承的 environment、插件设置和执行策略；
  • 生成 SessionSource::SubAgent(ThreadSpawn { ... }) 及 AgentMetadata；
  • 按需准备 fork history，再调用 ThreadManager 创建 child thread；
  • 持久化 thread-spawn edge，之后提交首条输入。

这条路径表明 Codex 的抽象中心是 thread/session 与 agent tree。被分析的调用路径没有显示“每个 subagent 再启动一份独立 codex 可执行文件”的证据；但仅凭这段静态证据，也不应把它扩大成对所有平台、所有运行模式的绝对断言。相关实现见 AgentControl spawn 流程。

2. 子线程有独立身份，也保留父子来源关系

child 并非只是在父会话里追加一段带标签的对话。它有自己的 thread id、session source 和 agent path；source 元数据记录父 thread、层级和路径。控制器还会把 spawn edge 持久化，供后续恢复和父子关系查找使用。

“有独立线程身份”不等于“完全隔离”。创建时仍可能从父级继承环境选择、插件禁用列表、执行策略和动态工具；如果请求指定 fork mode，还会准备历史记录。公开源码注释特别指出：复制对话历史不应改变发起 spawn 的那一轮原有能力。具体继承项取决于请求、配置及当前 feature，不能把它简化成“所有上下文都复制”或“子 Agent 从零开始”。

在新 thread 建好并建立关系后，控制器才提交初始输入；代码分别处理普通 user input 和 inter-agent communication。V2 下还会解析模型信息等启动配置。此后 child 作为独立执行单元继续跑自己的 agent loop。

2.1 child 实际拿到什么：首条消息、配置和历史

V2 spawn_agent 的 message 会成为 child 的第一条 AgentInput::Message，并以 TriggerTurn 模式触发新一轮执行。处理器还会依调用来源把它包装为 AgentMessage::Plaintext 或 AgentMessage::Encrypted；这是源码选择的输入类型，不足以单独推断后续传输或模型侧的解密细节。也就是说，fork_turns: "none" 仍会收到显式传入的 message，只是不会 fork 父线程历史。见 V2 spawn handler 与 消息类型选择。

fork_turns 的默认值是 all；none 表示新建上下文，all 表示完整历史 fork。兼容旧调用的正整数也会被接受，但实现并不会按数字截取轮数。V2 已拒绝旧参数 fork_context。新建上下文时，代码可能保留父线程的 paginated history 模式；只有 V2 dynamic-tools 功能开启时，才复制父会话的 dynamic tools。完整历史 fork 则读取 parent model context，再过滤某些 AgentMessage、父会话专属元数据及可能需要替换的指令片段。它不是把 rollout 文件原样复制过去。相关分支见 参数解析 和 fork / fresh thread 创建。

child 的基础配置从发起 spawn 时的 live turn 构造，会同步当时生效的模型/provider/reasoning、developer instructions、approval policy、reviewer、工作目录和 permission profile。请求指定的模型或 reasoning effort，以及已配置的 subagent 默认值，会经过模型目录和能力校验后应用。agent_type 对应的 role 在此基础上再叠加有限配置：源码允许角色提供指令、模型、性格、服务等级，或关闭部分 feature/skill；角色不能替换父会话的 authority。完整历史 fork 默认继承父角色；V2 显式指定 agent_type 时才应用角色覆盖，V1 则拒绝这种组合。见 child 配置准备 和 role 配置覆盖。这些是匹配版本源码定义的组装规则，并不证明某个在线 child 实际解析到的值。

工具集合也不是把父 Agent 的 registry 整体复制给 child。child session 保存被选中的 dynamic-tool snapshot；每轮再结合 child 自己的 turn config、environment snapshot、MCP binding、extensions 和 dynamic tools 构造 tool router。role 对 feature 的覆盖只收集对 shell、apps、plugins、memory、request-permissions 等指定 feature 的关闭操作；角色文件里的开启项不会通过这段 overlay 被应用。因此可以确认动态工具存在明确的 V2 条件继承，而其他可用工具由 child 配置与当时的 MCP/extension/model 条件共同决定。源码不足以列出某个实际 child 当时看到的完整工具清单。见 session 初始化、每轮工具路由构建、工具注册计划 和 role feature overlay。

再看模型收到的工具 contract：V2 schema 要求 task_name 和 message；agent_type、模型和 reasoning 覆盖是否出现，取决于构造工具时的 options。工具描述会列出配置中的用户角色和内置角色，部分角色描述还会注明模型或 reasoning 已锁定。这里有个值得记录的描述差异：schema 文本说 fork_turns 只支持 all 和 none，但实际 parser 也接受正整数，并把它映射成完整历史 fork，不会据数字限制历史轮数。schema 把该字段定义为字符串而没有枚举校验，因此这是模型可见描述比实际 parser 更窄。见 V2 工具 schema、角色描述构造 与 fork 参数解析。

3. 并行受容量与登记机制控制

spawn 不只是创建 thread。控制器会先登记 membership、检查 execution capacity，并通过 registry 预留 spawn slot；V2 resident 模式还有对应的 residency slot。成功后才 commit 这些登记。源码也有 PendingSpawn，在创建尚未完成时暂时持有 agent-tree membership，避免一个“待完成 spawn”失去树上的归属。

execution capacity 对应的是正在执行的 V2 子 Agent turn：session 用 effective V2 max-thread 设置初始化 limiter；turn 开始时取得 RAII guard，并由 task 持有到执行结束。spawn 阶段的 capacity 检查、turn 的执行 permit、registry 的 thread 记账和 resident slot 是不同层的控制。

本机二进制字符串里出现了 max_concurrent_threads_per_session、min_wait_timeout_ms、max_wait_timeout_ms 等配置名，以及“pending spawn must own agent-tree membership”一类错误文本。这些只能证明该构建包含相关配置与防护逻辑；没有检查运行时最终配置，不能据此给出具体并发上限。

spawn 路径还为失败和取消准备了回滚边界。线程建好后，PendingSpawn 暂时持有 child 与 agent-tree membership；只有首条输入被接收后才 disarm 并提交 registry/residency reservation。若此前发生错误，drop 清理会异步移除并停止 child、尽可能丢弃 rollout，等待可能尚未结束的 spawn-edge 写入，再把边标成 closed 并释放 membership。未提交的 registry reservation 也会通过 drop 归还计数与预留 path。这里是源码规定的清理流程，不是本次故障注入的运行时观察。见 spawn guard 与 registry reservation。

4. wait_agent 等待的是活动，不是 join

V2 wait_agent 没有 targets 参数。它按当前 sub-turn 找到对应的 turn state，然后订阅 session input queue 的 activity；订阅发生在检查 pending activity 之前，避免错过已经排队的活动。已有的 user input 或 function-call output 被归为 steer；pending inter-agent communication 被归为 mailbox，若两类都在 pending turn state 中，steer 优先。新消息成功加入当前 turn mailbox、session mailbox 入队或显式 mailbox 通知会发布 mailbox activity；新输入并入 turn queue 会发布 steer。若已有 pending activity，handler 立即返回；否则等待 watch channel 变化或 deadline。结果分为 mailbox activity、被新输入 steer、超时三类。超时来自请求值或配置默认值：低于配置下限会抬到下限，高于上限则返回参数错误；源码默认下限为 10 秒、默认值 30 秒、硬上限 1 小时，配置可改变这些值。channel 是 watch 型，重复变化可能合并，handler 读取唤醒时的当前 activity。

因此 V2 版本不是按 child ID 做 join(child)：它不查看某个 child 的终态，mailbox activity 或 steer 都可能结束本次等待；timed_out 只在 deadline/channel 关闭时为 true。实际 V2 completion result 使用单独的 inter-agent message 路径，等待被 mailbox activity 唤醒也不等同于父模型已经消费了结果。具体实现见 V2 wait handler、input queue activity 和 timeout defaults。

同名 legacy wait_agent 是另一种契约：它接收 targets thread ID 列表并订阅各目标的 status，最先到达终态的目标会结束等待；多个目标同时已终态或在首次完成时已就绪的结果可以一起返回。没有目标时不会等待，timeout 必须为正数，再 clamp 到默认范围。结果包含已观察到的目标状态和 timed_out。所以需要区分版本：V1 是“等指定 child 状态”，V2 是“等当前 turn 的输入队列活动”。来源：legacy wait handler、V2 wait handler 和 tool schemas。

V2 工具说明称 mailbox 更新会返回“哪些 agent 有更新”的摘要，但当前 handler 的实现只返回固定的三种 message 和 timed_out，输出 schema 也没有 agent 列表或更新内容字段。因此这段说明不能当成实际 wait 结果会指出具体 child；具体消息内容仍需从 parent turn 的 mailbox/model context 读取。这是匹配 tag 内部的描述与返回结构差异，不代表某次在线会话的模型行为。

还有一个时序边界：wait_agent 的初始 pending 检查通过 has_pending_mailbox_items() 判断 session mailbox 是否非空，这个检查不读取当前 turn 的 MailboxDeliveryPhase。但真正把 mailbox 通信加入当前 turn 输入队列时，会检查该阶段；队列读取路径也只在 CurrentTurn 时才 drain mailbox。助手输出可见 final-answer 文本后，源码会把 mailbox delivery 推迟到 NextTurn（若仍有明确的同轮工作则保留当前轮）；后续工具调用、需要 follow-up 的模型输出或新 steer 输入会重新开放当前轮。于是，wait 因 mailbox 队列活动而返回，并不保证该消息能进入当前这次模型请求；它可能仍留待下一轮。来源：mailbox phase 与输入队列、final-answer 阶段切换 和 V2 wait。这是匹配 tag 的静态源码结论，尚未通过在线 session 时序实验验证。

本机二进制中还能找到 spawn、wait、list_agents、send_message、followup_task、interrupt_agent 等 V2 handler 名称，也能找到 legacy agent handler 符号。它们说明构建中存在这些操作面；不同版本、feature flag 和产品界面暴露哪些工具，需要另外确认。

一个会话为什么走 V2：版本选择顺序

在这份匹配版本源码里，features.multi_agent_v2 的显式配置覆盖会选 V2；全局 agent 功能明确禁用时选择 Disabled。否则新 child 会先尝试从 parent/source 或 fork/resume history 继承版本，再回退到配置特性：Collab 对应 V1，没有开启则 Disabled。旧历史若没有记录版本元数据，会按 V1 恢复。turn 初始化还会读取模型元数据作为候选版本，但配置覆盖优先；会话确定版本后会记入 session 状态。

所以二进制里存在 V2 handler，并不能证明某一个窗口或会话实际用了 V2。最终分支还取决于 feature/config、模型元数据、parent/history 继承和 session 初始化。后来我对本次研究所用的 Codex Desktop 会话做了结构化核对：rollout 的 session_meta 标记 originator=Codex Desktop、版本 0.162.0-alpha.17.2，48 条 turn_context 全部记录 multi_agent_version=v1。桌面 app-server 正在使用的本机状态库中，该 thread 没有 agent_path，thread_spawn_edges 没有指向它或从它发出的边；thread-history 投影中也没有 collabAgentToolCall 或 subAgentActivity 项。因此，现有证据支持“本次研究会话记录为 V1，且没有观察到子 agent 或持久化 spawn 关系”；它不代表其他会话或桌面默认值，也不排除未写入这些记录面的其他执行路径。来源：Config 版本优先级、spawn 版本继承与回退 和 历史版本恢复。

紧接着我做了一个反向验证：用同一嵌入式 CLI 启动全新的 exec，传入 --ignore-user-config --enable multi_agent --disable multi_agent_v2，只要求创建一个固定回复的 child。单独运行的 features list --disable multi_agent_v2 显示 V2 为 false；debug models 的输出也把 gpt-6.1-sol 标成 v1。但该新 exec 的 rollout turn_context 仍记录 multi_agent_version=v2，实际 spawn 调用使用 V2 形状并只返回 task_name，child 正常返回固定文本。匹配 tag 的 selector 代码说明，关闭 multi_agent_v2 只会取消配置对 V2 的强制选择；只要 agents 仍启用，它会继续检查当前 turn 的 ModelInfo.multi_agent_version，缺值时才回退到 feature fallback。源码还澄清了观测口径：codex debug models 会自行构造配置和模型管理器，再输出一次 raw_model_catalog；会话则从其模型管理器取活动目录，按当前模型名匹配候选并生成 ModelInfo。两个调用位于独立命令/会话上下文，不能把 debug 输出当作该 turn 实际消费的元数据快照。匹配 tag 的 with_config_overrides 不会改写 multi_agent_version，所以配置覆盖不是目前已知的差异来源。只读检查本机模型缓存时，只取出 gpt-6.1-sol 的版本字段和缓存时间：该缓存记录为 v1，fetched_at=2026-10-13T10:35:56Z；而探针 rollout 创建于 10:28:48Z，所以这是探针之后的目录快照。匹配 tag 的默认缓存 TTL 为 300 秒；源码和时间戳说明缓存会刷新，但不揭示探针当时 session 内存里的目录值。当前可确认的是：这次 turn 最终得到的版本与单独 debug models 输出的版本不同；可能的目录/上下文差异有源码路径支撑，但尚未直接观测本次会话使用的候选 ModelInfo，因此具体差异来源仍未知。--disable multi_agent_v2 不是已验证的强制 V1 方法。证据来自本机 CLI rollout/命令输出及匹配 tag 的 resolve_multi_agent_version_for_model、multi_agent_version_for_model、debug models 实现、模型目录候选匹配 与 ModelInfo 配置覆盖。静态源码确认 selector 的输入/优先级和两种查询的处理流程，不确认本次 turn 实际采用的目录内容；该探针仅代表本次新建 exec。

V2 工具表面也受配置控制

匹配 tag 的 MultiAgentV2Config::default() 中，wait_agent_enabled、expose_spawn_agent_model_overrides 默认开启，disable_direct_message 默认关闭，hide_spawn_agent_metadata 和 non_code_mode_only 默认开启。这是源码默认值，解析后的配置可以覆盖。tool plan 还会先检查当前 turn 是否允许 collaboration tools、版本是否为 V2；non_code_mode_only 会在 ToolExposure::DirectModelOnly 与 Direct 之间选择。disable_direct_message 会同时省略 send_message 和 followup_task，而 wait_agent_enabled 单独控制 wait_agent 是否注册。spawn schema 里的 agent type、model、reasoning 字段还受各自配置控制。

这些规则解释了为什么只看到某个 handler 的二进制字符串，无法推出当前 session 的模型实际收到了哪些工具。来源：V2 默认配置、tool plan 注册条件 和 spawn schema。

5. send_message 排队，followup_task 触发新一轮

这两个工具共用一条消息处理路径：先拒绝空白消息，再把目标解析成 thread ID，从调用方当前 turn 构造恢复配置，提交 AgentInput::Message，成功后向调用方会话发出 Interacted 活动。它们的关键差别是 delivery mode：send_message 使用 QueueOnly，followup_task 使用 TriggerTurn。这不是两个不同的消息格式，而是两种不同的投递与唤醒策略。

对已加载的子 Agent，send_message 把普通通信放进它的 session mailbox；若子 Agent 正在运行且当前 turn 接受 mailbox 输入，它可能在该 turn 中收到消息，否则消息留待之后处理。目标未加载时，消息保存在本地 runtime mailbox，之后加载 session 再转入输入队列。普通空闲 session 收到 QueueOnly 消息不会因此自动开新 turn；源码里只有存在 durable sleep 时，队列处理才会额外尝试唤醒。

followup_task 则会确保 V2 目标 session 已加载，并把通信标成 trigger turn。明文消息类型是 NewTask；加密消息通过通信对象上的 trigger 标志表达同样的唤醒意图。session 在有待处理 mailbox 消息且当前空闲时，由共享 pending-work scheduler 创建普通 turn。触发式 follow-up 还会检查执行容量，并拒绝把 root agent 作为目标。

如果目标 child 已从内存卸载，恢复使用原 thread ID 和保存的会话历史/rollout，并要求历史记录仍属于 V2；它不会走 spawn 路径再造一个 child。由父代理主动执行的恢复会验证父线程仍在运行、父子关系一致且共享同一 runtime registry。followup_task 的 sender-driven 路径没有传入 parent 对象，因此由控制器根据保存的 child source、历史和恢复配置重新加载。换句话说，follow-up 可以唤醒一个已卸载的现有 child，但“能否恢复”仍受保存状态与当前配置校验约束。见 V2 恢复实现 和消息发送入口。

两种恢复入口重建配置的方式并不相同。父线程主动恢复时，controller 从父线程当前 turn 生成 child 配置，再恢复 child 保存的 reasoning effort、model 和 provider；若 source 指定了 agent role，则重新应用 role，但保留当前 approval policy、cwd 和 permission-profile snapshot。执行策略若已不再符合父子继承条件，恢复会失败。缓存的环境选择还要与父线程当前 ready environment 的 ID、cwd 和 workspace roots 精确匹配；pending/failed 状态会被拒绝，配置不一致也会被拒绝。对于本地执行器，旧 child 权限会与当前 owner 权限求交；远端执行器出现权限变化时则拒绝恢复。这些检查说明恢复不会直接把旧权限当作仍然有效。源码见 V2 恢复与环境校验。

消息工具触发的恢复没有传入 parent 对象。它沿 child 保存的 ThreadSpawn source 查找已加载父线程，以便继承环境快照；执行策略只有通过父子兼容检查才会继承。该路径没有从 parent 对象传入 client MCP extensions。父线程已加载时会读取它的 inherited instructions；否则回退到共享 instructions provider。也就是说，“恢复原 child”明确保留 thread/history 身份，但运行配置是否从当前父线程重建，取决于调用入口。相关来源：环境与执行策略继承 与 V2 恢复实现。

因此，send_message 更像投递一条稍后可读的协作消息，followup_task 更像给指定子 Agent 安排后续一轮。两者工具调用成功并发出 Interacted，都只证明通信被接受或留存，不能单凭这个活动断言目标模型已读取消息。以上来自匹配版本源码静态分析，没有在本机实际启动子 Agent 做运行时验证。见 共享消息处理器、send_message、followup_task、controller 投递、session mailbox 处理 和待处理工作调度器。

中断、关闭与恢复是不同动作

V2 interrupt_agent 先读取目标当前状态，再派发中断，并把中断前的状态作为工具结果返回；成功路径会在调用方会话上发 Interrupted 活动。它拒绝 root 和 self target。若目标已卸载或内部 session 已结束，中断派发遇到对应的 not-found/dead 错误会按成功处理，而且中断路径本身不会为了操作去重载目标。因此这个活动说明工具走完了可接受的中断路径，不单独证明目标当时确有运行中的 turn 被取消；返回的 status 也是派发前快照。

中断不会把子 Agent 从树中关闭。显式 close_agent 才会先把持久化 spawn edge 标为 closed，再关闭目标及当前仍存活的后代；普通 shutdown 会移除运行时登记，但源码刻意不在该操作本身关闭 spawn edge。之后的 followup_task 则走触发新 turn 的消息路径，并确保 V2 子 Agent session 已加载。因此界面上的 Interrupted 活动、Agent 当前状态和 spawn-tree 边是否关闭，应分别理解。以上是匹配版本源码静态路径，没有进行本机中断/恢复实验。见 V2 interrupt handler、interrupt controller、shutdown 与 close 和触发式消息加载路径。

状态映射里，显式中断和 budget-limited abort 都会成为 Interrupted。这个状态在 agent status 逻辑中不算 final，普通完成消息格式化也会跳过它；因此不能把“被中断”当成“正常完成但结果为空”。不过 residency 管理采用另一套条件：只要没有活动 turn、durable sleep 或 trigger-turn mailbox 项，Interrupted 与 Completed、Errored 一样可以从内存卸载。结合上面的 spawn edge 语义，这意味着 child 可以处于非 final、已卸载、关系边仍打开的状态，之后再通过 follow-up 恢复。相关来源：状态映射、完成消息格式化 和 residency 淘汰条件。以上仍是静态源码分析，没有做本机中断、淘汰和恢复实验。

同一组工具中的 list_agents 也有明确边界：它先从内存 registry 取得 agent metadata，再查询 thread manager 的已加载 session 并读取状态；当前没有加载的已知 child 会被跳过。可选 path_prefix 按调用者自己的 agent path 解析。根 Agent 只有在其 thread 已加载时才会出现在结果里。因此这个工具适合看当前 runtime 中可见的 agent 状态，不能当作完整的历史子线程目录；桌面 UI 另有持久化 thread/list 与历史发现路径。见 V2 list handler、AgentControl list implementation 和registry view。

6. 完成通知按 agent 版本分流

与本机 CLI 版本号对应的公开 tag 源码中，control.rs::maybe_start_completion_watcher 是 legacy 路径。它只接受带结构性 parent 的 ThreadSpawn 来源，并先向 agent-tree runtime 登记 watcher 工作；fresh spawn 和 resume 两个调用点都只在有效版本不是 V2 时启动它。状态订阅先发当前快照，再发 Tokio watch channel 合并后的变化；若订阅建立失败，或流结束/出错前没有观察到终态，就回查一次当前状态。Completed、Errored、Shutdown、NotFound 属于终态；PendingInit、Running、Interrupted 不属于终态，所以单次 interrupt 不会触发完成通知。树级 shutdown 取消会中断等待；若最终状态是 Shutdown 且树正在关闭，也会抑制它，避免把生命周期清理当成 child 结果。其余终态按路由分支交给 parent：child 有 agent path 且状态显示为 V2 时，发送 trigger_turn=false 的 inter-agent result message；否则注入不启动 parent turn 的 SubagentNotification。V2 发送错误会被忽略，parent 不存在或 path/message 构造失败则直接结束。watcher 的 teardown guard 会随任务完成释放；任务异常退出而未标记完成时，会把 agent-tree shutdown 记为失败。见 watcher 实现、状态订阅、终态判定、tree runtime 生命周期 和 fresh/resumed spawn 调用点。这是匹配 tag 的源码行为，没有捕获在线 watcher 事件。

同一版本 tag 中，V2 的调用链是另一条：child session 发出 TurnComplete 或 TurnAborted 时，Session::send_event 会进入 maybe_notify_parent_of_terminal_turn；该方法先要求版本为 V2、来源是带 agent path 的 ThreadSpawn，再从终态事件和已记录错误构造 AgentTurnOutcome，交给 AgentControl::turn_finished。控制器随后由 completion.rs::notify_parent_of_terminal_turn 路由结果。成功完成且有 parent turn id 时会发 SubAgentActivityKind::Completed，之后按终态构造结果消息并排入 parent 通信队列，trigger_turn 为 false。错误终态使用相应的 completion 文案，部分拒绝错误有专门处理。见 Session 终态事件调用链 和 terminal outcome 路由实现。

这条 V2 结果路径还有一个边界：状态映射把普通 Interrupted 视为非 final，maybe_notify_parent_of_terminal_turn 因而不会为普通中断调用 turn_finished；它也只响应 TurnComplete / TurnAborted，所以单独的 ShutdownComplete 不会由此生成 parent 结果消息。Guardian 的 TooManyDenials 中断是特例：session 会把它映射为 Errored 并附带错误类型，再走结果路由。child 自己的终态事件仍会被发送和记录，但这与父端 completion 通知是两件事；静态源码不能据此判断桌面 UI 是否通过其他状态读取及时呈现中断。见 Session 事件过滤与 outcome 构造、状态映射 和 状态消息格式化。

Completed 活动本身不是结果消息：协议项只有 activity id、kind、child thread id 和 agent path，没有正文。控制器把它作为即时完成项发到活动接收者的 session，依次产生 ItemStarted 与 ItemCompleted；app-server v2 使用 canonical TurnItem 生命周期，旧 SubAgentActivity event 仍为 rollout/raw-event 兼容消费者转发。随后构造的完成文本才是单独的 InterAgentCommunication，发往结构性 parent。桌面端又把 child 的状态与 final response 分开读取。因此 “活动显示 Completed”“结果消息成功入队”“面板取得最终回复”分别代表三件事。来源：活动协议与项类型、活动发射、app-server 生命周期处理。

活动发射是 best-effort 且要求 activity recipient 的 session 当时可从 runtime 取到；路径解析失败或 get_thread/发事件失败只记 debug 日志，控制器仍继续向结构性 parent 投递结果通信。结果投递另有 queued/failed 指标。因此如果发起者不是结构性 parent，发起者的 Completed 活动可能缺失，而结构性 parent 仍收到结果；两条通道的送达情况需要分别判断。来源：activity recipient 与错误处理、runtime thread 查找。这是静态源码控制流，不表示本机曾发生该失败。

完成活动和结果消息也不一定发给同一个 agent。若 child turn 记录的 initiating_agent_path 与其结构性 parent path 不同，源码会尝试把 Completed activity 发给这次 follow-up 的发起者；完成结果消息则仍按 parent_thread_id 发送给结构性 parent，并保持 trigger_turn=false。trigger turn 的发起者信息来自 inter-agent 输入的 author，或 turn-start options，再写入 turn metadata。因此活动归属反映“谁请求这轮任务”，结果归属仍反映“child 属于谁”。来源：turn metadata 生成、turn input 与 完成路由。这是静态源码路径，未运行嵌套 child 实验。

这两套实现都说明：状态/活动事件与结果消息不是同一个事件，而且排入 parent 队列不等于 parent 模型已经消费并整合了答案。客户端另外有一个针对 /flora/subagent/thread/turns 的查询模块，会在有可用记录时选择 child 的最新 final answer；那属于另一条结果展示/读取路径。尽管版本号相同，公开源码 tag 与本机安装包之间仍缺少构建来源证明；以上版本分流描述的是被检查的 tag 源码，并由本机符号/字符串作静态交叉佐证。

我继续追踪 trigger_turn=false 的结果消息如何进入 parent。若 parent session 已加载，控制器把通信交给 session mailbox；消息可在当前 turn 仍接受 mailbox 输入时进入该 turn，否则会留在队列里供后续 turn 收取。若 parent 未加载，消息先保存在本地 agent runtime mailbox，session 下次加载时再转入输入队列。parent turn 真正处理队列项时，InterAgentCommunication 会转成带 author、recipient 和正文的 AgentMessage，写进会话历史与 rollout，再参与模型上下文构建。因此，子 Agent 已完成、完成活动已显示、结果消息已入队、结果已进入父会话上下文、模型实际采样并使用结果仍是不同阶段。源码能证明路由、队列到历史的转换，不证明某次在线请求确实使用了结果。具体见 control.rs、mailbox.rs、handlers.rs、input_queue.rs、hook_runtime.rs 和 protocol.rs。

再看协议表示时，完成文本的包装层容易造成误读：InterAgentCompletionMessage 实现的 contextual fragment role 是 assistant，但 V2 completion 路径只调用它的 render() 取正文，随后把这段文本放入 InterAgentCommunication。协议的 to_model_input_item() 最终生成 ResponseItem::AgentMessage，带 child author 与 parent recipient，明文内容是一个 InputText；它不是普通 ResponseItem::Message { role: "assistant" }。因此应按 agent-to-agent 消息理解它的身份，而不能仅根据格式化器上的 role() 推断父模型历史里的消息类型。record_inter_agent_communication 会先将该 AgentMessage 准备为 history item、赋 input order，再写入 session history 和 rollout，最后发送对应 raw response item 事件。静态源码能证明这个类型转换与记录次序，不证明任何具体请求实际采样或理解了该文本。来源：completion message fragment、communication protocol conversion 和 session history/rollout recording。

成功完成结果里的 last_agent_message 也不等于 UI 查询明确优先的 final_answer。源码将 assistant Message 解析成 AgentMessage；在最终化时，把正文各文本片段拼接，空白正文变成 None，非空正文成为候选 last message。这个提取没有按 phase 过滤；phase 在旁边用于判断是否延后 queue-only mailbox。随后 turn 逻辑把最近一次采样返回的候选值带进 TurnComplete，完成通知再复制它作为 payload。相比之下，桌面 UI 的独立查询明确先找 phase=final_answer，没有时才退回最近非空 agent message。因此源码里的“child completion payload”和 UI 的“优先 final answer”是两种选择规则；静态分析不能证明某次运行里最后一条消息属于什么 phase。来源：assistant item 到 turn item 的映射、turn item 最终化与文本提取、turn 结果回传 和 UI final response query。

结果正文的大小处理也不对称：format_inter_agent_completion_message 对错误状态的错误文本按 Tokens(900) 截断，常量为 1,000-token 消息目标并预留 100 tokens 给信封；成功状态则直接复制 last_agent_message，这层没有同样的截断调用。因此这里只能说错误文案在该格式化层有明确截断，而成功结果没有看到同层截断；不能据此推断完整模型上下文或其他传输层没有自己的预算/限制。见 完成消息格式化 和 结果消息结构。

7. UI 显示的是协作事件的投影

应用 JavaScript bundle 中观察到两类相关结构：

结构 能看到的字段 UI 侧用途
codex_collab_agent_tool_call tool、status、sender/receiver thread ids、prompt、agentsStates 表示 spawn、send input、resume、wait、close 等协作工具调用及其状态
codex_sub_agent_activity agentPath、agentThreadId、kind、id 表示 started、interacted、completed、interrupted 等子 Agent 活动

bundle 把活动状态映射成 waiting、working、done、failed，并分组放进 Active / Done。换言之，界面列表是控制层事件的呈现结果，不是 Agent 调度本身；UI 的 completed 也不等于上文所说的结果消息必然已被主模型消费。

7.2 后代快照如何发现和补全

继续沿 bundle import 找到 app-shared-8bd9d0399038.js 中的 SubagentTopology。getSubagentDescendantSnapshot 本身只是从 thread store 取已知后代，并附带 isComplete: false；异步 discover 才会查找和 reconcile。创建发现任务时会记录一份发现开始时的 runtime 状态，完成后用它与读取结果合并，避免发现过程中到达的活动状态被旧历史覆盖。相同 parent 的发现会复用 in-flight promise；直接子线程发现和整棵后代发现分别缓存。

  • 在支持 thread-list filters 的 host 上，发现逻辑用 thread/list 按 sourceKinds: ["subAgentThreadSpawn"]、未归档、创建时间倒序分页，且 useStateDbOnly: true。服务端版本达到 0.143.0-alpha.16 后请求 ancestorThreadId 一次取后代；旧版本逐层用 parentThreadId 查直接子线程并递归扩展。遇到重复 cursor 或查询结果早于 parent 创建时间会停止继续翻页。
  • 不支持该过滤能力的 host 会从 child transcript/history 中找 spawn id：支持 thread/items/list 的路径读取 item 历史；paginated history 则扫描 thread/turns/list 的 turn items。可识别的记录包括 subAgentActivity 的 started/agentThreadId 和 collabAgentToolCall 的 spawnAgent/receiverThreadIds。
  • 发现时把已观察到的 spawn id 与历史发现的 id 合并，对尚未纳入快照的 child 调 thread/read(includeTurns: false)。读取结果必须匹配请求的 child id 和预期 parent id；成功后递归发现该 child 的子树。补读最多两个 child 并发，单个失败或身份不匹配会把整体结果标记为不完整，而不是将 child 当作不存在。
  • 对尚未加载且使用 paginated history 的线程，会继续分页读取 turn items 来重建嵌套 spawn 拓扑；对应读取失败也会保留“不完整”状态。spawn 事件若只指向一个已在 store 中且 parent 匹配的 child，会先后台 hydrate 这个 child 再发现其子树；否则退回对 parent 做完整发现。
  • runtime item 事件流收到 collabAgentToolCall(spawnAgent) 或 subAgentActivity(started) 时会触发 discoverForSpawn。因此面板读取的 store 快照和事件驱动的后台发现是两条协作路径；静态代码只证明存在该触发器，不代表每次面板打开都会重新查询。

这揭示了列表数据的两层语义：快照是目前已知的后代集合，发现结果另有完整性标志；面板可以先展示已加载 child，同时后台补查遗漏的后代。thread/list 的过滤参数和 thread/read 都是客户端向 app-server 发出的调用观察，不能据此断言服务端如何存储 parent-child 关系、如何授权，或所有 host 均走相同路径。

同版本源码中的 app-server 与 state DB

继续沿 rust-v0.162.0-alpha.17.2 tag 检查服务端实现后，可以把上面的客户端查询和一个具体存储路径对应起来：thread/list 把 parentThreadId、ancestorThreadId 转为直接子线程/后代关系过滤，两者不能同时指定。thread store 将查询传给 state DB；后代查询通过递归 SQLite CTE 沿 thread_spawn_edges 展开，再与 thread 表连接。SubAgentThreadSpawn source kind 在 app-server 侧通过 session source 做过滤。

spawn 路径会把 parent-child 边 upsert 到本地 agent graph store；child 为 ephemeral 时跳过持久化。创建 spawn edge 的异步任务会在发送 child 首条输入前被等待，因此在这个源码快照里，后代列表依赖的关系边早于 child 首次接收任务写入。关键实现可查看 thread_processor.rs、state/src/runtime/threads.rs、thread-store/src/local/list_threads.rs 和 control/spawn.rs。

spawn edge 另有 open/closed 生命周期：open 表示 child 仍是 live 或 resumable 的图节点；显式 close_agent 会先关闭 edge 再 shutdown，而普通 shutdown_live_agent 刻意不关闭它。因此这条持久关系状态不能直接当作 UI 的 working/done/failed 状态。

这是同版本号公开源码对客户端观察的解释，不是对本机 app-server 进程的直接观测；没有签名构建元数据证明安装包一定来自该 commit，也没有从桌面 bundle 单独确认每个 host 都使用这一路径。因而它收窄了“tag 的存储/过滤语义未知”，但不把它提升为当前安装实例的运行时事实。

7.4 活动事件怎样进入桌面状态

沿着 Core 到 app-server 再到桌面 bundle 追踪后，可以把 UI 更新链路具体化。Core 的 AgentControl::emit_sub_agent_activity 为一个 TurnItem::SubAgentActivity 连续发出 ItemStarted 和 ItemCompleted。app-server v2 将这两个规范 item 事件转为 item/started 与 item/completed 通知；v2 路径会跳过旧的 EventMsg::SubAgentActivity 生命周期事件，避免把 legacy/raw-event 通道当成桌面主路径。桌面共享 bundle 收到 typed item 通知后更新 conversation turn；完成 spawnAgent 调用项或 subAgentActivity(started) 活动项后，会调用 SubagentTopology.discoverForSpawn，再去发现或刷新 child。

SubAgentActivity 的业务 kind 包括 started、interacted、interrupted、completed；V2 的 spawn、消息投递和 interrupt handler 分别发出前三种记录。每条活动记录自身都会立即走完 ItemStarted/ItemCompleted。所以协议层的 ItemCompleted 表示活动记录已结束，不表示 child Agent 已完成。

另一个容易忽略的边界是接收方：spawn、interact、interrupt 活动被写入发起工具调用的 session/turn；child 完成时，完成活动会写入可解析出的 initiating thread，找不到时退回 structural parent。child 的最终结果则单独通过 inter-agent communication 发给 structural parent。于是活动记录中“受影响的 child”和“承载记录的会话”可以不是同一个线程，尤其在嵌套协作时更要区分。这个静态链路解释了活动如何推动 UI 状态刷新，但本机没有捕获桌面端实时通知流，也没有据此证明每种 host 都走相同路由。源码依据：活动发射、spawn、interact、interrupt、完成路由、app-server 事件处理、v2 event mapping、v2 item conversion。

桌面端把这些 activity 投影为独立时间线卡片：started 显示为 active，interacted 显示为 updated 并标记为消息事件，interrupted 和 completed 显示为对应状态；名称取自 Agent path 最后一个非 root 段。这个卡片还会经过 background-subagents 开关和当前 Agent path filter。它不是 child 的权威运行状态；面板的 Active/Done 分组来自单独的 thread/topology 状态。尤其是 interrupt_agent 的返回契约明确给出“派发前的状态”，并说明 Agent 仍可接受后续消息和任务；interrupted activity 记录的是 interrupt 操作成功受理，并不证明线程已经进入终态。换句话说，activity 卡片解释“发生了什么操作”，child 状态解释“线程目前怎样”。这些映射来自安装 bundle 与匹配 tag 源码的静态证据。

8.1 子 Agent 自己是否还能继续 spawn，取决于模型能力元数据

源码把“当前会话采用 V2”与“此 turn 注册协作工具”分成两道检查。根线程通过 collab_tools_enabled 的 agent-path 条件；非根 V2 child 还要求当前 model metadata 明确标记支持 V2。于是 child 的历史/会话版本是 V2，并不自动意味着它能继续 spawn、发消息或管理下级 Agent：如果它当前选用的模型没有 V2 能力标记，这组协作工具不会注册。V1 则使用单独的下一层深度限制。

另一个容易混淆的开关是 non_code_mode_only。开启时，spawn、消息和管理工具使用 DirectModelOnly：它们进入普通模型可见工具列表，但不会进入 Code Mode 的嵌套工具集合；关闭时采用 Direct，Code Mode 可用时也允许从嵌套工具面调用。这个枚举只描述工具计划的曝光面，不足以证明本机某次对话的实际配置或模型请求内容。

在 V2 下，disable_direct_message 会同时去掉 send_message 与 followup_task，wait_agent_enabled 则单独控制 wait_agent；interrupt_agent 和 list_agents 仍在通过协作门控时注册。最终 router 还会用所需管理工具是否全部实际暴露来计算 can_manage_children。对外部 session，若关闭直接消息，router 还要求配置的消息板 post 工具可用，否则工具计划会报错；内部 session 不走这项校验。依据为匹配 tag 的 spec_plan.rs、tool_executor.rs 和 router.rs。这些是静态源码规则；本机 resolved config 和模型能力值仍未知。

模型选择列表使用的判断又不同：V2 下只排除模型目录中明确标记为 Disabled 的 preset，因此元数据缺失或标为 V1 并不会被这项过滤自动排除；但 child 自己要拿到继续协作的工具，前述运行时门控要求其当前模型明确标记 Some(V2)。所以“能在 spawn 的模型选项中选择”不等于“child 可递归 spawn 或管理下级”。这是两个源码谓词的边界，并非我观察到的本机实际故障；本机会话拿到的模型目录元数据仍未知。依据 child_config.rs、multi_agents_spec.rs 和 spec_plan.rs。

8.2 V2 的递归层级与资源限制

匹配版本源码中，agent_max_depth 被 V1 的协作工具门控及 legacy spawn/resume 路径使用；V2 的 collab_tools_enabled 没有比较 depth。V2 child 的 ThreadSpawn 来源仍逐层记录递增深度，但本次检查到的 V2 工具注册路径不把它当最大层级限制。换言之，若 child 模型明确支持 V2 且资源允许，它在源码规则上可以继续拥有协作工具；这不是说真实任务可无限递归。

V2 资源控制分开管理：max_concurrent_threads_per_session 形成 V2 effective agent-thread capacity（扣除 root），spawn 用它预留 residency slot；session scoped execution limiter 另行约束活跃 V2 child turn，创建前也会先检查 execution capacity。V2 residency spawn 不会再给 registry spawn reservation 附加第二个 max-thread 限额。因此这里可确认的是“检查到的 V2 工具门控无显式最大深度，运行中的 child 受 residency/execution 容量控制”，不能推导出历史 child 总数也被同一个数封顶。来源为 spec_plan.rs、config/mod.rs、control/spawn.rs、control/execution.rs 和 control/residency.rs。配置实际值和运行时容量未观测。

源码默认的 max_concurrent_threads_per_session 是 4，扣掉 root 后 effective child capacity 为 3。显式 features.multi_agent_v2.max_concurrent_threads_per_session 优先于旧的 agents.max_concurrent_threads_per_session；后者会先加回 root，再进入统一容量计算。这些是默认值与解析优先级，不代表我已读取本机当前对话的 resolved config。来源仍是匹配 tag 的 config/mod.rs。

8.4 关停请求和清理责任是两步

0.162.1 还公开了 ThreadManager::request_agent_tree_shutdown(thread_id)。它只能从已加载 thread 取得该 session 的 local runtime；成功后立即关闭该 tree 的新 membership admission、取消共享 cancellation token、关闭 mailbox，并返回 AgentTreeShutdown。调用方再调用 wait() 或 wait_detailed()，等待关停 fence 之前已登记的工作排空。admit_start 在创建 membership 前后各检查一次 fence，因此与关停同时发生的新启动会被纳入等待或以 RuntimeShutdown 拒绝。

membership 覆盖的不只是 child spawn：源码将 session startup 与 session loop、fresh spawn、agent resume、V2 child reload、legacy completion watcher，以及 resident eviction 等工作登记进同一棵 tree。取消 startup 时，SessionStartupGuard 会先停止 session I/O 或清理已建 session，再 discard 尚未提交的 persistence；session loop 则持有单独 teardown guard。未正常完成的 guard 会成为 GuardAbandoned 报告项。报告最多保留 64 条失败，额外部分通过计数表示；wait() 只给通用错误，wait_detailed() 才返回结构化明细。

这个 handle 的语义是“封住并等待当前 runtime”，不是代替调用方完成所有卸载：API 文档明确把 registry removal 与调用方负责的 persistence handoff 留给调用方；跨这个 runtime 的同一 thread ID 顶层 load/resume 也必须由调用方另行串行化。结合 subagent 创建时把 parent 的同一个 LocalAgentRuntime 传给 child，可推得：若调用方把某个 child thread ID 交给此 API，拿到的仍是父、该 child、同 runtime siblings 共用的关停状态；它不是只关 child 子树的句柄。它也不等于 close_agent 的图操作：后者先尝试把目标 spawn edge 标成 closed，再遍历目标和 live descendants，逐个执行 agent shutdown。公开 app-server 的 idle-thread unload 又是第三种路径：对单个 CodexThread 调 shutdown_and_wait()，成功后以 thread identity 条件从 manager 移除。当前 rust-v0.162.1 仓库内没有 request_agent_tree_shutdown 的生产调用点；因此只能确认 host/SDK 可调用该 runtime 级接口，不能证明 ChatGPT 桌面用它关闭 subagent tree。来源：shutdown API、membership 与 admission fence、child 复用 parent runtime、startup cleanup、close_agent tree traversal 和 app-server per-thread idle unload。以上是静态源码结论；没有调用该 API 或制造关停竞态。

8.6 主对话停止会由桌面客户端继续清理活跃后代

继续沿共享 app-shared-8bd9d0399038.js 的 interruptConversation 追踪后，发现上一节的边界需要补全：子 Agent 面板本身没有停止按钮，但桌面会话管理器在中断一个 conversation 后，会在符合条件时调用 interruptSubagentDescendants。当来源是 user-stop，它把后代清理排到 scheduler 后台；其他来源会等待后代清理结束。例外包括递归清理本身和本地 stream role 为 follower 的会话。耐久线程的 thread/stop 路径也在成功后执行后代中断：用户发起时后台调度，其它调用方同步等待。

后代清理不是给根线程发一个“shutdown whole tree”请求。客户端先用当前 descendant snapshot 对已知的 active child 调用自身的 interruptConversation(..., "descendant-cleanup")，并记录已处理 ID；随后再跑一次 descendant discovery，对仍标记 active 且未处理的 child，先尝试本地 conversation 中断。若 child 不在本地 store 或该调用未能处理，则读取它最近一页 turn；只有最新 turn 状态为 inProgress 时，才单独发 turn/interrupt，参数含该 child 的 thread ID 与 turn ID。对后代列表使用 Promise.all 并发处理。递归调用的 descendant-cleanup 来源会阻止再次触发一轮嵌套级联，因此一次根级遍历覆盖整棵已发现子树而不会无限递归。

服务端 turn/interrupt handler 则只加载请求里指定的 thread，校验该 thread 的 active turn ID，然后向该 thread 提交一个 Op::Interrupt；它本身没有树遍历。因而“停止 parent 会连带尝试中断 descendants”是桌面客户端编排出来的行为，不是 app-server 对单个 turn/interrupt 的隐式传播。此处“尝试”很重要：清理有发现失败、子请求失败和后台异步窗口；用户停止可能先返回而后代仍在清理，日志会记录失败。这个源码路径是对内嵌 app.asar 的静态恢复，尚未实际点击停止，也没有远端 host 的运行时 trace。证据文件为 app-shared-8bd9d0399038.js（SHA-256 607ad0866dd25ed3764711b4467a9b60708353a599485b5249ff4cbe0e870245）；服务端对照为匹配版本 turn_interrupt_inner。

8.7 停止级联依赖 best-effort 的后代拓扑发现

继续追 subagentTopology.discover 后，发现级联会先拿 thread store 中已知的 descendants 快照，再请求重新发现。当前桌面 host 的路径会用 thread/list 的 spawn-source 过滤和 ancestor/parent 关系分页（每页最多 200 条）；在不支持该过滤的 host 上，则结合内存里观察到的 spawn 活动，以及从持久化 history 提取的 subAgentActivity.started / spawnAgent receiver IDs，逐层读取并校验 child thread。cloud history 通过 thread/items/list 分页，paginated history 通过 thread/turns/list 读取活动记录；子树读取并发上限为 2，并检查 child 的 thread 身份与 parent 关系。

发现器会用 isComplete 标记 cursor 异常、历史读取失败或 child 缺失等不完整情况。但停止 helper 只读取 descendantThreads，没有检查 isComplete；因此部分发现仍会继续中断已经找到的 active child，同时遗漏未发现后代的可能性保留。这让 8.6 节的“best-effort”不只是中断请求可能失败，也包括停止前的树枚举本身可能不完整。证据仍限于本机 bundle 的静态代码，没有注入发现错误或在运行中的桌面会话验证覆盖率。

8.8 本地中断会校验 turn 身份，并清理关联执行

本地 owner 执行 interruptConversationSelf 时，会先检查当前最新的 in-progress turn；若调用方提供了 expectedTurnId，它必须仍与该活跃 turn 相同，否则返回空结果，避免误中断已经变化的 turn。确认后才发单线程 turn/interrupt 并将本地 turn 标为 interrupted，同时安排清理该 turn 的 Node REPL 执行。user-stop 会把这些执行清理作为后台工作启动；如果没有活跃 turn，则清理后台 terminal 后返回空结果。后代级联把空结果视为“未处理”，因此会再查最新持久 turn，必要时按 thread ID 与 turn ID 发直接中断。该身份校验和清理行为是客户端 bundle 静态证据，没有在线竞态实验。

多窗口的 stream follower 不直接在自己的窗口中断 owner 正在运行的 turn：它通过 desktop IPC 把 thread-follower-interrupt-turn 请求转给 owner，由 owner 的 manager 执行中断及其后代级联，所以 follower 自己的 finally 不再重复清理。若 owner 超时、不可用或协议版本不匹配，follower 会清除失效的 stream ownership、把会话标为 needs-resume，再退回本地中断；ownership 清除后不再是 follower，因此同一外层流程仍会尝试后代清理。以上是 bundle 中的路由控制流推导，未模拟多窗口断连竞态。

8.9 归档前的运行时停止与普通中断不是同一个入口

继续追 bundle 里的 stopThread 调用点后发现，CHn 虽然把它包装成 user stop，但当前资源中唯一找到的实际调用点位于 beforeArchiveConversation 的受限运行时分支。归档一个符合 subagent 来源条件的线程时，durable 模式会走后代中断；非 durable 模式则先请求暂停受限 runtime，只有暂停成功且允许中断活动 turn 时，才调用 stopThread 并通过回调记录被中断的 turn。它属于归档前清理路径，不能据此称为子 Agent 面板里的停止按钮。

renderer 的 use-resume-conversation-if-needed effect 会观察两个派生值：child 所属的 host ID，以及它的 subagentParentThreadId。后者来自 conversation 的 parentThreadId 或 source 中的 parent ID，并保存在 loaded/archived thread title state；host selector 则结合 conversation 的 manager/summary host 解析，并带有 host-list fallback。两个值都可用时，effect 才向该 host 发送 subagent-thread-full-fidelity-changed(enabled: true)，并在清理时发送 enabled: false。继续追 app-shared 的 store 实现后，可以确认 watch 由 effect atom 支撑：订阅会挂载 effect 并安排一次初始检查，之后被读取的状态变化会让它再次运行。因此新挂载或重建的 watcher 能用已有的 parent/host 关系重发 enable。但 React effect 的依赖仍只有 child conversation ID 与 store 对象，Electron connection 实例/registry 不在依赖中；单独替换 connection 不会重挂这个 watcher。已检查的新连接注册路径会广播 connection state，但没有更新 conversation 的 parent relation。其他路径是否会改变 watcher 的两个值，或另行回填 child ID，仍未知。

证据位置：main-CqEoQDOU.js 中 host registry replacement 约偏移 3353690；src-BJv5Mk7n.js（SHA-256 72e2b366d574206f76fc079c79b64c31ce378970a797475ded8709908d338f08）中 subagentThreadIds 初始化约 1189433、dispose 清理约 1219032、唯一 thread/started 添加点约 1252400、过滤查询约 1252969；UR 检查 source.subAgent.thread_spawn.parent_thread_id 约 1154174；registerWebviewWindow 约 1196846、surface setter 约 1198170，IPC receiver 约 2104239。renderer 模块 use-resume-conversation-if-needed-cd15159177f0.js SHA-256 为 2299468dc1ce305855a9fc93cd9d11c2956b60023563d8360483ee2d44a818f4，sender effect 约偏移 5325。共享 store bundle app-shared-8bd9d0399038.js SHA-256 为 607ad0866dd25ed3764711b4467a9b60708353a599485b5249ff4cbe0e870245：q6t 从 conversation/source 推导 parent relation 约在偏移 2620356，titleState 为 loaded/archived 状态保留该关系约在 2632928；host selector F3 约 5689682，parent selector Wsi 约 5694550。watch 实现中 Ost 通过 store.sub 挂载 effect atom 约 1679810，wst effect/mount hook 约 1678048，Nk 的 watch wrapper 约 1684368，predicate watcher Xst 约 1684904。偏移只对对应文件 hash 有效。只检查静态 bundle，没有实际替换 remote connection。

8.28 本机 app-server 与 remote host 使用不同的 connection 创建入口

继续追 Electron 主进程 bundle 的 connection owner，发现前面的 createAndRegisterRemoteConnection 结论需要限定为 remote host。main-CqEoQDOU.js（SHA-256 09d19386e1f23cf4ccbc950fc40d85a1e8a064a08be588b2a4be6a89f6ada9e6）中，host manager 构造时直接调用 createAppServerConnection(localHostId) 创建本机 app-server connection（约偏移 3302289），随后把这个对象加入 appServerConnectionRegistry（约 3303344）。如果配置了 durable thread host，则由另一段构造逻辑单独创建和注册（约 3306487）。createAndRegisterRemoteConnection（约 3353690）由 remote connection handler 使用，因此它的 dispose/replace 行为不能直接套到本机 connection 上。

2026-10-14 的一次脱敏进程快照同时看到桌面主进程下有本机 embedded Codex CLI app-server，以及另一个以 exec-server --remote 连接云端 environments endpoint 的进程。进程参数中的环境/session 标识不记录。这个快照证明当时两种进程并存；它不说明具体 subagent thread 或通知由哪个 host 承载，也不代表所有会话的固定拓扑。

继续沿 manager 生命周期追踪，在同一 main-CqEoQDOU.js 中只找到一个 new hXe(...) 构造调用点（约偏移 3358549），位于主进程启动流程。manager 的 dispose()（约偏移 3344603）会取得 registry 中全部 host ID，对每个已注册连接调用 dispose()，随后移除 connection 和 execution-host 注册；本机 connection 已在该 registry 注册，因此若退出时仍在其中，也会进入这段清理循环。不过循环没有逐个等待 connection 的 dispose() 完成。

正常 will-quit 路径（约偏移 3384353）会先阻止立即退出、刷新状态并处理其他服务，再通过 flushAndDisposeContext 调用 manager 清理。这个回调会等待 manager 和另一个 service manager 的 dispose()，并在 finally 刷新 tracing；外层等待最多 5 秒，超时后退出流程仍可继续。更新安装的 immediate-exit 路径也复用这个回调和 5 秒等待。因此静态代码证明的是“退出流程会启动 manager/connection 清理”，不能据此断言异步 connection 清理一定在进程退出前全部完成。

综合来看，同一 connection 实例的普通 transport 重连保留 subagentThreadIds；remote host 显式替换会创建新实例，bundle 中未发现直接回填旧 child ID 的入口；本机 connection 有独立的创建/注册路径，并会在 manager 退出清理中被调用 dispose()。主 bundle 中单一 manager 构造点支持应用重新启动时再次创建 manager，但 child 线程是否跨应用退出继续运行、其 parent/host 关系如何重新发现、新 connection 如何重新收到 child 通知，仍没有证据。以上是静态 bundle 检查和一次脱敏进程快照；没有重启、断开连接或采集通知。

新增退出生命周期证据位于同一 main-CqEoQDOU.js：manager dispose() 约偏移 3344603，唯一 new hXe(...) 调用点约 3358549，normal will-quit handler 约 3384353，启动流程传入 flushAndDisposeContext 约 3812129；update-install immediate-exit 调用点约 3374211 与 3814882。manager 清理循环会调用所有已注册 connection 的 dispose() 并移除 registry entry，但没有 await 每个 connection；退出封装最多等待 5 秒。只证明清理会被启动，不能证明每个异步 dispose 在进程退出前结束。完整边界和复核方法见公开证据记录。

8.29 thread/list 恢复会话，不会直接登记 connection 的 child 过滤集合

继续沿 connection bundle 核对列表与通知注册的关系。src-BJv5Mk7n.js（SHA-256 72e2b366d574206f76fc079c79b64c31ce378970a797475ded8709908d338f08）里的 listThreads() 只是 thread/list 请求包装（约 byte offset 1205725）；conversation list helper 则通过 sendRequest 发 thread/list 并消费返回 rows（约 438282）。两条路径都没有写入 connection-local 的 subagentThreadIds。全 bundle 唯一直接添加 child ID 的位置仍是满足 subAgent source 条件的 thread/started 路由（约 1256453）。因此列表与 history hydration 可以恢复 conversation 数据，但不能据此推断通知过滤集合也被回填。

还发现一条特殊的 prewarm 通知路径。对安装包内所有 JS 做引用搜索后，只找到一个 prewarmThreadStart() 调用方：conversation prewarm manager，它用新会话参数预先准备普通 thread/start（src-BJv5Mk7n.js 约 byte offset 900036–900508；main-CqEoQDOU.js 请求适配器约 733031），没有找到 subagent 创建路径调用它。若某请求标记了 prewarmThread，成功响应会把返回 thread 放入 tracker（约 1259615）。其原始 thread/started 到达时，suppressThreadStarted() 会让通用路由提前返回（约 1255164），早于 child ID 登记条件。稍后收到 turn/start 时，客户端会发布合成的 thread/started；该回调只调用内部 notification handlers 并向窗口广播（约 1197380），没有再进入 routeIncomingMessage，所以合成通知本身不会写入 subagentThreadIds。

这是条件路径分析。当前客户端调用图指向普通 conversation 预热，没有证据表明 subagent 会进入该流程；不能排除服务端或未包含在此 bundle 的其它调用方。后续是否另有生命周期事件登记 child 也仍未知。仅静态检查，没有发起请求、重连或采集通知。

8.31 V2 子线程会被按需卸载，但中断状态不一定能重载

我把本机匹配版本与公开源码快照对齐后，发现一项明确的版本差异。本机桌面内嵌 CLI 是 0.162.0-alpha.17.2（源码参照 commit 740e5af33c71225640e0c1c1555c514c2c93ab74）；公开 tag rust-v0.162.0-alpha.20（commit 15c477d788a575de432f661def200ae7bc4a835e）和 rust-v0.163.0-alpha.9（commit 4753ce3d19df9ffa58353736c4ffde49ed071589）都包含 V2 residency 驱逐和加载路径。完整 Git 历史显示这两个 tag 的关系不是线性升级：共同祖先为 c333d755d44d4eb764cffd2bd862d86d790e91e6，git rev-list --left-right --count alpha.20...alpha.9 为 1 166。因此下面是两个公开快照的对照；只能把该路径的出现时间界定为“最迟 alpha.20 已存在”，不能据此认定具体引入提交或本机桌面运行了这些实现。

容量达到上限时，resident 队列从最久未触达的候选开始尝试卸载。它跳过被保护的线程，并要求候选仍是同一个已登记 runtime，且处于 Completed、Errored 或 Interrupted 状态，没有活动 turn、持久睡眠或待处理的触发式邮件。卸载时会等待线程退出，阻止并发投递；把尚未读取的 queue-only 邮件放回 mailbox，并将 environment selections 暂存在本地 agent registry，最后移除 runtime 和 residency 记录。找不到可卸载对象时会返回 residency capacity 错误。源码：alpha.20 residency。

重载不是所有被卸载 child 的保证。恢复路径会检查 agent registry 元数据、持久化 thread/history、V2 标记与父子来源一致性；如果由父线程发起，还要求父线程仍在同一个 registry 中登记、正在运行且属于 V2。随后会重建配置，并重新校验父线程派生的执行策略和环境权限，再恢复原 thread ID。更关键的是，alpha.20 的测试明确覆盖了一个反例：Interrupted child 可以通过卸载资格检查，但卸载后调用重载仍得到 ThreadNotFound。所以运行时驱逐与可恢复性是两件事，不能把它概括成“子线程都能休眠后恢复”。源码：alpha.20 reload、interrupted child 测试。

这部分来自后续上游源码及其测试，不是对本机 .17.2 的动态观测；也没有证明 agent registry 能跨 Codex 进程重启保留。完整版本差异和边界见公开证据记录。

8.32 alpha.9 app-server 快照还有一条由“无订阅且空闲”触发的 child 卸载路径

继续对照 .162.0-alpha.20 与 .163.0-alpha.9 两个源码快照后，我确认容量驱逐之外还有一条 app-server 生命周期路径。.163.0-alpha.9 的 listener 会识别同时满足 V2 和 SessionSource::SubAgent 的 child；当它没有订阅客户端、且线程状态持续 inactive 达到配置的 thread_unload_delay，便登记 pending-unload guard，再委托 core 的 try_evict_v2_thread。成功卸载后清理 listener/watch 状态并发出 thread/closed。普通非 V2 线程仍走 app-server 原有的 unload_thread_without_subscribers。对照 .162.0-alpha.20，该快照的 listener 还没有这个 V2 专用分支。

因此需要分开看两种触发原因：core residency 达到容量时会尝试驱逐；app-server 也会因 child 长时间没有订阅者且处于 inactive 状态而卸载。它们最后调用共享的 core 卸载实现，但入口和调度条件不同。源码：alpha.9 lifecycle listener、alpha.20 对照。

同一版本新增的 disconnected_v2_child_lifecycle 测试覆盖断连期间创建 child：没有已初始化客户端时，listener 仍能为已加载、非 ephemeral 的 V2 child 建立后台生命周期监听；测试确认仍在运行的 child 不会过早收到关闭，并在 idle deadline 后通过父线程实际调用 followup_task，检查 child 下一次模型输入仍包含它之前的 assistant 回复。测试还检查断连的 parent 和 child runtime 最终会释放。这些是源码中的测试断言，我没有在本机运行该测试或触发真实断连。源码：alpha.9 lifecycle 测试。

这表明 alpha.9 公开快照把 app-server idle 生命周期接到了 V2 的安全卸载与恢复机制；它仍不能证明本机 .17.2 桌面构建使用这份实现，或本机真实 child 经历过该路径。完整版本差异见公开证据记录。

8.33 消息投递会 pin resident，spawn 取消清理延伸到最终 await

在 alpha.9 快照里，向已加载的 V2 子线程发送消息前会取得 residency read pin；pin 会核对 thread runtime 仍是 registry 中的同一个实例，并更新 LRU。这样 eviction 不能在投递期间移除该 runtime。冷恢复的 child 会在发送前按需加载；本地刚被 eviction 的 child 则有区别：QueueOnly 可不加载 runtime、直接把消息排入持久化 mailbox，TriggerTurn 会先尝试加载，再提交 follow-up。

所以 delivery receipt 代表控制层接受了投递，不证明模型已读取或执行消息。这里也区分了冷恢复和本地 eviction 的邮件处理策略。源码：alpha.9 send path、residency pin。

spawn 方面，child 首条输入通过 admission 后，控制器仍先 await 最终 status 和 config 读取；这些步骤完成后才 commit registry/residency 预留并 disarm PendingSpawn，紧接着通知 thread 已创建。因此取消发生在这两个最终读取期间时，临时 guard 仍负责清理；commit/disarm 之后的 tool-result 发布则在该 guard 边界之外。这是源码规定的所有权顺序，不是我做过取消故障注入后的运行时观察。源码：alpha.9 spawn path。

8.34 host 消息的 sender context 有来源校验，child 设置区分“省略”和“空值”

alpha.9 的 turn-input admission 只识别特定 host message-delivery 工具产生的独立 function-call output，再尝试为被投递的消息补充 sender context。投递结果里的 source thread ID 只用于定位 sender，不作为消息内容的授权证明。sender runtime 未加载时，代码会向 host thread store 请求最新 model context，最多等待 5 秒；检查返回 thread ID 和 session metadata 后，从历史中重建最多三组最新的本地 user/assistant 交流。tool bodies、继承来的历史和 verified answer 不会作为 sender 对话复制；不完整的 user message 也不会当作完整文本传入。授权失败、读失败或超时会退化为不附加这段上下文，而不是无限等待。

这解释了为什么被委托任务有时能带上最近的真实对话作为上下文，同时不能把工具返回体伪装成用户原话。来源：turn-input admission、sender-context capture。

spawn 时，parent 优先从 subagent session source 解析，缺少时才使用显式 parent option；这个选择发生在版本判定、execution-capacity 检查和设置继承之前。disabled_plugin_ids 也保留了输入差别：调用方省略时沿用当前 parent 的设置，明确传入空数组则表示 child 这一轮选择不禁用任何 plugin。来源：parent resolution、plugin inheritance。这些都是 alpha.9 源码规定的行为，不代表本机 .17.2 的动态观测。

8.35 spawn_agent 从工具参数进入 child 配置和首轮输入

与前文匹配 .162 源码时确认的参数行为相同，alpha.9 的 V2 schema 仍要求 task_name 与 message，并描述 fork_turns 仅支持 all / none；agent_type、model、reasoning_effort 则按构造选项决定是否暴露。这个独立分支快照的 handler 还明确使用 deny_unknown_fields，并把被解析到的 fork_context 作为不支持参数返回错误。它没有把 schema 限制扩展为枚举校验：缺省/空白仍按 all，旧正整数仍映射到完整历史 fork，不会按数字截取轮数。来源：V2 tool schema、参数定义、handler 与结果、参数解析。这是跨 branched tags 的静态源码核对，不代表线性版本演进。

handler 根据工具调用来源转换初始消息，再进入共享的 thread_spawn::spawn。这一层拒绝空白消息，准备 V2 child 配置，并将用户提供的 task_name 接到父 agent path 后形成规范路径。ThreadSpawn session source 同时记录 parent thread ID、递增后的 depth、规范路径和 role。child 配置以正在执行的 turn 与捕获的 step settings 为依据：刷新实际 model/provider/reasoning 与 base instructions 来源，再应用请求或配置默认的 model、reasoning、role 规则，并复制当前 turn 的 approval policy、reviewer、cwd 和 permission profile。显式 model 与 reasoning effort 会经过可用性/支持级别校验。来源：共享 spawn、配置准备、运行时与共享配置、model override 校验。

是否继承历史与 child 是否立即开始工作是两件事：无论 fork_turns 选 fresh 还是 full-history，首条 AgentInput::Message 都使用 TriggerTurn。full-history 分支还会校验 spawn call/source，并先 flush parent rollout，再读取可 fork 的历史快照；它不是简单复制一个内存列表。controller 返回已接纳的 child 后，handler 才发出带真实 child thread ID 与规范路径的 Started activity。回给模型的工具结果则是 task path，可按设置附带 nickname；它不把内部 thread ID 当作 task name 返回。来源：首条输入与 spawn options、fork history 准备、activity 与工具结果。

这条调用链来自公开 rust-v0.163.0-alpha.9 源码静态分析。它说明该快照如何把参数、父 turn 配置和首条消息交给 child；不能据此断言本机安装包就是此 commit，也不能断言某次模型调用实际选择了哪些可选参数。

8.36 首条消息接纳、turn task 启动和模型推理是三个时点

alpha.9 的 spawn 顺序还能再分细一点。controller 创建并登记 child runtime 后，才提交首条 TriggerTurn communication。已加载的 child 通过有序的 Op::InterAgentCommunication 进入 session handler；handler 先把消息放入 mailbox，再让共享 pending-work scheduler 决定是否启动 turn。child 空闲时，scheduler 会取出 mailbox 输入、构造 turn context 并调用 start_task。后者记录 turn 已开始、登记 active task，再用 tokio::spawn 启动异步 task future。来源：communication submission、mailbox handler、pending-work scheduler、task registration。

因此，空闲 child 的首轮 turn task 会在 spawn 完成前被登记并交给 Tokio 执行；spawn 随后才读取 status/config、提交 registry/residency reservation、解除临时清理责任并通知客户端。这里能证明“初始输入已接纳”和“turn task 已提交运行”，不能证明模型请求已在 spawn_agent 返回前发出，更不能证明模型已经读完任务或完成工作。若 child 当时不能启动新 turn，mailbox 接纳也不等同于立即推理。来源：spawn admission 与 client notification。这是 alpha.9 的源码时序；没有在本机触发 live delegation、延迟推理或取消故障注入。

8.37 委托消息先成为 child 的 AgentMessage 历史，再进入 sampling prompt

RegularTask 消费 mailbox 中的 TurnInput::InterAgentCommunication 时，输入记录器把它转换为 ResponseItem::AgentMessage，写入 conversation history 与 rollout；恢复历史时也用同一个转换函数重建该消息。明文消息以文本内容和 author/recipient 字段进入 AgentMessage。加密消息则把 ciphertext 保留在独立字段，并带有模型可见的 NEW_TASK/MESSAGE 类型、task name、sender 和 payload 边界提示。来源：输入记录、通信到 AgentMessage 的转换、rollout 重建。

首轮普通采样前，run_turn 会先处理可能的 pre-sampling compaction、MCP/plugin/context 准备和 turn-start hooks，再记录输入；随后从完整 conversation history 构造 sampling request 输入、调用 build_prompt，最后进入 ModelClientSession::stream。若采样前 compaction 出错，源码也会先保留/记录 pending input 再退出。因此“task 已启动”与“provider client 已发出采样请求”之间还隔着这些准备步骤；即使走到 .stream(...)，静态代码也不能证明远端服务已收到请求或模型已生成 token。来源：turn 前置处理、输入记录与 turn-start hooks、历史构造 request、provider stream 调用。这里分析的是 alpha.9 core path，没有捕获真实 provider 请求，也不推断远端模型如何解释 AgentMessage。

8.38 child 正在采样时收到协作消息，可能在 item 边界触发 follow-up

alpha.9 的 response loop 并不是每收到一条新 mailbox 消息就立即取消当前模型请求。它在一个输出 item 完成后才检查：assistant Message 的 phase 为 commentary 或 partial_answer，或者当前 item 是 Reasoning，才属于可触发 mailbox preemption 的边界；AgentMessage、工具调用和工具输出不在这个检查集合里。若此时已有 mailbox 消息且 defer_mailbox_preemption 没启用，当前 sampling request 会以 needs_follow_up 结束，让后续 request 处理排队消息。该检查发生在 item 边界，不是 token 边界。来源：response loop。

同一 tag 的 feature spec 将 defer_mailbox_preemption 标为默认关闭。对应的场景测试夹具把流式响应暂停在 reasoning、commentary 或 partial-answer item 后，排入两条 trigger_turn=false 的 child 消息，再继续返回 update_plan 工具调用。断言区分两种策略：未启用 defer 时记录 mailbox-preemption；启用时保留当前 response，让工具结果和两条 agent 消息一起进入下一次模型请求。两种配置都预期两次模型请求。这里引用的是源码和测试夹具，不代表我执行了测试或在真实 child 上观察到该行为；本机桌面会话的 feature 配置仍未知。来源：feature spec、场景测试夹具。

外层 run_turn 进一步说明 follow-up 如何进入下一次采样：当 sampling 返回 needs_follow_up，它先让 input queue 把 mailbox 消息接纳到当前 turn；完成当前采样与工具处理后，再检查 pending input 并决定是否继续循环。因此可以从源码闭合 alpha.9 内部“item 边界命中 → 当前 sampling 收尾 → mailbox 接纳 → 下一 sampling step”的控制流。它仍是源码路径，不是本机桌面运行观测。来源：外层 turn loop。

8.39 本机 V2 turn_finished 入口与装箱 future

继续核对本机嵌入式 CLI 的 V2 终态回传入口。Mach-O 符号表含有 AgentControl for LocalAgentControl::turn_finished 具名 arm64 符号，地址为 0x1049ddce0；LC_FUNCTION_STARTS 将其精确边界限定为 0x1049ddce0..0x1049ddda0，共 0xc0 字节。对这段范围单独反汇编，可见它分配一个 8232 字节对象，并返回对象指针及常量数据指针。

这与同版本公开源码 api.rs 的 turn_finished 返回 Box::pin(self.notify_parent_of_terminal_turn(outcome, trace)) 的形态相符；二进制里还存在三处 notify_parent_of_terminal_turn closure callsite 元数据。这些是本机静态二进制观察与同版本源码的对应证据，不是运行时执行证据。

尚未逐指令确认这个匿名异步 future 的 poll 函数、内部结果分支，或上游 session 终态事件调用者。因此目前可以说本机二进制含有与源码相符的具名入口和装箱 future 构造，不能据此声称完整 V2 终态到父线程的机器码链已经还原，也不能证明桌面会话实际执行过它。

8.40 从返回的 vtable 定位 V2 completion future poll

继续从 turn_finished 返回的 fat pointer 追进异步对象。入口在 0x1049ddd58 将常量地址 0x10dffdd48 放入返回寄存器 x1，与堆对象指针 x0 一起返回。该地址处的 vtable 数据依次解码为 drop 函数 0x104cc794c、对象大小 0x2028、对齐 8，以及 Future::poll 方法指针 0x1049d1a70。函数起始表将 poll 函数边界限定为 0x1049d1a70..0x1049d406c，共 0x25fc 字节。

这个精确范围的反汇编包含 async 状态分派。按 arm64 BL 指令解码 __TEXT,__text 后，定位到 poll 内两条 formatter 调用：0x1049d2df0 直接调用 format_inter_agent_completion_message，0x1049d33c4 直接调用 format_guardian_interruption_message；定点 llvm-objdump 与函数符号表确认了指令地址和目标地址（分别为 0x10587d474、0x10587d248）。completion formatter 在二进制中的另一条直接引用 0x104dd4648 位于 poll 范围之外，不计入这条链。同版本源码 notify_parent_of_terminal_turn 中的两个消息构造分支与这两条直接调用相符。

继续看 Guardian 调用前的分支：状态机从 [x19 + 0x1f8] 读取 64 位值并与 4 比较，再从 [x19 + 0x1d0] 读取一个字节并与 9 比较；这条路径还检查 +0x228、+0x1e0 处的可选指针值。相邻路径会进入普通 completion formatter。同版本源码把 Guardian formatter 限定在 (AgentStatus::Errored(_), Some(CodexErrorInfo::TooManyDenials))，其他状态走普通 formatter。因此机器码控制流与源码的特例分支高度吻合；但我还没有独立解码 future 捕获字段布局，不能把偏移或比较常量直接断言成某个 Rust enum 字段/判别值。源码 enum 的声明顺序不作为机器码布局证明。到这里，turn_finished 的 poll 入口、异步状态分派、两种 formatter 调用及 Guardian 特例的控制流关联都有静态证据；具体桌面会话是否执行过它仍未知。见源码分支和协议状态声明。

仍未逐状态把机器码映射回源码每个分支，也未隔离 Session::maybe_notify_parent_of_terminal_turn 到本机 turn_finished 的上游机器码调用边。以上只证明安装二进制包含这些结构，不证明桌面会话执行过该路径。

8.41 用 AgentControl 方法表交叉核对 turn_finished 槽位

继续检查本机 Mach-O 中 AgentControl for LocalAgentControl 的方法指针布局。两个数据区都呈现 Rust trait-object vtable 的标准头部：drop 函数指针、对象大小 0x70、对齐 8，后面接 trait 方法入口。按同版本 AgentControl trait 声明顺序，turn_finished 前有 13 个方法；因此它应处于 vtable 方法索引 13、距表首 0x80 字节的位置。两张表在该槽位都指向具名入口 0x1049ddce0，相邻槽位也分别对应 record_usage、service_tier、propagate_config_update 等实现。这与符号表中的 AgentControl for LocalAgentControl::turn_finished 名称形成独立交叉验证。

这确认了 trait 方法表的解释和 turn_finished 槽位偏移。后续 ARM64 指令扫描找到了表首的 PC-relative 地址构造引用（见 §8.42）；此前“没有找到直接引用”仅指没有普通原始指针副本。session 终态事件通过 trait 对象间接调用 +0x80 槽位的机器码位置仍未隔离。第三个原始指针命中位于 callsite 元数据交错区，不按第三张 vtable 计数。因此这仍不是完整调用边或运行时执行证明。分析对象是本机 arm64 CLI 二进制，来源身份和桌面会话是否走过该路径仍受前文所述限制。

8.42 从 ARM64 地址构造追踪 AgentControl 方法表引用

虽然二进制中找不到两张 AgentControl 方法表表首的普通原始指针副本，ARM64 代码会通过 ADRP 加 ADD 生成这些地址。对已解码的两张表分别找到以下指令位置：表 A 0x10dffdb58 在 0x1049d8940、0x104ae8a58、0x104ae9060 被构造；表 B 0x10e04ad78 在 0x1059a63f0、0x1059a6b34 被构造。0x1049d8940 随后把表 A 写入 watcher 相关异步状态；另外两条表 A 引用位于 Session::with_window_and_fork_metadata，表 B 的引用则位于 Session::rollout_reconstruction::reconstructed_window_from_compaction 对应的异步区域。这把此前仅从数据布局识别的方法表与 Session/watcher 的状态构造关联起来。

在 0x104ae8a58，指令先从表 A 的 +0x18 读取方法指针，再间接调用。匹配版本 AgentControl trait 中第一个方法是 identity，所以这个调用点证明 Session 使用该 trait object 调用 identity，并非终态回调。turn_finished 在 +0x80；当前新找到的表引用还没有闭合到这个槽位的 Session 调用点。扫描过程中，若把任意 [object + 0x80] 读取误作 [vtable + 0x80]，会把普通对象字段和其他 trait 的 drop 调用误报为候选，因此后续只接受已追踪 vtable 指针上的槽位读取，并核实其后的间接分支。所有结果仍是本机二进制静态观察，未捕获运行时终态事件。

8.43 复核一个 +0x80 间接调用候选

对另一个候选点 0x105947854 做了精确 LLDB 反汇编，并用 Mach-O LC_FUNCTION_STARTS 确认其边界属于 LLDB 命名为匿名函数的代码块 0x105944318..0x10594f06c。符号表把这段代码关联到 codex_core::session::rollout_reconstruction::reconstructed_window_from_compaction（符号入口 0x10592e364；候选函数入口距其 +0x15fb4）；早段还带有 codex_core::session::turn::try_run_sampling_request 的源码调用点元数据。候选点处，代码从 [x19 + 0x1620] 指向的对象偏移 +0x8d0/+0x8d8 读取一对指针，再从第二个指针的 +0x80 取函数地址并间接调用。

这补齐了候选指令的函数边界和寄存器/字段数据流，也把它放回 rollout reconstruction 代码区；没有证据显示该 fat pointer 属于 AgentControl，更没有证据把它连到 session 终态事件。因此这个点不再作为 turn_finished 调用候选。不能只因为 AgentControl::turn_finished 在该 trait 的 vtable +0x80，就把所有 +0x80 间接调用归给它。上游 session 终态处理到 turn_finished 的机器码调用边仍未定位。静态分析，没有运行时终态事件。

8.44 排除 completion future 内部的 tracing callsite 引用

继续核对 turn_finished poll 中指向 notify_parent_of_terminal_turn 的数据引用。nm 将 0x10e36b5d8、0x10e36b5f0、0x10e36b608 标为该方法内部嵌套 closure 的 callsite 元数据。poll 范围内的引用点 0x1049d1ea8、0x1049d1ff4、0x1049d24d8、0x1049d3148、0x1049d37fc 经 LLDB 定点反汇编后，分别进入 tracing 的 __is_enabled 检查或 callsite 注册逻辑；附近的 0x1049d2b60、0x1049d348c、0x1049d3800 也把相同元数据交给 DefaultCallsite::register。这些引用位于 turn_finished 异步 future 自身的日志路径，不能因为数据符号含有 notify_parent_of_terminal_turn 就解释成 Session 对 turn_finished 的调用点。

这排除了一个容易混淆的候选类别，并强化了对 §8.40 中“closure callsite metadata”的边界说明；没有找到 Session 到 vtable +0x80 的间接分支。结论来自本机 arm64 二进制的符号名和精确指令反汇编，未观察运行时执行；上游调用边仍未定位。

小结

目前证据支持一个更精确的图景：spawn 是经共享 AgentControl 进入统一的线程与 Agent tree 管理流程；child 有独立 thread/session 标识，同时按策略继承设置或历史；spawn 关系先被持久化，再投递首条消息；legacy completion watcher 与 V2 terminal-event forwarding 走不同路径，父子通信、等待、终态消息和 UI 活动事件是彼此相关但不同的通道。

最重要的实现细节不是“同时开几个模型”，而是如何可靠地登记子节点、约束容量、建立可恢复的父子边，并让协作消息与界面活动保持一致。下一步若要把逆向再推进，需要取得桌面 host 的运行时配置/事件证据，或继续把本机二进制的 watcher 异步状态机和公开源码逐段对齐；可复核的采集脚本与证据台账已整理在 Codex Subagent Reverse Engineering 仓库。文中将受控 CLI 实测与静态源码/二进制结论分开标注。
