Codex Subagent 逆向笔记：从 spawn_agent 到父子线程协作

Posted on 2026-10-13 In AI Agent Word count in article: 37k Reading time ≈ 2:14
结合 ChatGPT 桌面版内置 codex-cli、客户端 JavaScript 与公开 Codex 源码，拆解 子 Agent 的创建、上下文继承、协作消息、等待、完成回传和界面状态，并标注版本与证据边界。

Codex 的 subagent 看起来像“主 Agent 派出几个小 Agent 并行工作”。从实现证据看，更准确的模型是：父 Agent 通过协作工具请求创建一个有独立线程身份的子 Agent；共享的 Agent 控制器负责登记、调度、通信和回收父子关系；客户端再把这些状态呈现成活动列表。

本文结合本机 ChatGPT 桌面应用内置 codex-cli 的静态分析、应用资源中的 UI JavaScript，以及 OpenAI codex 仓库与本机版本号一致的源码 tag 交叉整理。版本号相同提高了源码对照的可信度，但没有签名构建清单证明本机二进制确由该 commit 构建；因此我仍把本机观察和源码解释分开说明。

先看整条链路

  participant A as AgentControl
  participant C as Child thread

  A->>A: prepare config / source / history

  A->>C: create thread + accept initial input
  A-->>P: spawn returns

    P->>P: Continue current turn or wait for activity

  par Separate completion signals

    A-->>P: QueueOnly AgentMessage to parent mailbox
  end

并行关系是理解交互的关键：spawn 的返回表示 child 初始输入已接纳，不表示 child 已完成；terminal status、完成 activity 和结果消息也是不同信号。结果进入 parent mailbox 后仍可能等待可接收的 turn，入队本身不证明父模型已读到答案。下面按版本与证据来源分别展开这些边界。

上图中从工具处理器到子线程创建、持久化关系和首条输入的步骤，来自版本 tag 源码；本机二进制中也能找到相应符号和校验字符串，但静态反汇编没有独立证明所有异步分支的具体运行顺序。

1. 工具调用不是直接启动一个 shell 子进程

该版本源码中的 V2 spawn handler 会把模型给出的 agent 描述整理成 SpawnRequest，其中包含发起者、配置、初始消息、父子关系及 fork 选项，然后交给 agent_control.spawn(...)。初始消息被指定为触发 child 新一轮执行的输入。可对照 V2 spawn handler。

控制器的 spawn_agent_internal 随后会：

  • 取得 agent-tree membership，并确定 parent thread；
  • 计算适用的 multi-agent 版本并检查执行容量；
  • 向 registry 预留 slot；
  • 解析继承的 environment、插件设置和执行策略；
  • 生成 SessionSource::SubAgent(ThreadSpawn { ... }) 及 AgentMetadata；
  • 按需准备 fork history，再调用 ThreadManager 创建 child thread；
  • 持久化 thread-spawn edge，之后提交首条输入。

这条路径表明 Codex 的抽象中心是 thread/session 与 agent tree。被分析的调用路径没有显示“每个 subagent 再启动一份独立 codex 可执行文件”的证据；但仅凭这段静态证据，也不应把它扩大成对所有平台、所有运行模式的绝对断言。相关实现见 AgentControl spawn 流程。

2. 子线程有独立身份，也保留父子来源关系

child 并非只是在父会话里追加一段带标签的对话。它有自己的 thread id、session source 和 agent path；source 元数据记录父 thread、层级和路径。控制器还会把 spawn edge 持久化，供后续恢复和父子关系查找使用。

“有独立线程身份”不等于“完全隔离”。创建时仍可能从父级继承环境选择、插件禁用列表、执行策略和动态工具；如果请求指定 fork mode，还会准备历史记录。公开源码注释特别指出：复制对话历史不应改变发起 spawn 的那一轮原有能力。具体继承项取决于请求、配置及当前 feature，不能把它简化成“所有上下文都复制”或“子 Agent 从零开始”。

在新 thread 建好并建立关系后，控制器才提交初始输入；代码分别处理普通 user input 和 inter-agent communication。V2 下还会解析模型信息等启动配置。此后 child 作为独立执行单元继续跑自己的 agent loop。

3. 并行受容量与登记机制控制

spawn 不只是创建 thread。控制器会先登记 membership、检查 execution capacity，并通过 registry 预留 spawn slot；V2 resident 模式还有对应的 residency slot。成功后才 commit 这些登记。源码也有 PendingSpawn，在创建尚未完成时暂时持有 agent-tree membership，避免一个“待完成 spawn”失去树上的归属。

本机二进制字符串里出现了 max_concurrent_threads_per_session、min_wait_timeout_ms、max_wait_timeout_ms 等配置名，以及“pending spawn must own agent-tree membership”一类错误文本。这些只能证明该构建包含相关配置与防护逻辑；没有检查运行时最终配置，不能据此给出具体并发上限。

容量检查不等于原子预留

我在 2026-10-16 把容量结论重新核对到 OpenAI Codex 上游 main 的 6ae8b8a。AgentControl::check_turn_admission 明确是 advisory check，不预留名额；admit_turn 在任务开始时另行增加活动数。不同 child session 有各自的 ToolCallRuntime dispatch lock，却共享 agent-tree limiter，因此两条 session 的检查可能在任一新 turn 取得 guard 前都通过。当前提交与容量审计所用的 e89b7c4 在 limiter、admission API、tool-dispatch lock 和 task guard 文件上逐字一致；codex_thread.rs 的差异是 suspension 注释更新，明确要求宿主在转移所有权前另行完成树清理，或 fence 并终止树上的 persistence writer。这个源码顺序允许 check-then-start 交错，但没有证明真实运行超过上限，也没有 Desktop 运行时观测。详见容量检查与 guard 的证据记录。

4. wait_agent 等待的是活动，不是 join

当前 V2 wait_agent handler 先应用配置里的 timeout 下限、上限和默认值，然后订阅 session input queue 的 activity。等待结果分为三类：收到 mailbox activity、被新输入 steer、达到超时。它返回的状态也明确对应这三种情况。

因此它不是传统线程库里的 join(child)：它不只是盯着 child 是否退出，也不保证“所有 child 都完成后才返回”。一条协作消息就可能唤醒等待；父 Agent 随后可以读取结果、继续等、给 child 发 follow-up，或自行整合现有进度。具体实现见 V2 wait handler。

本机二进制中还能找到 spawn、wait、list_agents、send_message、followup_task、interrupt_agent 等 V2 handler 名称，也能找到 legacy agent handler 符号。它们说明构建中存在这些操作面；不同版本、feature flag 和产品界面暴露哪些工具，需要另外确认。

V1 和 V2 的 wait_agent 不是同一种等待

同名工具在两个版本中的契约不同。V1 的 wait_agent 接收一个或多个目标 agent，等待目标状态进入终态，并返回 agent ID 到状态的映射；多目标时，任一目标先结束即可唤醒调用。V2 则没有目标列表，它订阅父线程自己的输入活动：子任务消息进入 mailbox 可以唤醒它，用户 steer 也可以唤醒它。V2 返回的是通用等待结果，不包含哪个子任务更新、其终态或消息正文。

这也解释了为什么“wait 已返回”不能直接等同于“某个子任务已完成”。状态通知和结果消息有各自的路径：V2 结果消息单独进入父线程通信队列，再由输入/历史处理路径提供给后续模型请求；wait 的返回文本本身不承载结果。固定源码快照 740e5af 中，V2 工具描述提到会提供更新摘要，但 handler 的返回结构没有 agent 字段，测试断言也确认消息正文不在 wait 结果中，因此本文以 handler 实际返回结构为准。

这部分是该公开源码快照的静态分析，不是 Desktop 实时运行捕获，也不代表所有版本。具体边界和源码位置见逆向研究账本。Lab 的 Inspector 现在可以逐个选择子任务完成、其他子任务发消息、用户 steer 和超时，观察两种等待契约的不同返回。

5. 完成通知按 agent 版本分流

与本机 CLI 版本号对应的公开 tag 源码中，control.rs::maybe_start_completion_watcher 是 legacy 路径。它订阅 child 状态直到终态；订阅流结束或失败时会再查询一次状态。终态出来后，它会把结果送回 parent：带 V2 agent path 的情况使用 inter-agent completion message 并设 trigger_turn=false，legacy 情况则注入不启动新 turn 的 SubagentNotification。树正在关闭时的 shutdown 通知会被抑制。更关键的是，spawn.rs 调用点明确只在 multi_agent_version != V2 时启动这个 watcher，因此不能把 watcher 当作 V2 child 的通用完成机制。见 watcher 实现 和 spawn 调用点。

同一版本 tag 中，V2 的调用链是另一条：child session 发出 TurnComplete 或 TurnAborted 时，Session::send_event 会进入 maybe_notify_parent_of_terminal_turn；该方法先要求版本为 V2、来源是带 agent path 的 ThreadSpawn，再从终态事件和已记录错误构造 AgentTurnOutcome，交给 AgentControl::turn_finished。控制器随后由 completion.rs::notify_parent_of_terminal_turn 路由结果。成功完成且有 parent turn id 时会发 SubAgentActivityKind::Completed，之后按终态构造结果消息并排入 parent 通信队列，trigger_turn 为 false。错误终态使用相应的 completion 文案，部分拒绝错误有专门处理。见 Session 终态事件调用链 和 terminal outcome 路由实现。

这两套实现都说明：状态/活动事件与结果消息不是同一个事件，而且排入 parent 队列不等于 parent 模型已经消费并整合了答案。客户端另外有一个针对 /flora/subagent/thread/turns 的查询模块，会在有可用记录时选择 child 的最新 final answer；那属于另一条结果展示/读取路径。尽管版本号相同，公开源码 tag 与本机安装包之间仍缺少构建来源证明；以上版本分流描述的是被检查的 tag 源码，并由本机符号/字符串作静态交叉佐证。

完成结果如何进入父线程，以及什么时候落盘

我继续沿着 rust-v0.162.0-alpha.17.2 的结果投递路径追到父线程。child 终结后，控制器根据 ThreadSpawn 来源找结构父线程，把终态格式化为 inter-agent message，并以 trigger_turn=false 提交。成功提交的指标是 queued；它只说明消息进入投递路径，不表示父线程已读取。成功 child 的 SubAgentActivityKind::Completed 是另一条活动事件，而且需要 parent turn 信息。

父线程是否加载、是否正在接收 mailbox input，会改变结果的下一站：

父线程状态 结果位置与唤醒行为
已加载、turn 活跃 进入 session mailbox 并发布 activity。wait_agent 可能因此返回；当前 turn 只有在 mailbox 接收阶段开放时才会接入，否则消息留待后续 turn。
已加载、空闲 QueueOnly 本身不启动普通 turn。若线程带有 durable sleep 标记，mailbox activity 可以启动恢复 turn。
本地 eviction 卸载 runtime 仍有 eviction 记录时，不必先加载 session；结果保留在进程内 runtime mailbox，稍后加载时再转入 session input queue。
冷恢复、没有本地 eviction 记录 路径会先按 thread identity 懒加载历史，再走已加载 session 的投递流程。因此“未加载”不是单一状态。

真正的记录边界在父线程把 TurnInput::InterAgentCommunication 处理为 turn input 时：随后会写入 typed AgentMessage 和 inter-agent metadata，并由历史重建逻辑重放。进入 session/runtime mailbox 之前和期间，已检查代码展示的是进程内队列；没有发现把尚未读取的结果单独写入磁盘的步骤。因此不能把 runtime mailbox 描述为跨进程持久队列，也不能保证进程退出后未消费结果可恢复。这个图来自匹配 tag 的静态源码追踪，没有诱发进程退出或运行测试。

已发出的模型请求不会被新到的 child 结果改写

把这条路径接到模型请求构造后，可以看清一个容易混淆的时间边界：每次 sampling 都先从当时的 session history 建立 Prompt.input，再构造并序列化 ResponsesApiRequest。如果 child 结果在请求 A 发出后才抵达，它不会倒插进 A 已经构造好的输入；结果要先通过 parent mailbox 的接收阶段，再被记录成 typed AgentMessage，之后某次 sampling 才会从更新后的 history 构造请求 B。这个 B 可能是同一 turn 的后续 sampling，也可能来自稍后的 turn，取决于当前 turn 是否继续以及 mailbox phase 是否开放。源码因此证明的是客户端的后续请求候选路径，并非某个实时请求必然含有该消息，更不证明远端服务或模型已经消费它。可沿父线程 sampling 与 follow-up 循环、请求构造与输入准备及mailbox phase 接收边界交叉检查。桌面实验台现在把“请求 A 已发送”和“结果进入后续请求 B”画成两条时间线，避免把 wait 唤醒误读成正在运行的模型请求被动态改写。

7. 根 turn 挂起时，根线程完成不等于子树清理完成

对照公开仓库的两个快照 97ebf2d 与 9c84e89，core/src/session/turn_suspension.rs 的处理发生了变化。旧快照会先枚举当前已加载的后代；如果找到子线程，就返回 HasLiveDescendants。源码注释同时说明，这只是当前快照，不是阻止并发 spawn 的原子门闩。

新快照移除了这个早期拒绝，顺序变为：先 flush 根线程历史；重新检查并取走活动 regular turn；取消该 turn 但不追加终态事件；清掉进程内待处理输入；关闭共享 agent runtime 的新启动入口、取消信号和 mailbox；停止根 session runtime；再次 flush 并关闭根 writer；最后发出 ShutdownComplete。

flowchart LR
  A[旧快照：列出已加载后代] --> B{有子线程？}
  B -- 是 --> C[返回 HasLiveDescendants]
  B -- 否 --> D[继续挂起]
  E[新快照：flush 根历史] --> F[取消根 turn，不写终态事件]
  F --> G[关闭新启动入口 + 取消共享 runtime + 关闭 mailboxes]
  G --> H[停止根 runtime，flush 并关闭根 writer]
  H --> I[发出根 ShutdownComplete]
  G -. 另一个跟踪器等待已准入的树操作 .-> J[AgentTreeShutdown.wait_detailed]
  I -. 不代表 .-> K[所有后代清理已结束]

这里需要把三个不同的信号和调用点分开：ShutdownComplete 是根 session 在自己的 runtime 清理和根 writer 关闭后发出的事件；AgentTreeShutdown.wait() 和 wait_detailed() 都等待共享 tracker 中已准入的操作，后者还可返回结构化清理失败报告；app-server 的 shutdown_drain_waiter 则在 thread/revert 时等待旧 listener 处理完 ShutdownComplete，随后才替换 runtime。第三个等待器是 listener 事件排空，不是子树清理等待。

我把精确提交 9c84e89 拉到本地后，对其完整 tracked source 搜索 request_agent_tree_shutdown、AgentTreeShutdown 和 wait_detailed()：API 在 core 中定义并由 core-api 导出，生产代码没有调用点；能找到的调用处在 core 测试。app-server 的 listener drain 也没有调用 tree-shutdown handle。因此，当前公开源码明确规定宿主应单独等待树清理，但这个提交本身没有展示生产宿主如何完成交接。打包版 Desktop 宿主可能位于该仓库之外，仍待检查；不能把“仓库内未找到”扩大成“Desktop 一定没有等待”，也不能用根事件推断所有子线程已经退出。

我又检查了本机 ChatGPT Desktop 26.1007.71326 的 Electron 主进程 JS 资源：从 app.asar 索引读取了全部 34 个 /.vite/build/*.js 文件，共 10,339,235 字节；已知主 bundle main-CwxgTOle.js 的 SHA-256 与之前记录一致。对 request_agent_tree_shutdown、AgentTreeShutdown、wait_detailed、ShutdownComplete、shutdown_drain_waiter 和 thread/suspend 做精确字串扫描，均未命中。这说明当前检查到的 Electron 主进程 JS 层没有这些字面调用或处理器；它不覆盖 app.asar 中的 webview 资源、内嵌 Rust app-server 的行为、动态生成的 RPC 名称，也不能证明不存在功能等价的宿主等待逻辑。因而“宿主交接”仍是未解决问题，而不是已证实不存在。

8. 本机版本与官方源码 tag 对照

用户停止父线程时，子线程清理在后台继续

继续检查同一安装版 Desktop 26.1007.71326 的 webview 资源后，找到了客户端 conversation manager 的中断实现。interruptConversation 会先等待当前线程自己的 interrupt 逻辑；当来源是 user-stop，它把 interruptSubagentDescendants 放进 scheduler 后台执行，不等待整个后代清理结束。因此，Stop 操作返回不能作为“所有子 agent 已停止”的证据。Durable thread/stop 的 user 路径也采用后台清理；其他符合条件的来源则会等待后代清理。

后台 helper 分两轮处理：先对已知后代快照中的线程并发尝试本地 interrupt；之后重新发现一次后代，对仍显示 active 且尚未处理的线程再尝试本地 interrupt。如果本地没有对应 conversation，就读取最新 turn，并且只在 turn 状态为 inProgress 时发送 turn/interrupt。递归调用使用 descendant-cleanup，避免每个子线程再次触发整棵子树级联。单个子线程失败会记日志后继续；第二轮重新发现失败则结束这次补充扫描。

这说明 Desktop 客户端做的是分两轮、尽力而为的子线程中断编排，不是服务端原子树取消。快照变化、失败和竞态都可能使某个子线程没有被确认停止。证据来自当前安装包内 app-shared-8340f229c2b3.js（SHA-256 3b4cabc382e71f0da7398393a619d7c62d13dfae598a5fe2e9880ab8d31d1bf5）与 app-initial-1ab6fbe93c4f.js（SHA-256 f3d5fedc993d0ead2720c9877d8c72a82dc5fb2d935f13ad9426e6964fb6f105）的静态代码。这里没有实际点击 Stop，也没有观测子线程最终状态。详细调用条件与异常边界见研究账本。

11. Desktop 退出会请求 stdio 清理，但不等待它完成

为了避免用更新的公开 main 推断本机安装版，我对齐了 ChatGPT Desktop 内嵌的 Codex CLI 0.162.0-alpha.17.2，并检查上游同名 tag rust-v0.162.0-alpha.17.2（peeled commit 740e5af33c71225640e0c1c1555c514c2c93ab74）。随后把 Desktop bundle 的 child.kill() 调用与 Node 信号语义、该版本 app-server 的 stdio transport 串起来。

Desktop 的退出清理会对直接启动的 stdio 子进程调用不带参数的 child.kill()。Node 默认发送 SIGTERM；匹配版本的 app-server 默认启用 Unix SIGTERM handler。handler 启动 45 秒进程 watchdog、取消 stdio forwarding，并发送 ConnectionClosed。单客户端 stdio 的关闭事件会进入 app-server 退出流程：关闭 RPC gate、清理连接、drain 后台任务，再并发请求关闭 ThreadManager 中登记的线程，每个线程有 10 秒上限。若清理卡住，watchdog 最迟在 45 秒后以退出码 1 结束进程。

这里的“登记线程”有明确边界：ThreadManager 退出时先复制当时 map 中的条目，再并发关闭这个快照里的线程；成功关闭的条目会从 manager 移除，超时或失败的继续保留。该版本的线程创建路径会在 session 初始化后把 runtime 注册进同一 map。因此，这条清理覆盖快照时仍在 manager 中的线程，不是沿 spawn 父子关系递归遍历；每线程 10 秒 timeout 是并发执行，也不意味着所有线程按顺序累加等待。该 tag 的 AgentTreeShutdown 等待句柄方法名是 wait()。显式 close_agent 则走另一条 shutdown_agent_tree 路径：从内存中的 spawn tree 找当前 live 后代，再分别关闭请求节点和后代；没有证据显示 app-server 退出会调用这个显式关闭路径。退出流程仍不能证明快照之后才登记的线程、已移出 manager 的 runtime，或宿主侧 tree-wait 与 persistence-writer handoff 已完成。

退出流程会先关闭 app-server 的后台任务 tracker，并最多等待 10 秒；新线程启动正是由这个 tracker 托管。启动代码要等拿到初始 SessionConfigured 事件后才把 runtime 插入 ThreadManager。所以，如果 tracker 等待超时而启动任务仍在登记点之前，后续的线程 map 快照可能看不到它。这是源码给出的覆盖边界，不能当作已复现的 Desktop 竞态或已确认会遗留的线程。

  A[Desktop will-quit dispose] --> B[stdio connection.close]

  C --> D[stdio SIGTERM hook]
  D --> E[45s process watchdog]
  D --> F[cancel forwarding + ConnectionClosed]
  F --> G[close RPC gates + connection cleanup]
  G --> H[drain background tasks · up to 10s]

要区分另一条路径：AppServerExit::Forced / process::exit(0) 是 managed Unix-socket daemon 的强制退出路径，它会 abort connection-cleanup tasks，不执行普通 drain 和 shutdown_threads()；它不是 Desktop 启动的 stdio 子进程退出链。

因此静态证据现在支持：Desktop 退出会向 stdio app-server 发出 SIGTERM，而 app-server 会开始有界清理已登记线程，并由 45 秒 watchdog 兜底。 但 Electron 的清理链没有等待直接子进程退出，所以不能据此确认清理完成；shutdown_threads() 也不等于等待共享 agent tree 的 AgentTreeShutdown.wait()。显式 close_agent 的子树关闭是独立路径，不代表退出时也会调用。私有后代是否都在 manager 登记表中、tree wait 与 persistence-writer handoff 是否完成仍未证实。没有实际向进程发信号或关闭 Desktop 做运行时观察。

12. 桌面端的 Subagents 面板负责浏览和读取结果

继续检查本机 ChatGPT Desktop 26.1007.71326 的 app.asar 后，我把本地 Codex 会话的 subagent 面板入口与 ChatGPT 会话面板分开追踪。两者都展示子 agent，但打开路径和数据读取方式不同。

本地会话的 openLocalConversationSubagentsPanel 先为父 conversation 建立右侧面板 tab，并把选中的子 conversation ID 写入 durable route。选中子线程时，调用方会尝试 hydrate 对应的线程/祖先；如果该线程尚未加载，会读取 thread-list summary，并按条件 hydrate 后台线程、载入历史页。若用户从列表点进某个 background agent，则先激活其 summary、确保第一页已加载，再打开独立的后台 agent tab；同一个 conversation 已经打开时会去重。这表明面板是围绕已有 conversation/session 状态构建的浏览入口，不是本次追踪到的 spawn 创建入口。

继续沿客户端共享状态层追踪后，可以把“选中”“摘要可见”和“详情历史已加载”拆开理解。activateThreadSummary(id) 会在已有 thread summary 可用时构造轻量 conversation 并放进本地映射；它本身不等于读取完整历史。ensureConversationFirstPage(id) 先检查归档抑制和本地 conversation；若尚不存在，会调用 hydrateBackgroundThreads([id])，再检查状态。如果已有 conversation 但历史状态仍需补齐，则继续调用 loadOlderConversationHistoryPage(id)。后台 hydrate 最终可经 readThread(id, includeTurns, options) 发出 app-server thread/read RPC，参数包含 threadId 与 includeTurns；并发的后台读取可能会合并。因而面板里“已经选中”不代表完整 transcript 已经加载，详情仍可能处于补读状态。这条路径读取已知线程，不是 thread/start 或创建 subagent 的证据。

共享分页加载器还区分了几种容易被 UI 混为一谈的结果。若非 evicted 历史已经完整，它直接返回 complete；否则按条件尝试补取 partial item page、canonical-history boundary、带 cursor 的较旧 turn page，最后才初始化背景线程。单页结束后会检查状态是否推进，以及是否还存在 continuation cursor 或未加载 item page：有进展且仍有内容时返回 more；没有进展，或仍不完整却没有 cursor，则报错。首次本地历史初始化会包含 turns；若服务端标记历史有分页边界，初始窗口最多五轮。includeTurns 因调用路径而异，因此不能把所有详情读取都概括成 thread/read(includeTurns=false)。more 也只说明还有分页工作，不证明调用方随后把所有页都取完。

以上分页状态是共享客户端状态层的静态分支。没有捕获真实 cursor、RPC、加载页数或渲染结果；图里的四种可选状态用于解释源码分支，不代表某次会话真实经过了其中任一条。

23. LocalAgentControl 的构造与替换边界

继续检查当前安装版 Desktop-embedded CLI 0.163.0-alpha.10.2。在 ARM64 Mach-O 中，符号表将 0x1055d9870 命名为 ThreadManager::agent_control_for_config。用 LLDB 将反汇编严格限制在该函数至下一个命名函数 0x1055d9a2c，可以看到它准备配置数据，并在 0x1055d9978 直接调用内部地址 0x10561cac0。该内部地址没有可用的独立符号名，因此这里只记录“构造入口调用”，不把机器码本身直接认定成已解析的 LocalAgentControl::new。

匹配版本的公开源码给出了对应语义：agent_control_for_config 调用 LocalAgentControl::new，传入 ThreadManager 状态的弱引用、线程 ID 生成器副本和当前配置中的 rollout_budget。普通的新线程路径会调用该方法生成控制器；若请求携带内部父线程，则会先沿用父线程捕获的 AgentControlInit。之后，如果 ThreadManager 安装了 agent_control_factory，注册阶段可把本地 controller 换成 host 提供的 AgentControl，但保留本地 runtime；没有 factory 时 controller 保持原样。

进一步区分线程入口后，factory 规则更精确：新建根线程、fork 根线程和冷恢复线程进入注册时，初始的 Local 控制器可被 host factory 替换；内部子线程携带父线程捕获的 AgentControlInit，不会匹配只处理 Local 控制器的替换分支。若恢复的是仍在运行的线程，ThreadManager 会在注册与 factory 选择之前直接返回已驻留线程，继续使用其现有 controller。这里的“冷恢复”与“复用运行中线程”是两种不同路径。

因此，源码支持的构造与选择边界是：本地 ThreadManager 可构造 LocalAgentControl；内部子线程继承父 controller；配置了 host factory 的根线程或冷恢复路径可替换成 host controller。这解释了为什么静态二进制里存在 LocalAgentControl 的 spawn 方法和多张候选表，却不能单凭这些静态数据断言某次 handler 一定选中了它。当前安装版仍未捕获到 V2 handler 调用时的实际 vtable，内部调用目标也未独立命名；本轮没有启动 child。

这条分支边界也已做成交互场景图：可以切换新建根线程、fork 根线程、冷恢复、内部子线程和仍在运行线程的恢复，并开关 host factory，查看源码规则如何改变控制器选择。图展示的是匹配版本源码的决策，不表示我们已经捕获到安装版某次 spawn 的实际 vtable。

31. canInteract 如何影响本地子会话

继续追踪 build 20586 的 local-conversation-subagents-panel-tab-70cb3c70c0c0.js 到子会话 renderer local-conversation-thread-5ec41ebdd09b.js（344,921 bytes，SHA-256 e203868a18600a77a62ec38aa908de2fe7f4719f6b5c3c2c356eceda04b95479），可以看到面板只在 child.canInteract === true 时将 canInteract 传为 true。renderer 对未提供的值默认按 true 处理；值为 false 时，恢复查询不会收到 child thread ID，thread 按只读呈现，composer 不显示。值为 true 时，代码可以尝试恢复并显示 composer，但还要经过 writer-conflict 等独立状态判断。

writer conflict 是另一道 UI 门控：即使 canInteract 为 true，它也会让 thread 只读、隐藏 composer，并显示冲突提示；提示提供重试，条件允许时还提供 fork 操作。列表选择逻辑中，明确不可交互的 child 会打开 Subagents 面板，其他 child 继续走 background-agent/detail 路径。这些都是客户端路由和呈现条件，不能据此推断服务端授权、安全边界，或某个运行中 child 的实际 canInteract 值。

本地 Lab 已把这几个条件做成可切换的解释图：分别改变 canInteract 和 writer conflict，观察恢复资格、transcript 只读状态与 composer 显示结果。它是对静态 bundle 逻辑的交互式讲解，不会操作 Codex 会话。更多源码上下文、模块哈希和复核方法见研究账本。

32. 子线程选择会验证祖先链，并丢弃过期导航

继续沿 build 20586 的本地会话面板追踪，我检查了面板入口、异步 opener 和 verify-descendant 三个模块。验证器会沿 parentThreadId 向上检查：不能把父会话本身当作子线程；祖先链不能循环；已知 host 必须一致；最终链路必须到达面板所属的父会话。若中间祖先记录缺失，客户端会先看父会话的 descendant snapshot；在调用方允许修复且 snapshot 尚不完整时，它会用 includeTurns: false 补齐缺失祖先，再重新验证。通过后才确保所选子线程的第一页会话历史已加载。

这个过程包含异步等待，因此 opener 还检查选择是否已经过期。它开始处理子线程 A 后，如果用户切到 B 或关闭面板，A 的校验和补齐仍可能结束；但在应用成功结果、失败回退或结束 loading 前，代码会重新检查面板当前请求的 child ID。若请求已变化，旧 continuation 直接退出，不会把界面切回 A。被拒绝的祖先链则回到子线程列表。父会话重建时可能执行的 hydrateBackgroundThreads([parent], {includeTurns: true}) 是另一条路径，不应与缺失祖先的 metadata-only 补齐混为一谈。

以上是对本机 Desktop app.asar 中静态客户端代码的确认，不表示这些请求在某次运行中实际执行，也不能证明服务端授权、网络响应或界面完成渲染。精确模块大小、SHA-256、ASAR 根哈希和复核方法记录在研究账本。本地 Subagent Lab 新增了四种可切换说明：合法祖先链、host 不匹配、缺失祖先和切换选择期间的旧请求；它只解释源码分支，不连接正在运行的 Codex。

34. 协作版本在 turn 中解析，不能只看 thread/start

继续沿公开 Codex 源码追踪（提交 67a709665ac7b50311b93e32612c9a8281684787），发现版本选择不一定在新线程创建时完成。app-server 收到 turn/start 后读取该轮的模型与协作设置，再按有效 StepSettings 模型取得 model_info。新 session 初始化时可能还没有 MultiAgentVersion；第一次完整 turn 会结合有效配置和模型 metadata 解析版本，并写入一次性状态。因此，仅凭 thread/start 不能确定首轮会采用 V1 还是 V2。

版本解析后，tool registry 才为该 turn 注册 V1 或 V2 的 spawn_agent handler。两个 handler 最终都调用共享的 AgentControl::spawn 接口；这里分支的是工具表面和 handler 行为，并非两套不同的 AgentControl 实例。常规 app-server session 则绑定 LocalAgentControl，spawn handler 进入该控制器后才继续执行容量和子线程创建路径。也就是说，协议版本解析、工具 handler 选择、AgentControl 后端选择是三个相关但不同的问题。

若要判断某个 Desktop 任务实际使用了什么版本，应把同一线程的证据连起来：turn/start 请求及有效模型、对应 model/list 的模型 metadata、首个完整 turn rollout 中的 SessionMeta.multi_agent_version，以及实际 spawn_agent 调用和其子线程的来源/父线程关系。rollout 字段能证明版本解析结果；spawn 调用与关联子线程才能证明该路径真的运行过。单独看到 spawn_agent 名称不能区分 V1/V2，公开源码也不能证明 Desktop 传入了什么请求或元数据。

这次追踪的是公开源码提交，不是 Desktop 实时采样。关键调用位置、文件和本地复核步骤见研究账本。

35. Lab 的 spawn 回执表示排队，不代表子进程已启动

对本地 Subagent Lab 的只读代码检查发现，它的 spawn_agent 会先把任务放入本地队列，再返回任务 ID；实际 CLI 子进程是在后续调度阶段启动。因此，调用成功只能证明队列接收了请求，不能证明子进程已启动，更不能证明 Codex 已接受该子线程的首轮输入。此前界面上的“Child task created”容易让人把这几个阶段混为一谈。

小结

目前证据支持一个更精确的图景：spawn 是经共享 AgentControl 进入统一的线程与 Agent tree 管理流程；child 有独立 thread 标识，并在同一协作树内继承 controller/runtime；根线程的 host/local controller 选择受线程入口、factory 和 MultiAgent 版本约束；spawn 关系先被持久化，再投递首条消息；legacy completion watcher 与 V2 terminal-event forwarding 走不同路径，父子通信、等待、终态消息和 UI 活动事件是彼此相关但不同的通道。

最重要的实现细节不是“同时开几个模型”，而是如何可靠地登记子节点、约束容量、建立可恢复的父子边，并让协作消息与界面活动保持一致。当前未解的关键点是：静态候选 controller method table 中哪一个会被某次 Desktop spawn 实际选中，以及安装版运行时是否能捕获完整的 spawn 与面板更新链。current main 的全仓调用点检查进一步表明，受检仓库中的生产组合没有安装 factory，但它仍不能证明私有 embedding 的实现，也不能替代对安装版 spawn 的运行时采样。可复核的采集脚本与证据台账已整理在 Codex Subagent Reverse Engineering 仓库。目前这篇笔记没有把静态分析写成运行时结论。

42. 面板列表投影与子线程详情读取是两条路径

60. 版本匹配的源码解释了 codex exec --json 为什么漏掉 V2 spawn

上一节把“rollout 里确实创建了 child，但 --json 流没有 spawn 项”的原因留作未知。我随后取回与安装版本完全对应的 Codex 源码：CLI 0.163.0-alpha.10.2 对应提交 4ebc485。因此，这次对照不再依赖较新的 main 快照。

V2 的 spawn_agent handler 在 AgentControl::spawn 成功后发出一个 SubAgentActivityKind::Started，其中带有 child thread ID 和任务路径。这个项目经由 core 的 ItemStarted / ItemCompleted 生命周期进入 app-server，再由协议层保留为 ThreadItem::SubAgentActivity。可以沿着版本对应的 V2 spawn handler、activity 生命周期、app-server 通知转发和协议 item 转换逐层复核。

缺口出现在 standalone CLI 的 JSON 投影器：它显式支持 CollabAgentToolCall，但没有 SubAgentActivity 的 exec JSON 表示；不认识的 ThreadItem 会由映射器返回 None。ItemStarted 和 ItemCompleted 都会经过这层映射，所以 V2 spawn 的 activity 在进入 CLI JSON 输出之前就被丢弃了。关键位置是JSON item 映射和开始/完成事件映射。这与 10 月 19 日的观测吻合：rollout 有已完成的 spawn_agent function call 和带父线程 ID 的 child rollout，而 --json 没有对应 spawn item。

这也说明 V2 的 child 事件应该按 app-server 的 SubAgentActivity 类型追踪，不能假定它会采用 V1 的 CollabAgentToolCall 形状。wait_agent 事件里的空 recipient/state 字段只描述 wait 工具调用自身，不能据此反推没有 child。当前原因已经由版本匹配的源码解释；具体是哪张 controller vtable 服务任务、Desktop renderer 是否收到并画出原生 subagent 面板，仍需独立证据。完整路径和脱敏运行记录见研究账本。这篇文章仍只在本地更新，未推送或发布。

65. 关闭后的 V2 子线程仍可出现在树里，但冷恢复不会恢复其 Agent 身份

69. 内联行状态与区块汇总状态的具体规则

在当前安装的 ChatGPT Desktop 26.1013.40934（build 20770）中，调用方 local-conversation-thread-845836667d0b.js 的 zO 从 sites-end-resource-8a7a3656de67.js 导入活动投影器和汇总函数。前者根据活动项、background-agent 记录、当前 turn key 与 later-activity 集合构造行；后者把所有行的 activityStatus 汇总为内联块状态。两个 bundle 文件的 SHA-256、符号名及打包字符串偏移已记入本地研究账本；ASAR 中没有对应 source map，因此偏移不是原始源码行号。

逐行状态规则：

  • 有 background-agent 记录且 parentTurnKey 匹配当前 turn 时，行 status 沿用该记录的 status；记录属于其他 turn 时，行 status 为 done。
  • 没有后台记录时，活动项 displayStatus 为 completed 或 interrupted 会得到行 status: done，其余得到 status: active。
  • 行 status 为 done、属于当前 turn、且 child conversation ID 不在 later-activity 集合时，activityStatus 为 done；其他情况沿用活动项的 displayStatus。当前调用点传入的是空集合。
  • 缺失、空白，或与 agent thread ID 相同的显示名会被过滤，不生成展示行。

块级汇总的优先级是：有任意 interrupted 则为 interrupted；否则有任意 updated 则为 updated；否则列表非空且每项都是 completed 或 done 时为 completed；其他情况为 active，空列表也因此为 active。这解释了汇总函数的静态实现，但没有证明某次真实对话中的缓存记录取值，也没有捕获实时通知、React commit 或屏幕绘制。打包代码分析与运行时 UI 证据仍需分开看。

我进一步检查了同一 build 20770 中的独立 Local Subagents 面板模块 local-conversation-subagents-panel-tab-33b5e3e9938b.js。这个面板把 status === done 的记录放入 Done 分组，其余状态都放进 Active。行摘要优先显示截短后的 objective，其次显示 statusSummary；如果两者都没有，非 done 行显示 “Working”。waiting 还会显示 Waiting 标签；未完成且带有 startedAtMs 的行显示已运行时间。Done 行可能使用 lastAssistantMessageAtMs 或 recencyAtMs 显示相对时间。

72. Local Subagents 面板记录从哪里来，又如何刷新

我把 build 20770 的 Local Subagents 面板继续向上追到了共享 selector 和 descendant store。面板模块导入 selector 后取得父会话对应的 child rows；行构造器先读取父级历史中的 subAgentActivity 和 spawnAgent receiver，再把 source-linked 后代、缓存 conversation 与活跃 thread summaries 合并进候选集合。它随后结合父子 turn 归属、子会话历史、resume state、runtime status 和 descendant discovery 是否完整来派生最终行，并按最近活动时间排序。

刷新也不是面板自己定时拉取。挂载后的 store 会订阅父线程活动项、已发现的后代线程和 app-server 的 thread 生命周期通知，并调用 discoverSubagentDescendantSnapshot(parent, {reconcile: true})。新 child、归档/删除/取消归档、后代里的嵌套 child 活动，以及 resumeState 进入 needs_resume 都可能触发重新发现和 selector 更新；订阅会在卸载时清理。

这补上了“面板拿到哪些记录”和“哪些事件会让它重新计算”两段静态链路。Local Subagents 行与父时间线 inline activity 仍是不同展示路径；当前证据不能证明两者逐行同源，也没有捕获真实 RPC 通知、React commit 或桌面实际绘制。完整 bundle 哈希、符号和复核步骤见本地研究账本。博客仅本地修改，没有推送或发布。

73. 点选面板刷新信号，逐步看它如何回到 selector

这让“发生变化 → 请求重新发现 → 重新投影列表”比一张固定流程图更容易检查，也把不同来源的事件放在同一刷新环里比较。演练仅切换说明内容，没有连接本机 app-server；它不模拟真实 selector 执行，也不声称某个 child 一定会出现在面板中。实际记录仍由 ancestry、缓存、运行状态和 discovery completeness 等条件共同决定。
