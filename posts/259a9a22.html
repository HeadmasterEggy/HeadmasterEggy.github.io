Agensh 论文精读：没有中央指挥，1024 个 Agent 如何协作写软件

Posted on 2026-09-30 In Paper Word count in article: 7.9k Reading time ≈ 29 mins.
逐节精读微软研究院 Agensh 技术报告：五步协作循环、Git + 消息 + 共享上下文三层基础设施、完整 Worker 提示词与事件驱动运行时、ProgramBench 五任务及 1,024 Agent 实验的分任务数据，以及结果的适用边界。

原论文：Agensh: Scaling Organizational Intelligence to 1,024 Agents，Zhihao Zhan*、Ting Song*、Li Dong†、Shaohan Huang、Jianxun Lian、Yan Xia†、Furu Wei†（* 同等贡献，† 通讯作者），Microsoft Research，arXiv:2609.26781v1，2026 年 9 月 22 日，标注为 Technical report。PDF · 项目主页 · 代码

如果让大量编码 Agent 同时完成一个大任务，瓶颈未必是它们各自写代码的速度，也可能是中央 Agent 分配工作、消解冲突和合并成果的能力。Agensh 的尝试是：去掉负责派工的中央指挥，让每个工作者自行寻找任务，并用共享基础设施维持协作。

论文最醒目的数字是：在“无互联网、六小时重建 pandoc”的实验中，1 个 Agent 的最终测试通过率为 33.89%，1,024 个为 55.06%。但这不等于“任何任务上堆到 1,024 个 Agent 都有效”：1,024 Agent 的实验只覆盖 pandoc；五任务对比最多扩展到 128 个，且分任务看并不单调。下面按“问题—机制—提示词与运行时—实验—协作现象—局限”逐节拆解。

一、论文要解决什么问题

1.1 背景：从单 Agent 到多 Agent

论文开篇的判断是：单 Agent 系统能感知上下文、通过工具行动、更新状态并迭代地推进目标，但它受限于一个上下文窗口、一条动作流、一份记忆流，顺序执行在复杂真实任务上延迟很高。要突破这些限制，就需要扩展 Agent 数量。作者引用的是 Kim 等人的 Towards a science of scaling agent systems（arXiv:2512.08296），把“Agent 数量”视为继模型能力、推理预算之后的又一个扩展维度。

1.2 现有做法：orchestrator–worker

现有的多 Agent Harness，如 Codex sub-agent、Claude Code sub-agent 与 agent teams、Copilot 的 /fleet 命令、Kimi Agent Swarm，普遍采用 orchestrator–worker：一个主 Agent 负责规划、拆解任务、分派给并行的工作者，并管理它们。论文（第 1 节）指出这种结构通常需要一个经过训练的编排者才能拆得好，而且整体的可扩展性从根本上受限于编排者管理工作者、整合其贡献的能力。图 2 用“星形 + 中心 Orchestrator”对比“星形 + 中心是轻量基础设施”来表达这一点：Agensh 里中心不是一个会思考的 Agent，而是共享工作区、消息接口和共享上下文。

1.3 “无中央指挥”的准确含义

这里的“无中央指挥”有明确含义：没有一个主 Agent 为全体工作者逐项派工和合并。它不意味着没有共同目标、规则、共享状态或事件分发系统。恰好相反，论文的核心贡献是用一套基础设施承接这些协作工作。所有工作者共享同一个用户目标，运行相同的协作协议；每个人都可以发现任务、声明负责范围、实现、验证、合并，然后继续找下一件事。Agensh 改变的是组织层，不是底层语言模型。

1.4 论文的贡献一览

  1. 提出 Agensh：一个没有中央编排者的、可扩展的多 Agent 组织 Harness，由“协作循环 + 轻量组织基础设施”组成；
  2. 在 ProgramBench 上最难的五个任务上，用同一个模型与 Harness 验证 1→128 个 Agent 的扩展效果（平均通过率 19.31%→28.78%，约 49% 相对提升），并展示更大的组织能更早达到相近的通过率；
  3. 在 pandoc 上把规模扩展到 1,024 个 Agent（33.89%→55.06%）；
  4. 从工作轨迹中归纳出随规模逐步出现的自组织协作形态：同伴协调 → 多人集成 → 标准化流程 → 组织级角色专业化。

二、Agensh 的结构：每个 Agent 跑同一套五步循环

论文第 2.1 节、图 3 给每个工作者规定了一个并发、异步重复的循环：

  1. Gather context，收集上下文：读取共同目标、当前状态、同伴进度、消息和已积累的发现，弄清已经完成了什么、还剩什么；也与环境交互，识别并规划自己接下来有用的步骤。
  2. Claim sub-task，认领子任务：自己提出要做的子任务，并把 CLAIM 追加到共享上下文中公布。如果两个工作者的认领重叠或冲突，鼓励他们通过私信解决。
  3. Take action，执行：通过可用工具在本地解决该子任务；一旦确认了可能帮助其他人的发现，就通过共享上下文汇报中间进展。
  4. Verify results，验证：把本地进展与子任务的验收标准对照，不满足就修改做法直到满足。
  5. Merge progress，合并进展：把成果合并进共享工作区，并发布一条更新，说明改了什么、背后的想法、验证证据，好让同伴在此基础上继续。如果合并被冲突阻塞，就先吸收最新的同伴进展、解决冲突，再合并一次。

合并后回到第一步，基于新集成的工作和最新的同伴更新选择下一个子任务。三个关键设计点：

  • 子任务的发现与分配是自组织的：工作者自己提出、自己认领，没有人替它决定。
  • 完全异步：每个工作者继续往下走，不等所有同伴完成一轮迭代。
  • 进展逐步累积：发现和已验证的贡献通过共享基础设施沉淀下来，推动整个组织走向用户目标。

用一个简化例子理解：重建文档转换器时，有人探索表格行为并认领解析模块，有人探索命令行参数，有人修复构建脚本。各自验证后通过 PR 合入主分支；遇到相同文件或接口，再发消息协商。这是对论文机制的说明性例子，不是论文报告的一条具体执行轨迹。

三、三层组织基础设施

论文第 2.2 节、图 4 把基础设施拆成三块，各自解决不同的协作问题：

组件 要解决的问题 论文中的实现
共享工作区 保存拟议、进行中和已集成的工作；支持并发写入与异步读取；保留版本历史；把合并冲突暴露给工作者去回退和解决 Git 平台 Gitea：工作者在私有检出和分支上修改，把贡献集成到主分支；Git 记录变更来源、检测文本合并冲突，并为所有工作者提供 issue 和 PR
消息接口 协调进行中的工作、解决归属重叠、处理依赖冲突 Mattermost：共享任务频道承载团队公告；私信用于紧急的一对一沟通；保留对话历史并异步投递
共享上下文 保存可复用的发现与工作意向 思路来自 DeLM（Mao & Mirhoseini，arXiv:2606.10662），但调整了工具格式与工作者指令

3.1 共享工作区

要求是“一个支持并发写、异步读的文件系统”。选 Git 的理由很实际：分支隔离让工作者能各自开发，PR 让成果以可追溯的方式进入主分支，冲突则以文本合并冲突的形式暴露出来，让工作者自己回退解决。

3.2 消息接口：两种优先级

  • 较低优先级的共享任务频道消息：在每轮循环开始时交给工作者；
  • 较高优先级的私信：在每次基础设施工具调用结束时交付。

这样，工作者能及时处理重叠认领、协商依赖、请求帮助，而同伴同时继续工作。

3.3 共享上下文：带类型的追加式记录板

工作者发布简短、有类型的记录：

类型 含义
OBSERVED 观察到的行为
FACT 已确认的事实
FAIL 被证伪的尝试（附录提示词称其为“价值最高的条目：它阻止同伴在这个方向上继续花预算”）
CLAIM 正在负责的范围
PATCH_SUMMARY 已完成改动的摘要，含 files= / idea= / evidence=

后端是一个追加式数据库，保留近期记忆；为支持更长的任务视野，论文新增了 context grep 工具，让工作者能搜索“近期记忆”之外的完整历史记录。新的共享上下文条目被视为更高优先级更新，会在其他每个工作者“下一次基础设施工具调用返回”时被转发，使同伴的发现在整个组织内可见。

四、实现：叠在单 Agent Harness 上的一层

论文第 2.3 节强调，Agensh 是叠加在单 Agent Harness 之上的组织层，而不是替代品：

  • 单 Agent Harness 负责：一个工作者的会话状态、调用模型、执行工具、产出下一步响应——也就是“一个工作者如何推理和行动”；
  • Agensh 负责：工作者身份、协作协议、事件路由、稳健分发、共享工作区访问、消息、共享上下文，以及恢复与存活机制——也就是“有多少工作者接收事件、共享状态、协调，并反复向共同目标贡献”。

单 Agent 循环与多 Agent 协作循环之间的接口刻意保持最小且即插即用：协作循环是通过每个工作者提示词里的工作流指令实现的，而非硬编码进运行时；完整提示词见附录 A，除工作者 ID 外每个工作者完全相同。因此，Agensh 可以通过轻量的、针对具体 Harness 的适配器，接到 Claude Code、Copilot 等不同底层 Harness，而不必改变协作循环、共享服务或底层 Harness 的 Agent 循环。论文实验使用 Copilot。

这个分层也解释了论文的“自组织”：它主要改变谁决定下一项任务，以及成果如何流入集体状态，并未展示训练一个全新的单体模型。

五、附录里的细节：Worker 提示词与运行时

正文没有展开、但对理解“为什么这套东西能跑起来”很重要的信息，都在附录 A、B 里。

5.1 Worker 提示词（附录 A）

1,024 Agent 配置下，pbench-team1-worker1 收到的提示词结构如下（其他工作者只有 ID 不同）：

身份与环境：“你有 1,024 个同伴。”工作记录在 Gitea：issue #1 就是任务，工作者为自己认领的方向开自己的 issue，用 PR 提交工作；在 Mattermost 的 pbench-task 频道里交流，“要简短、具体”；发现写在共享上下文记录板上。私信会在对方当前这一轮内送达，因此适合处理“两个人正要改同一个东西”的碰撞；其他一切用频道。

记录板规则：记录板会在每一轮开始时渲染进提示词；每条限 100 字符，PATCH_SUMMARY 限 300 字符，长版本放 detail 里，同伴可 board_unfold。board_read 返回近期完整记录板（最多最近 2,000 条），board_grep 在完整历史里按关键词搜索，逗号是 OR、& 是 AND（例如 a&b,c&d 表示 (a AND b) OR (c AND d)）。“不要重新推导同伴的 FACT，不要重试被记为 FAIL 的东西。”

团队定位：“1024 个编码者，地位平等。你认领要做的东西，你做，你合并，你选下一件事。”合并到 main 之前先同步最新 main；与同伴同步以避免重复；始终专注于复现参考程序，只有当你的信息会大幅影响别人的工作时才动用协调工具。

任务（ProgramBench 逆向重建）：容器里有一个预编译的参考程序 /opt/pbench/executable，只能运行它来观察行为（--help、各种输入、边界用例），不能读取其字节（权限 root:root 0111，cat/od/objdump 都会被拒绝），“别试图反编译，那是作弊”。

三条铁律（违反任何一条整个任务作废）：

  1. 完全自主：整个团队自己定义需求、拆解、完成，没有外部输入；不要在 Mattermost 上等指示，“答案永远是：把重建往前推”。
  2. 无互联网：集群离线，git clone 原项目源码、pip install、npm i 远程包都会失败；只能用容器里已有的工具链（gcc / make / python / node 等）。
  3. 硬交付约束：仓库根目录必须有可执行的 compile.sh，运行后产出根目录下名为 ./executable 的文件。评测器会打包 repo HEAD → 解压 → 删除已提交的 ./executable → 运行 ./compile.sh → 用生成的 ./executable 跑隐藏测试。“没有根目录的 compile.sh = 0 分。”

工作循环（每步由做这件事的人自己完成）：

  1. 运行参考程序，找出还没构建的部分；
  2. 在共享上下文里以 CLAIM 宣布要认领的区域；
  3. 在该区域上运行参考程序（ulimit -v 67108864 限制内存），基于当前 main 写出复现其行为的代码，实现期间不必与他人同步代码；
  4. 用相同输入运行参考程序与自己的构建并对比；
  5. 推分支、开 PR、合并到 main；若合并被拒绝，先把最新 main 合进自己的分支，重新检查再推；
  6. 用 PATCH_SUMMARY 在记录板上说明完成了什么，回到第 1 步。

事件与中途到达的条目：环境以 [event]（含 event_id、source、kind、observed_at、summary）通知工作者；事件只陈述事实，怎么办由工作者自己决定。私信与同伴的新记录板条目会中途附加到你正在等待的工具结果上，其他一切排队到本轮结束后送达。中途到达的记录板条目的处理规则：FAIL → 如果你正在做这件事就停下；FACT/OBSERVED → 拿来用；与你正在构建的内容相同的 CLAIM → 撞车，用私信解决；其他 CLAIM → 继续做自己的。

杂项：构建所需的一切都要提交，评分器从 main 的全新克隆构建，不会调用仓库外的二进制；数据路径用 dirname(realpath(argv[0])) 解析。其余“MCP、git CLI、shell、curl、写文件，手边有什么用什么；工具不够就找一个，没有就自己造”。

从这份提示词能看出两点：一是协议高度依赖自然语言约定（认领、FAIL 的处理、撞车时用私信）而非运行时强制；二是任务提示词里已经内置了“铁律”，多 Agent 系统并非在一片空白里自己涌现出全部规则。

5.2 事件驱动运行时（附录 B.1）

每个工作者由事件驱动，而不是由中央调度的步骤序列驱动：

  • 每个工作者配一个 router（路由器），监听 Gitea 的仓库活动和 Mattermost 的消息。Gitea 侧由服务端事件触发，拉取比“上次处理通知”更新的通知；Mattermost 侧有实时连接，断线重连后会补取错过的消息。
  • 新活动到来时，监听器把事件写入该工作者的持久队列并唤醒 dispatcher（分发器）；每个事件有唯一 ID 用于去重。
  • 分发器每次被唤醒，会排序、合并队列里待处理的事件，拼成下一条提示词，投递到工作者的持久会话，一轮结束后把事件标记为已发送。工作者一轮进行中到达的事件留在队列里，下一轮再送。
  • 失败重试：投递失败会以逐渐变长的间隔重试；路由器重启后，未完成的事件回到队列，工作者之前的会话被恢复。
  • 存活保障：工作者空闲 10 分钟，空闲检测器会发提示让它继续工作；如果一轮完成后没有产生任何共享上下文条目，会追加一条提醒，让它发布有用的发现。

5.3 共享上下文的两条投递路径（附录 B.2）

  • 新一轮开始时：路由器把排队的工作区通知、到达的消息和最近的共享上下文追加进提示词；
  • 一轮进行中：包装在所有基础设施工具调用外面的一层，把待处理的私信和新的共享上下文条目追加到工具返回的结果里。

论文特别说明：这条路径作用于 MCP 工具返回，不会打断任意正在运行的进程。也就是说，“实时”只是在工具返回的边界插入新信息，而不是强行中断工作者。

六、实验怎么设计

6.1 为什么是 ProgramBench

ProgramBench（Yang 等，Can language models rebuild programs from scratch?，arXiv:2605.03546）要求 Agent 在禁用互联网的条件下，仅凭参考软件的行为，在 6 小时预算内从头重建它，用来测试“复杂长视野任务上的 Agent 软件工程”。作者从其 200 个实例中，按官方扩展结果里“最先进模型的平均测试通过率”挑出最难的五个：

任务 领域 文件数 代码行数 代码体积 (MB)
FFmpeg 多媒体处理 10,090 1,549,005 75.51
gromacs 分子模拟 8,982 815,539 47.30
pandoc 文档转换 2,767 104,336 4.86
PHP-src 语言解释器 26,266 2,812,757 119.76
ctags 代码索引 7,313 246,228 9.15

注意：这张表是参考仓库的规模（表 1）。Agent 并不需要复刻每一行，评测的是重建程序在隐藏测试上的通过率，报告的指标是 ProgramBench 的 canonical-kept pass rate。因此这些数字表示通过的测试比例，不是“完成整套产品”的概率。

6.2 实验配置（附录 C）

  • 模型与 Harness：所有配置都使用 gpt-5.6-sol（high 推理强度）、相同的 Harness（Copilot）、相同的工作者协议和评测配置；单 Agent Harness 的最大输入 token 为 272,000，最大输出 token 为 128,000。
  • 时间：按 ProgramBench 准备 Agent 容器，总时限 6 小时，运行官方评测。
  • 错峰启动：为减少“抢同一块范围”的争用，前 1 小时每 30 秒启动一个 Agent，之后每 3 秒启动一个。记第一个 Agent 启动的时刻为 t，则 t + 6h 时所有 Agent 终止并导出提交。按这个节奏估算（这是我根据论文描述做的推算，论文没有明说），1,024 个 Agent 大约要到 1 小时 45 分钟左右才全部上线，也就是说千人规模在整场 6 小时里并不是一开始就“满员”。
  • 部署：1,024 个工作者分布在 16 个节点上，每个节点 64 个。
  • 收尾提醒：结束前 45 分钟发送统一提醒（停止分派新功能，确保根目录构建可用、已有工作已合并，把开着的 PR 落地，不能合并就说明并继续）；结束前 5 分钟发第二条（把能合并的合并完然后停下，确认默认分支上 bash compile.sh && ./executable 能运行，并发布最终状态）。
  • 单 Agent 基线：论文承认单 Agent 在实践中很难持续跑满 6 小时，所以给基线加了一个“停止钩子”提示，要求它别被之前计划的范围束缚，去拿参考程序在没试过的输入上运行，从交互中派生新任务，“把这 6 小时用满”；与它配对的是多 Agent 组织里的空闲检测器，工作者空闲 10 分钟后收到类似的提示（把差距补上，而不是“别被之前 CLAIM 的范围束缚”）。

7.3 “更早达到同样成绩”（图 6）

图 6 展示前两小时的通过率随时间的变化。论文的说法是：前两小时里，更大的组织更早达到相近的通过率。以 pandoc 为例，128 个 Agent 在 30 分钟检查点就超过 30%，32 个 Agent 与 8 个 Agent 分别在 60 分钟和 90 分钟检查点才首次超过；单 Agent 的曲线在前两小时始终低于这个阈值。作者据此认为，增加 Agent 数量不仅提升最终质量，也缩短了达到特定水平所需的时间。注意这里是离散检查点，不能解读为精确到分钟的首次达到时间；同时图 6 的各任务曲线形态差异很大，例如 FFmpeg 单 Agent 很早就进入平台期，ctags 的 32 与 128 个 Agent 明显领先。

八、作者观察到的“涌现协作”

论文第 3.2 节强调：所有工作者遵循同一套循环、拿到同样的提示词（仅 ID 不同），但随着组织变大，新的自组织形态逐渐出现，范围从“协调实现”扩展到“管理集成”“标准化流程”“形成专业角色”（对应图 1 右侧的四级阶梯：Peer coordination → Multi-worker integration → Standardized workflows → Specialized roles）。

  • 8 人：与同伴协调实现。 工作者可以约定一个具体的技术接口，各自独立实现符合该接口的部分；也能自己发现并解决认领重叠。gromacs 中，有工作者公布了模块接口，其他人独立实现遵循它的命令模块；FFmpeg 中，有工作者在与同伴讨论重叠问题后改变范围，去做互补的工作。
  • 32 人：多人共同管理集成。 多个工作者可以共同推进一个技术贡献。PHP-src 中，几位同伴起初认可了某个贡献，随后另一位发现具体反例，先前的认可被撤回，作者修复后同伴再次审阅，最后由一位同伴合并。工作者在管理集成上变得更活跃，参与交流的同伴范围也更广。
  • 128 人：自发专业化与流程标准化。 工作者根据相关经验选择审阅者并重复使用这些审阅关系；也能把“整合某个贡献”的责任移交给一位同伴，由其解决冲突、验证合并后的工作并合并。pandoc 中，两位工作者建立了一个标准化集成协议：作者更新并测试分支，然后把 commit hash 发给同伴验证并合并，此协议后来被其他工作者沿用。几次失败之后，工作者进一步修订协议：约定授权同伴执行整个更新、测试、检查、合并的循环，同伴明确接受并对新的 PR 执行了这一修订后的流程。
  • 1,024 人：组织规模的角色专业化。 多个工作者承担同类的专门角色或在同一技术领域积累专长。pandoc 中多位工作者担任集成者；一个工作者可以联系多个候选集成者，选择第一个有效回应者，取消其他请求，只有在选定之后才把代码交给对方去集成。在同一技术领域专门化的工作者，也能在另一位工作者的尝试失败后接手工作，从而避免对单个工作者的依赖，增强组织的稳健性。

论文的解读是：这些形式的协作完全是自组织的——工作者自己选择合作者、划分责任、建立并修订工作流。但这些是从轨迹中观察到的定性案例，没有统一的量化统计；不能据此断言每次 1,024 Agent 的运行都会出现同样的组织形态。

九、相关工作与定位

论文第 4 节把相关工作分成两类：

多 Agent 组织与协作 Harness - Claude Code：支持持久的 agent teams，但协作仍围绕一个固定的 lead 会话——由它派生其他 Agent、管理共享任务、协调 Agent 间消息； - Codex：用带委派的并行工作者的子 Agent 工作流，结果路由回父 Agent 汇总； - Kimi Agent Swarm：训练一个编排者来拆解任务、调度并行子 Agent 以降低延迟，但仍是 orchestrator–worker 的并行方案。 - Agensh 研究的是另一种组织结构：自组织的工作者共同承担发现任务、协调依赖、整合结果的责任，并通过持久的工作循环推进。

共享上下文与去中心化协作 - DeLM 把异步工作者、任务队列和共享上下文结合起来，让 Agent 在累积的进展上继续工作，而无需把每个更新都经过中央控制器；Agensh 的共享上下文直接借鉴其核心想法； - ChatCollab 把人和 AI 作为对等参与者放进 Slack 协调角色、请求和进度；SlackAgents 把 AI Agent 嵌入 Slack 工作区做沟通与任务编排； - 就共享工作区而言，Carlini 的“用一队并行 Claude 构建 C 编译器”实验用 Git 仓库和任务锁文件协调 16 个 Claude Agent，工作者自选任务并合并改动，没有编排 Agent；STORM 把多 Agent 编码重新表述为状态管理问题，用强制局部状态一致、写入时检测陈旧或冲突编辑的共享工作区替代相互隔离的 worktree。

十、如何评价这项工作

我认为最有价值的点：论文把大规模并行 Agent 的难题从“怎样让一个主 Agent 管理更多下属”转向“怎样让工作者持续看到共同状态，并对认领、验证、合并负责”。CLAIM 降低重复劳动，FAIL 传播负面知识，PR 与验证证据让成果进入可追溯的共享状态，事件驱动运行时保证了 1,024 个会话“不死、不丢、不重”。这种设计思路对需要长时间、多模块并行开发的任务有参考价值；而且它是通过提示词 + 通用工具（Git、聊天、记录板）实现，而不是训练新模型，工程上更容易迁移。

读结果时需要保留的边界：

  1. 任务范围有限。 五个任务都是离线程序重建；1,024 Agent 只测了 pandoc。结果尚不能直接推广到产品开发、网页研究、写作或其他软件任务。
  2. 分任务结果并不单调，平均数有被少数任务拉动的成分。 见 7.2：ctags 8 人时低于单 Agent，gromacs 前三档持平，FFmpeg 与 PHP-src 增益小、绝对水平低。“持续增加 Agent 就稳定大幅提升”这个措辞，比分任务数据显示的更强。
  3. 没有给出经济性结论。 论文报告通过率和到达某个通过率的时间，没有系统报告 token、算力、消息量、PR 数量或每提高一个百分点的成本。1,024 个各带 272k 上下文的会话跑 6 小时，成本显然远高于单 Agent；更高的成绩不自动等于更省钱。
  4. 组件贡献未隔离。 论文固定了模型和 Harness 来比较人数，但没有消融实验分别量化共享上下文、消息、事件路由、Git、提示词的作用，也没有与“orchestrator–worker”基线在同样 Agent 数下做直接对比——尽管引言正是把后者的可扩展性瓶颈当作动机。因此“去掉中央指挥本身带来多少收益”，从数据上无法回答。
  5. 统计不确定性未展示。 文中给出的是各配置的成绩和轨迹，没有多随机种子重复、置信区间或显著性分析。尤其 128→1,024 的 4.12 个百分点差距，ctags 8 人时的下降，都不能仅凭一次运行判断稳定程度。
  6. 基线与多 Agent 的干预并不完全对称。 单 Agent 有“持续工作”停止钩子，多 Agent 有空闲检测器；多 Agent 还有错峰启动和统一收尾提醒。这些设置有其合理性，但也说明结果依赖大量运行控制细节。
  7. 任务提示词里内置了不少规则。 例如“完全自主”“别等指示”“先运行参考程序”“FAIL 要停手”，这些是“自组织”的先决条件，协作行为并非从零涌现。
  8. “无中央指挥”是组织概念。 系统仍有共享服务、相同规则、统一时限和收尾提醒，这些本身就是关键工程投入。
  9. 涌现观察是案例性的。 第 3.2 节的四个层级来自若干条轨迹的挑选，没有说明发生频率，也没有与未出现这些行为的运行对比。

十一、一句话总结

Agensh 展示了一种让多个 Agent 自行认领任务、共享发现、互相处理冲突并完成验证合并的组织方式：一层薄薄的组织 Harness（一段相同的提示词 + Gitea、Mattermost 与追加式共享记录板 + 事件驱动的分发与恢复），叠在现成的单 Agent Harness 上。在论文给定的六小时离线程序重建实验中，增加 Agent 数量带来了更高的平均测试通过率（1→128：19.31%→28.78%），也更早达到相近成绩，pandoc 上扩展到 1,024 个仍在上升（33.89%→55.06%）；但分任务数据并不单调，千人规模的证据目前只有 pandoc 一项。下一步若要判断它是否适合实际工程，还需要成本、重复试验、组件消融、与 orchestrator 基线的同规模对照和更多任务类型的证据。
