一、三种需求模型怎么串起来

W12 复习课上老师把需求阶段讲成一条从笼统到具体的流水线：

步骤 模型 要做到什么
1 Ad hoc 用自己习惯的方式（文字或随手画的图）把用户需求记下来。不要求正式，但要完整，后面的分析都从这里取材
2 Feature diagram 第一个正式模型：从 ad hoc 里提炼出特征，按层级排成一棵树，标出关系和约束。画完它就定下了整个项目的范围
3 Use case 特征图不够细，开发者（或 AI）没法据此写代码。所以要给每个关键特征写 use case：actor 怎么和系统交互，成功场景和失败场景分别是什么

期末给的场景本身就相当于 ad hoc 需求，所以考题一般从第 2、3 步开始画。

方法 视角
Ad hoc 混合视角：what / how / how well 混在一起
Feature analysis capability-based view：系统 = 一组期望的特征
Use case analysis operational view：系统 = 一组帮 actor 达成目标的功能

贯穿例子：AI-native healthcare agency（第五节的 agentic use case 会用到）

角色 职责
Clinical director（人） 拥有判断、安全和审批
Intake agent 收集症状和上下文
Evidence agent 检索已批准的临床指南
Care agent 起草下一步并准备转诊
Operations agent 更新记录、排期和随访队列

Running goal：分诊患者咨询、协调照护，但不移除临床医生的问责。

Agent 如何选择下一步行动：

  • 模型解读目标和当前状态；工具让它读数据、在外部系统中行动
  • 指令和策略约束它的选择
  • 循环：plan → act → observe → adjust
  • 在条件要求时必须停止、询问或移交

对需求的含义：需求描述的是结果（outcome）；允许的决策权必须显式写出。

二、Ad hoc 模型：Secure Access Room 例子

2.1 场景

一个只允许授权人员停留的房间。设备：Fingerprint scanner、Fingerprint database、Access Control Software、Door、Motion detector、Horn、Panic button、Enable button、连接 Police Station 的电话线。

非正式规格（讲义原文三段）：

  1. 上电即启用。房间内的人任何时候可以按 panic 按钮呼叫警察（如遇抢劫）：通过电话线给警察发消息，不响警报。
  2. 系统启用时有人开门，必须在开门后 30 秒内扫描食指来解除系统。30 秒内无有效指纹 → 警报响 + 给警察发消息，消息包含安装时向警方登记的 8 位系统 ID。
  3. 系统未启用时，最后离开的人按 Enable 按钮，有 45 秒离开后系统启用。启用状态下运动传感器检测到从窗户进入 → 警报响 + 通知警察。

2.2 怎么写 ad hoc 模型

Ad hoc 图是临时性的图，用自然语言或随手画的框图把需求列全即可。Tutorial 3 建议按三类给每条需求打标签：

类别 问的是 Secure Room 里的例子
What 系统做什么 有人开门时要求扫指纹；panic 按钮报警
How 用什么手段做 通过电话线给警察发消息
How well 做到什么程度 开门后 30 秒内必须扫描；按 Enable 后 45 秒内离开

How well 那一类到了特征图里会变成约束（见 3.4），到了 use case 里会变成前置条件或失败条件。

三、Feature diagram

Feature：软件系统突出的、用户可见的方面、质量或特征。更严格的定义（Czarnecki & Eisenecker）：领域概念的一个属性，用于区分该概念的不同实例。

3.1 特征图符号

关系 含义 常见画法
Mandatory 子特征必须选 实心圆点
Optional 子特征可选可不选 空心圆点
Or 子特征中至少选一个 实心扇形
Alternative (xor) 子特征中恰好选一个 空心扇形
Cross-tree constraint 跨分支的依赖/互斥 requires / excludes 或逻辑式

3.4 把非功能指标写进特征图（W12 强调）

老师在复习课上专门提了一句：特征本身一般是功能需求，但重要的非功能指标也要放进特征图。有两种写法：

  1. 写在特征上：直接作为特征的属性或注释，例如 Fingerprint Identification {response ≤ 2 s}
  2. 写成约束：给某个特征挂一条约束，说明它的非功能要求

考场上的检查顺序：先保证特征树的层级和四种关系都对，然后补上跨树约束（requires/excludes），最后把场景里出现的数字（时间、次数、容量）挂到对应特征上。

3.5 Tutorial 3 的 E-Shop 例子

  • 根特征 E-Shop 标识一条软件产品线（SPL）
  • 实现 Catalogue、Payment、Security，以及可选的 Search
  • Security：High 或 Standard 二选一（xor）
  • Payment：Bank Transfer、Credit Card 或两者（or）
  • 跨树约束：包含 Credit Card 的系统必须采用 High security

可以把合法配置数一下：Payment 有 种，Security 2 种，Search 2 种，共 种；加上约束后，含 Credit Card 的 2 种 Payment 选项只能配 High： 种合法产品。

Feature model 是一条产品线所有产品的紧凑表示，常作为生成文档、schema、代码片段的输入。

四、功能需求 vs 非功能需求

功能需求（FR） 非功能需求（NFR）
回答 系统做什么（what） 系统做得多好（how well），对“怎么做”加约束
关注 系统功能 性能特征：可访问性、可靠性、延迟等

但对很多系统来说，两者并不总是可分的。
“Compute the optimal route for a data packet” 与 “Compute the optimal route for a data packet in 4 μsec” 可能是两个完全不同的系统——时间约束改变了算法和架构选择。

Agentic 软件的需求例子：

FR NFR
Agent shall check reported symptoms for emergency warning signs Low latency
根据自然语言生成内容 高准确率的 LLM 模型（NLP 与 CV）
与人对话 用户友好的人机交互（CHI）

五、Use case 模型

Use case 模型分两部分画：use case 总览图（overview diagram：有哪些 actor、哪些 use case、边界在哪）和 use case 规格（specification：每个关键 use case 的模板和场景）。复习课上老师说得很直白：总览图只能看出谁和系统交互，每一步具体做什么必须写在规格里。

5.1 概念框架

Use case：为了达成一个明确定义的目标而与系统进行的交互——这个目标对 actor 有价值。

  • Actor：有目标；与系统交互以达成一个或多个目标的实体（人或系统）
  • System under consideration：有职责支持 actor 的目标；也可能与其他系统交互
  • Use case 处于非正式（用户想要什么）与正式（工程师实现什么）之间的边界上
  • 作用：给出需求的上下文、促进达成一致、是一组可能的场景

UML 的 use case 图只是一个速记表示——重要（也是困难）的部分是把 use case 本身写清楚。讲义里的元模型多重性：Actor 1 — 0..* Use case 0..* — 1..* Other system。

5.2 Use case 总览图怎么画

组件规则（Tutorial 3）：

组件 规则
Actor 与系统交互的用户：可以是人、组织、外部系统；必须是产生或消费数据的外部对象；用名词命名；是业务中的角色（一个用户可扮演多个角色，如教授既是 instructor 又是 researcher）；actor 触发 use case；对系统有职责（输入）和期望（输出）
Use case 椭圆；系统功能（自动或手工过程）；动词 + 名词命名（Do Something）；每个 actor 必须连到某个 use case，但有些 use case 可以不连 actor（如被 include/extend 的子用例）；可被扩展
Communication link actor 与 use case 之间的实线，表示双方通过消息通信
System boundary 由需求文档定义，代表整个系统范围；大型系统（如 ERP）中每个模块（人事、工资、会计）可以各自是边界，整体边界包含所有模块

找 actor 的提问清单（Tutorial 4）：谁使用系统？谁安装、启动、维护、关闭？哪些其他系统使用本系统？谁从系统获取信息，谁向系统提供信息？有没有事情在预定时间自动发生？（有的话，时间/调度器也可以是 actor。）

找 use case 的提问清单（Tutorial 4）：

  • actor 想要系统提供哪些功能？
  • 系统是否存储信息？哪些 actor 会创建、读取、更新、删除（CRUD）这些信息？
  • 系统是否需要通知 actor 内部状态的变化？
  • 是否有系统必须知道的外部事件？由哪个 actor 告知？

例子：AI-Assisted Smart Shoe Store（Week 2 Tutorial）

场景：网购时很难选到合适的鞋。服务要做到：收集偏好 → 推荐鞋 → 解释每条推荐 → 支持比较和购买。AI 支持决策，顾客做最终选择。

Actor 目标 相关活动
Customer 找到合适的鞋 输入偏好、比较选项、选择并下单
Store Adviser AI 不够用时提供帮助 审核困难请求、支持顾客
Store Admin 保持服务准确 管理商品、库存、已批准信息
Payment / Delivery Service 完成外部操作 处理支付、确认配送

Actor ≠ 人名。Actor = 相对于系统所扮演的角色。 Actor 在系统外部，与系统交互以达成目标。

系统边界：Inside 是收集偏好、生成推荐、解释与比较、管理商品信息、创建订单请求；Outside 是 Customer、Store Adviser、Store Admin、Payment/Delivery。边界规则：AI 可以推荐和解释，但不做最终购买决定。

flowchart LR
    C([Customer])
    SA([Store Admin])
    PS([Payment Service])
    subgraph S [AI-Assisted Smart Shoe Store]
        U1((Enter Preferences))
        U2((View Recommendations))
        U3((View Explanations))
        U4((Compare Products))
        U5((Add Shoe to Cart))
        U6((Manage Products & Stock))
        U7((Process Payment))
    end
    C --- U1
    C --- U2
    C --- U3
    C --- U4
    C --- U5
    SA --- U6
    PS --- U7

每条线表示一个 actor 参与一个系统目标。

画总览图的步骤：

  1. 读场景，圈出所有“谁”，区分系统内部的功能和外部的角色/服务
  2. 外部服务（支付、配送、第三方 API）也是 actor
  3. 画系统边界框，框里只放目标（动词 + 名词），不放 UI 步骤
  4. 加 «include» / «extend» / 泛化（箭头方向见 5.4）
  5. 写清楚 AI 的决策边界（推荐 vs 决定）

常见毛病（Tutorial 4）：从 actor 的视角组织图，先画最高层再细化，只管 what 不管 how；边界要清晰；use case 不要太多、粒度要一致；actor 名称前后一致；不要把一个 use case 机械地拆成一串步骤 use case（那是功能分解，不是 use case）；纯 NFR、算法细节不适合放进 use case 图。

5.3 Use case 规格：Cockburn 方法

  1. Use case 由 actor 的目标驱动并围绕它定义
  2. Use case 以 actor 的一个动作开始（trigger）
  3. Use case 总是以明确结果结束：目标达成或未达成
    • Success scenarios（通常一个 main success scenario）
    • Failure scenarios（complications）
  4. 每一步都可能成功或失败；导致失败的条件作为对应失败场景的开头；失败场景从失败点分叉
flowchart TD
    P[Precondition] --> S1[STEP 1]
    S1 -- success --> S2[STEP 2]
    S1 -- failure cond 1 --> F11[STEP F1.1] --> F12[STEP F1.2] --> G2[Goal achieved: SUCCESS]
    S2 -- success --> S3[STEP 3] --> G1[Goal achieved: SUCCESS]
    S2 -- failure cond 2 --> F21[STEP F2.1] --> X[Goal not achieved: FAILURE]

注意：失败分支不一定以失败告终——恢复后也可能达成目标。

模板（ATM 例子）：

Name Goal Level Precondition Success Failure Trigger
Withdraw cash from ATM Obtain cash User（System 层面） User has ATM-readable card Cash dispensed to user Cash not dispensed despite valid request Insertion of card in ATM

Main scenario：1. 登录 ATM → 2. 选择取款 → 3. 指定金额 → 4. ATM 出钞 → 5. 登出

Extension scenario（当某一步失败条件成立时启动）：在第 4 步 {Insufficient cash on hand} → 1. 通知用户 → 2. 用户登出。

Tutorial 版模板：

Name Goal Level Precondition Success Condition Failure Condition Trigger
User Login User successfully logs in User goal level User is registered 登录并跳转主页 密码错误时显示错误信息 用户点击登录按钮

更完整的描述一般还包括（Tutorial 4）：名称、简述、优先级、actors、前置条件、基本事件流、其他事件流、异常事件流、后置条件。

事件流 含义
Basic event flow 通常、预期的路径（= main success scenario）
Other event flows 因其他因素走的其他路径
Exception flow 异常情况和替代分支（= extensions / failure scenarios）

5.4 «extend»、«include»、泛化

关系 含义 箭头方向 例子
«extend» 给 use case 加一个可选步骤，且不影响原 use case 的规格；需要 extension point 从扩展用例指向基用例（虚线箭头） Update Branch Balance --«extend»--> Withdraw Cash，扩展点 X1（第 4 步之后），条件 [service successful]
«include» 场景中某一步本身是一个子 use case（有自己的目标、actor）；主用例依赖子用例的功能 从基用例指向被包含用例（虚线箭头） Withdraw Cash --«include»--> Login（Login：询问 PIN → 输入 PIN → 验证 PIN …）
Generalization 父子关系，子用例是父用例的增强 实线 + 空心三角指向父用例 Pay by Card → Pay 
flowchart LR
    W((Withdraw Cash<br/>ext. point: X1))
    L((Login))
    U((Update Branch Balance))
    W -. "«include»" .-> L
    U -. "«extend» [service successful]" .-> W

讲义特别提醒：“Note the direction of the arrow!” —— extend 指向基用例，include 指向被包含用例。 这是考试和作业最常见的错误。

记忆：include 是“我必须用到它”（基用例知道子用例）；extend 是“它可以插进我”（基用例不知道扩展的存在，只暴露扩展点）。

保持简单：

  • Use case 应该让利益相关者容易理解，以便他们能推理
  • 避免实现细节、保持非正式（不是所有利益相关者都是技术专家）
  • 用易读的文本形式

5.5 例子一：Patient Consults AI Health Agent

字段 内容
Goal 患者得到症状的解决方案
Level User-goal
Primary Actor Patient
Preconditions 患者可访问 AI Health Agent；Agent 可访问诊所排期系统
Success postcondition 患者获得治疗建议（轻症）或确认的医生预约（严重/不确定）
Failure postcondition Agent 未能给出方案
Trigger 用户启动 AI Agent

Main success scenario：1 发起对话 → 2 Agent 问候并询问症状 → 3 描述症状 → 4 Agent 追问（严重度、持续时间、病史、过敏）→ 5 患者回答 → 6 Agent 对照医学指南分析 → 7 判断 (a) 轻症可居家/自我用药，或 (b) 需专业评估 → 8 若 7a：给出治疗建议 → 9 若 7b：预约医生 → 10 结束对话。

Extensions：

  • 5.a {描述不清或不完整} → 反复澄清直到信息足够
  • 7.c {症状危急} → 立即呼叫急救，而不是预约
  • 8.a {患者不理解建议} → 换种说法并提供教育资源

Nested use case（第 9 步）：查询医生空闲时段 → 患者确认时间 → 预约并提供确认信息。

5.6 面向 agentic 软件的 use case 模型

对 agentic 软件，use case 模型应该强调“有界自治（bounded autonomy）”和“可观察的结果”——而不只是固定的交互序列。

要素 写法
Actor goal 写业务结果，如 “deliver an evidence-backed weekly brief”，而不是 “run the research agent”
Authority 明确 agent 可以读、写、发送、购买或修改什么。把能力（capability）和权限（permission）分开
Success conditions 定义可观察的成功证据，而不是精确的推理路径
Failure and uncertainty 把缺数据、证据冲突、工具不可用、低置信度结果建模为正常分支
Human checkpoints 标出 agent 何时必须询问、获得批准、移交或停止

5.7 例子二：Assess and coordinate patient care（有界自治版）

字段 内容
Goal 安全的下一步被及时准备好
Level User goal
Primary actor Patient
Preconditions 患者身份与同意已确认；已批准的指南与排期工具可用
Success postcondition 经临床医生批准的指导已发送；记录已更新
Failure postcondition 未发送任何建议；已向临床医生报警并说明原因
Trigger 患者提交新的健康咨询

Main success scenario（bounded autonomy）：

  1. 患者确认身份、同意和当前症状
  2. Intake agent 检查急症警示信号
  3. Agent 结构化症状、病史和上下文
  4. Evidence agent 检索已批准的临床指南
  5. Care agent 起草分诊摘要和下一步
  6. Checker 验证依据（grounding）、隐私和安全约束
  7. Agent 准备回复（但不发送）
  8. 临床医生审核、修改并批准
  9. Agent 发送指导并更新健康记录

显式建模失败与移交：

  • Emergency red flag → 停止自动化，立即通知医生
  • 5.a {指南冲突} → 询问医生
  • Clinical context missing → 请求一次，然后移交
  • 7.a {未获批准} → 保存草稿，不发送建议

对比 5.5 与 5.7：前者 agent 直接给建议、直接预约；后者 agent 只起草，人类审批后才发送，失败后置条件是“什么都没发”。这就是“Requirements describe the outcome; permitted decision-making is explicit”的具体体现，也是项目 Stage 1 写 use case 时应该采用的写法。

六、解题模板：给定场景画需求模型

  1. Ad hoc：先自由列出所有需求，按 What / How / How well 标注，力求完整
  2. Feature model：把 What 类需求归成能力树，标 mandatory/optional/or/xor；特征间的依赖/互斥写成跨树约束，How well 里的数字挂到对应特征上
  3. Use case：从每个 actor 的目标出发画 use case 图；为核心 use case 写模板 + main scenario + extensions；agentic 功能要写 authority 与 human checkpoint
  4. 一致性检查：每个 use case 能映射回某个 feature；每个 mandatory feature 至少被一个 use case 覆盖

七、考点速记 / 易错点

  1. 三种模型的顺序：ad hoc（完整但不正式）→ feature diagram（定范围）→ use case（给关键特征写交互细节）。
  2. 特征图四种关系：mandatory（实心圆）、optional（空心圆）、or（实心扇形，≥1）、xor（空心扇形，=1）+ 跨树约束 requires/excludes。
  3. 非功能指标进特征图：写在特征上，或写成挂在特征上的约束。
  4. FR vs NFR：what vs how well；并非总可分（4 μs 例子）。
  5. Use case 总览图：actor 是外部角色（人、组织、外部系统、时间），用名词；use case 用“动词 + 名词”；画系统边界；每个 actor 至少连一个 use case。
  6. Use case 规格：Name、Goal、Level、Precondition、Success、Failure、Trigger + main scenario + extensions；失败条件写在分叉那一步的编号下（如 4.a {Insufficient cash}）。
  7. 箭头方向：«extend» 指向基用例；«include» 指向被包含用例；泛化指向父。
  8. Agentic use case 五要素：业务结果目标、权限（能力 ≠ 许可）、可观察成功证据、失败与不确定性作为正常分支、人工检查点。
  9. 易错：不要把 UI 步骤画成 use case；agent 本身一般在系统内部，不画成外部 actor（除非是外部系统）；外部支付/配送服务要画成 actor。
