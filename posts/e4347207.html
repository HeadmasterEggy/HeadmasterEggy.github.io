Context 与 Loop：从上下文治理到可验证的 Agent 闭环

Posted on 2026-10-22 In AI Agent Word count in article: 7.9k Reading time ≈ 29 mins.
详读张立行关于 Context 与 Loop 的实践记录：梳理上下文分层、主脑与执行器、独立 Advisor、经验固化、门禁自检和并发瓶颈，并整理可落地的任务卡与复盘方法。

很多人开始使用 Coding Agent 时，最关心的是模型能不能把代码写出来。使用一段时间后，问题往往变成：为什么每次都要解释同样的约束？为什么修复绕了几轮还没有进展？为什么工具报告成功，交付结果却仍然有问题？

张立行在《吃一堑，长一智：Agent 时代的两个关键词 Context 与 Loop》中，把这些问题放进了同一个工程框架：Context 影响当前任务如何行动，Loop 决定一次行动能否改善后续任务。

本文依据作者 2026 年 10 月 4 日发布的原始长文和对应 X 帖子整理，阅读与核对日期为 2026 年 10 月 22 日。下文先归纳原文的论证，再补充自己的工程解释、示例和操作模板；标注为“本文建议”的部分，是基于原文延伸的方法。

原文涉及的通过率、token、咨询次数和并发规模，都是作者对自己系统的记录，本文没有独立复现实验。它们适合帮助理解一个工作流的演化过程，不能直接当作模型排行榜，也不能据此推算其他团队的收益。

一、先看全局：上下文和反馈怎样形成循环

可以把一次 Agent 工作理解为四个相互连接的环节：

这里有两个不同的问题。

第一个问题是“现在知道什么”。 任务目标、仓库约束、可用工具、历史结论和验收标准，决定 Agent 如何理解问题。信息缺失会让它猜，信息过量又会让关键约束被淹没。

第二个问题是“结果改变了什么”。 如果这次失败只是留下了一段聊天记录，下一次仍然可能重演。只有结果能推动工具、流程或约束发生改变，经验才进入了系统。

本文用一个简单例子说明：Agent 在错误目录里构建失败后，提醒它“注意工作目录”可以解决当次任务；把项目入口、环境检查和构建命令收进一个稳定脚本，则能降低后续所有任务重复踩坑的概率。前者改善当前上下文，后者把反馈固化为可复用能力。

这也解释了为什么原文同时讨论提示词、Skills、执行器、代码审查、CI 和机器资源：它们共同决定一次任务从输入到交付的完整路径。

二、为什么代码生成变快后，人还是很忙

原文认为，编程比较早被 Agent 改变，与它的经济价值、丰富的训练资料，以及较多可执行的验证手段有关。但写代码的速度提升，不会自动让整个交付过程同比提速。

如果仍然需要人逐条拆任务、搬运上下文、观察进度、判断是否跑偏、检查结果、反复启动下一轮，那么代码生成越快，人工调度反而越容易成为瓶颈。

作者用自己的高强度使用记录说明这种变化：即使总 token 消耗很大，也可能主要是在维持人工盯守；后续工作流的价值，在于减少操作者必须持续介入的环节。token 数量和人类时间是两项不同的指标，原文的 token 统计还包含缓存读取，不能直接等同于新生成的内容量或费用。

为保留原文的量感，下面列出几项作者自述。它们彼此不是同口径的实验结果。

原文记录 数字 阅读边界
agent-config 的演进规模 约 1.6 万次提交、1800 多个 issue、近 2000 个合并 PR 工作记录规模，不等于相同数量的有效能力提升
当前每日 token 处理量 约 20 亿至 30 亿，包含缓存读取 不能直接换算产出、费用或净节省时间
执行器长期任务通过率 作者记录约 88% 至 93% 任务不完全同质，不是严格等难度模型基准
原生框架与 Pi 的一次配对比较 12 个任务中结果为 6 比 6 小样本，不能据此认定框架普遍等价

这个方向与 Anthropic 的 AI 原生软件交付文章相呼应：当代码生产提速，计划、审查、测试和发布也要一起调整。这里只能说明问题意识相近，不能把某个团队的具体效率数字推广到所有项目。

本文建议观察三个结果，而不只统计 Agent 写了多少代码：

  • 一项任务需要人介入多少次，每次介入是补事实、做判断，还是修补工具流程。
  • 从开始到获得可复核结果需要多久，其中有多少时间在等待、重复或返工。
  • 同类失败再次出现时，系统是否已有明确的检测与处理办法。

三、Context 治理：给不同信息安排不同位置

“给模型更多上下文”是一条不完整的建议。真正需要回答的是：哪些信息必须常驻，哪些按任务加载，哪些应该查询，哪些应该过期。

原文涉及的上下文来源，可以整理成下面这张表。用途划分是本文为便于实践所做的归纳。

信息来源 适合承载的内容 需要警惕的问题
全局规则 跨项目稳定偏好、权限边界、通用交付要求 把某个仓库的临时规定扩散到所有任务
仓库规则 项目结构、正式命令、长期不变量 把每次事故的完整经过都堆进去
Skills 可复用的专项流程与必要参考材料 没用到的流程也在启动时全部进入上下文
工具及接口描述 当前可调用能力、参数和返回结构 描述膨胀、重复工具、无关输出
记忆与历史记录 已验证的偏好、决策及带时间的事实 旧事实失效、不同客户端保存出互相冲突的版本
当前任务材料 目标、证据、范围、验收条件 只给结论，省略复现方法和约束

1. 上下文是一项预算

作者给主脑和执行器设置了不同的提示材料体积预算，并把预算检查自动化。值得学习的是“预算被实际执行”，而不是照搬某个 KB 数值。

文件大小、字符数和模型 token 数并不等价；语言、编码和分词器都会影响换算。预算也不能只看根目录规则：隐式加载的 Skills、工具说明和重复注入，同样会占用注意力。

Anthropic 的上下文工程文章把上下文视为需要持续筛选的有限资源，并讨论了上下文增长带来的表现下降。因此，审计的对象应当是模型本次实际收到的输入，而不只是某几个文件的长度。

本文建议定期检查：同一条规定是否出现了三次；某个长流程能否改成按需读取；历史结论是否还适用；工具输出是否保留了决定下一步的证据。

2. 先留下足够的行为证据

原文把保留行为轨迹放在地基的位置。没有任务输入、工具调用与结果记录，复盘就只能依靠操作者记忆；换模型、改规则之后，也难以比较行为究竟变在哪里。

本文建议至少能关联任务、代码版本、关键工具结果和最终验收证据。完整日志可能包含私密信息或凭证，应按内容设置访问范围和保留时间；不要把“版本管理”理解为把所有原始日志公开提交。不同工具的默认保留策略也需要在当前版本中核对。

3. 规则要能追溯，也要能删除

原文强调把规则、工具和 Skills 纳入版本管理。这样，一次行为变化才有机会追溯到具体输入变化，而不是凭印象争论“模型最近变笨了”。

另一半同样重要：模型和工具升级后，曾经必要的补丁可能已经失效。规则只有增长、没有删除机制，就会把旧模型的缺点变成新工作流的负担。

原文也没有把厂商的提示词建议当成无条件通用的答案。同一套流程如果使用不同能力、不同成本或不同回退路径的模型，仍然需要在自己的任务上检验约束是否有用。

本文建议给临时规则保留来源、适用条件和复查时机。删除一条旧规则前，用曾经触发它的案例做一次回归；回归稳定通过，才有证据减少负担。

4. AGENTS、记忆和事故记录应各司其职

稳定的项目规则适合写进仓库说明；容易变化的事实适合带时间与来源保存；具体失败则先进入可追踪的问题记录。

例如，“发布前必须执行项目检查”是长期要求；“当前部署停在某个提交”是需要刷新验证的状态；“某次依赖安装失败的完整输出”是诊断证据。把三者混在一个长期提示词里，会让状态越来越难维护。

记忆还需要考虑跨客户端的一致性。一个事实如果在不同工具里各存一份，修正其中一份并不会自动修正其他副本。原文提到共享文本和索引的做法；本文更关注其原则：明确权威来源，让变化有入口，让旧结论有失效办法。

5. Skills 和工具也有上下文成本

原文倾向于把外部 Skill 的有用经验吸收到自己的流程中，而不是不加选择地全局安装。对所有项目都高频适用的内容才值得常驻，项目专用材料应尽量留在项目内。

工具选择也类似。CLI 如果已经能准确完成任务，就值得与额外的工具接口比较：新增能力是什么，描述和输出的成本是什么，权限和认证是否更合适。原文偏好的 CLI 路线属于具体环境中的取舍，不能推导成“MCP 没有价值”。

本文建议用一次真实任务检查实际加载结果。目录里看起来只有少量规则，最终输入却可能包含重复说明、整套 Skills 和与任务无关的长输出。

四、主脑与执行器：分工首先体现在输入上

原文把规划、判断和验收更多交给主脑，把范围清楚的实现工作交给执行器。这个分工能否成立，关键在任务边界和输入是否清楚。

如果执行器同时读到了“你要继续调度其他执行器”的主脑规则，它就可能把一个局部任务再拆成新的组织层级。原文记录过这种递归委派造成的长时间空转。

因此，公共规范可以共享，角色职责必须单独表达。一个执行器通常需要知道：

  • 这次要解决的具体问题及已有证据。
  • 能修改的范围，以及必须保留的行为。
  • 如何运行、如何验证、如何汇报。
  • 何时应当停止尝试并返回阻塞原因。

模型和 Harness 应一起评估

Harness 可以理解为围绕模型运行的工具调用、会话管理和执行框架。原文讨论的 Pi 属于这类框架，它本身不是一个模型。

同一个模型换框架后表现不同，原因可能来自初始任务没有正确送达、规则重复、工具输出结构不同，或者加载了过量材料。原文的对照案例说明：修正输入与加载方式之后，先前的结果可能发生明显变化。

这意味着“哪个模型更强”与“哪个系统更适合这类任务”是两个问题。任务已经明确时，可以测试较快、较便宜的执行器；问题还需要判断范围、识别错误假设时，更强的推理和更清楚的上下文可能更重要。

原文包含小规模配对实验和较长期的本地通过率记录，但任务分布、样本量与运行条件限制了结论。本文不据此给具体模型排序。可迁移的做法是：用自己的失败案例，在任务、验收与预算一致的条件下比较完整系统。

五、Advisor：让独立判断真正进入流程

Agent 连续修复失败时，常见反应是继续补充解释，让它再试一次。但它可能已经围绕一个错误假设建立了整套推理，新增信息也被吸收到原来的解释里。

原文引入了只读 Advisor：让一个独立视角阅读必要材料，挑战当前判断，而不是直接接着改代码。

这里有两个作用需要分开看：更强的模型可能更擅长发现问题；新会话则能减少既有叙事的影响。换模型却完整复制所有历史，不一定获得真正独立的判断。

给事实，也暴露自己的偏见

作者提出的一个有意思的做法，是把咨询材料中的事实、自己的判断，以及自己希望得到的答案分别列出。这样 Advisor 更容易看到哪些部分需要挑战。

用外部条件触发咨询

如果完全依赖执行者自评“是否需要帮助”，卡住的流程可能一直不升级。原文倾向于用重试次数、新增失败轮次或审计结果等外部条件触发咨询。

本文建议根据任务风险设置明确预算，例如“同一失败在两次修复后仍然复现，就停止继续改动并提交证据”。这里的次数只是示例，不是所有项目的统一门槛。

Advisor 也需要接受验证。原文记录过 Advisor 的判断被实际复现推翻的情况。独立意见的价值，在于提出更好的假设和实验；最终仍然要回到代码、环境和可观察结果。

原文中较高的否定或部分否定比例，还有明显的样本选择因素：被拿去咨询的本来就多是困难任务。不能据此断言主脑在普通任务上同样经常出错。

六、Loop：把一次事故转成下次少做一件事

原文的配置与调度系统，是在多个项目的实际失败中逐步长出来的。复盘的重点不只是记住“发生了什么”，而是决定“系统应该因此改变什么”。

下面按机制归纳几类原文案例；每行末尾是本文总结的改进方向。

失败形态 为什么一句提醒不够 可固化的方向
新工作区缺少所需环境，运行路径出错 每次创建工作区都要重新发现条件 统一初始化入口，主动检查必要配置
执行器继续调度执行器，任务越拆越远 错误职责已经写进角色输入 从执行器模板中移除调度职责
压缩后的命令输出被误读为成功 关键信号在信息处理时丢失 保留退出状态与关键证据，核对远端结果
查询状态却返回大量无关信息 不必要输出反复占用上下文 提供最小查询接口与输出上限
问题代码修好了，同类问题又出现 修复只覆盖了一个实例 在最靠近失效点的位置增加约束或回归验证

这张表背后的判断是：能够交给程序稳定执行的约束，应当尽量变成程序行为。

例如，某目录禁止写入，单靠提示词需要模型每次都记住；权限边界和路径检查则能在执行时提供直接约束。格式要求可以由格式化工具执行；已知回归可以由针对性检查验证。

Anthropic 的交付文章也明确区分了 Skill 的指导作用和 Hook 的确定性执行作用。不过，Hook 是否能覆盖具体行为，仍取决于安装方式、触发范围和失败处理，不能仅凭“配置了一个 Hook”就认为风险已经消失。

复盘什么时候才算闭环

本文建议为一项改进保留四件东西：

  1. 原始失败如何复现，以及造成了什么影响。
  2. 选择了哪一层改进，为什么它能覆盖失效机制。
  3. 用什么案例验证改进有效，包括改进前应当失败的案例。
  4. 后续如何观察它是否仍在工作，何时重新评估成本。

原文中问题数量下降，是系统演进的一个观察值。仅凭绝对数量还不能证明质量提升：任务量、任务难度、发现和记录问题的方式都可能变化。更有用的追踪还包括同类问题复发率、人工介入时间和验证覆盖情况。

优化工具也要接受复盘

原文还讨论了输出压缩工具：节省输入量可能很可观，但如果关键上下文被裁掉，后续修改就可能更容易出错。

这里应评估的是净效果。省下的 token、增加的返工、丢失的证据和维护成本，需要放在同一张账上。这个案例不能直接证明某个工具对其他环境无用，也不意味着应当未经验证就更改现有工具链。

七、验证体系为什么也会骗人

这是原文最值得反复读的一部分。流程显示绿色，只能说明某些条件被满足；它是否检查了真正关心的行为，需要另外证明。

原文记录的异常包括：某种 PR 状态下模型审查被跳过，却被理解为已经通过；用于确认审查器工作的探测任务持续执行，但认证问题使真正的审查没有发生；多个仓库的状态看似正常，实际需要的审查能力并未启用。

这些现象揭示了几个不同层次：

链路中的任意前一步成功，都不能替代后面步骤的证明。

低成本检查优先，判断型检查补足

原文把验证放在成本梯度上考虑：编译、类型检查、静态检查和自动化测试，通常适合尽早执行；模型审查、界面截图与人工判断用于补充难以机械表达的部分。

具体顺序仍然取决于项目：有些构建非常昂贵，有些行为测试很便宜；前端“功能可用”与“视觉效果正确”也需要不同证据。选择语言和框架时，可自动获得的反馈能力同样是一项工程因素，但还要考虑生态和资源消耗。

本文建议为每项检查写出一句话：它能发现什么，发现不了什么。 这样就不容易把“测试全绿”误读为“产品的全部要求已经满足”。

用已知失败案例检验门禁

下面是本文延伸的实践示例：如果一个门禁声称能拦截错误，就给它一个受控的、已知应当失败的输入，观察它是否真正变红。

要验证的能力 受控输入示例 应观察的结果
自动化测试有效执行 临时引入会被目标测试覆盖的错误 目标测试失败，并使检查失败
审查器读取了代码 在隔离分支放置明确违反审查目标的变更 能定位问题，而非只返回通用总结
必需检查不能被跳过 使用预先约定的状态或条件触发跳过 状态明确显示未完成，并阻止交付
发布结果正确 核对目标版本或页面的可识别内容 观察到预期版本，而非只看到推送成功

这些实验应在隔离环境中进行，保留证据后清理。不要为了测试监控而把故意制造的错误发布到真实用户环境。

对于模型审查，单次漏报与整个审查链路失效也要区分：前者涉及能力和稳定性，后者涉及是否真正执行。两者需要不同的修复。

八、压缩与重开会话：保留证据，丢掉无效推理

原文讨论上下文腐化时，强调过长历史可能使 Agent 越来越难以摆脱早期判断。它提到的具体使用感受属于作者环境，不能当作所有模型在某个窗口比例上的统一阈值。

重新开始一段会话时，最重要的是整理交接材料，而不是简单把旧历史再复制一次。

本文建议保留：任务目标、当前代码状态、已经复现的现象、有效与无效的实验、尚未解决的问题，以及每项结论对应的证据。已经被推翻的解释要明确标记，不要让它重新混入“事实”。

例如：

会话重开和文件回退是两件事。清理推理上下文时，仍然要保存真实工作区状态，避免把无效推理与有价值的代码一起丢掉。关于压缩机制，可以继续阅读 从零开始理解上下文压缩：Pi 如何继续长会话。

九、并发规模扩大后，瓶颈会转移

当人工不再逐项盯守，系统可能开始受限于 CPU、内存、磁盘、网络和 CI 队列。原文的大规模执行器与多机器案例，说明的是这种瓶颈迁移，不构成某种硬件配置建议。

本文建议先看任务结构，再增加并发：

  • 哪些任务真正独立，哪些会争用同一个工作区或修改同一文件。
  • 哪些阶段占计算，哪些阶段等待网络，哪些阶段等待人工判断。
  • 各类任务是否有单独的队列、限流、超时和失败恢复。
  • 同一依赖能否缓存，验证是否重复执行了没有变化的昂贵步骤。

多启动一个 Agent，既增加执行能力，也增加调度、上下文和验收成本。如果没有清楚的工作边界与验证，并发可能只会更快地产生需要人处理的结果。

操作系统和运行环境也要围绕实际工作选择。原文对纯代码任务与图形界面、移动端任务做了不同取舍；本文更看重环境是否可复现、权限是否清楚，以及目标平台能否被实际验证。

十、从个人技巧到组织工作流

文章最后把讨论延伸到 Agent 开发环境和软件交付生命周期。相关概念也可以对照 Cloudflare 关于 Agent Development Lifecycle 的文章阅读。

对本文而言，一个组织是否适合 Agent 持续工作，可以沿着三个问题检查：

信息能否读取？ 需求、仓库、环境和历史决策是否可访问，来源是否明确，状态是否及时更新。

行动能否发生？ Agent 是否有与职责匹配的工具和权限，执行动作是否可追踪，失败是否可恢复。

结果能否回流？ 验收、用户反馈和运行故障是否进入后续计划，能否推动具体约束与流程改变。

只有“能读文档”，容易停在问答；只有“能操作工具”，容易形成无人验收的动作流。读取、执行和反馈连接起来，才可能持续承担交付。

人仍然需要承担目标选择、价值权衡、产品判断，以及需要明确授权的重大决策。减少机械搬运和重复检查，可以让这些判断获得更多时间。

十一、如何从自己的项目开始

下面是一条本文整理的渐进路线，适合已有 Agent 使用经验、但仍然觉得需要频繁盯守的项目。

第一步：只选一种重复发生的任务

选一个有明确输入和结果的场景，例如修复已复现的回归、更新一类文档，或者完成标准化依赖维护。先记录实际人工介入点，避免同时改造所有流程。

第二步：检查真实输入

确认任务首次进入执行器时是否完整，角色规则是否混杂，是否加载了无关 Skills，工具输出是否能支撑下一步判断。先修材料传递问题，再讨论换模型。

第三步：写清验收与升级条件

把“做完了”表达为可观察结果。为连续失败设置处理办法：停止修改、整理证据、请求独立判断，或者返回需要人决策的范围。

第四步：把复发问题固化到合适层

能通过初始化脚本解决，就不要每次口头解释；能通过机械约束拦截，就不要只依靠模型记忆。只有需要判断的内容，才保留为规则或咨询流程。

第五步：检验闭环是否真的工作

用已知失败案例检验检测能力，用远端或用户可见结果确认交付，用后续重复任务检验改进能否持续。没有回到实际结果的复盘，仍然只是文档。

在这一过程中，可以继续参考 我的 Vibe Coding 工作流：从 session log 到 skill 迭代、AI 开发工作流：轻量约束、端到端测试与人工审查，把任务记录、专项流程和验收证据连接起来。

十二、阅读这篇文章时，哪些结论应当保留边界

原文是一份密集的实践记录。最容易被过度推广的，是具体模型胜负、token 规模、成功率和设备数量。它们依赖任务分布、采样方式、上下文配置与统计口径；尤其是缓存读取量、任务完成量和真实经济成本，不能互相替代。

相比之下，更容易迁移的，是它提出的几类工程问题：

  • 模型实际看到了哪些材料，是否准确、必要且及时。
  • 执行角色是否清楚，任务是否有可独立验收的边界。
  • 失败后是否允许另一种判断进入流程。
  • 经验是否改变了系统行为，而不仅是增加了一条提醒。
  • 验证是否被证明有效，跳过和失败是否被正确表达。
  • 并发带来的收益，是否大于调度、资源与验收成本。

我认为这篇文章最值得带走的，是一种可以持续追问的工作方式：当前任务需要什么上下文；这次结果又应该让下一次发生什么变化。 两个问题都能得到具体答案时，Agent 才更有机会越用越省心。
