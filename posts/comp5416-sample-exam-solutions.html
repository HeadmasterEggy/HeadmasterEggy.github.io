Part 1：样卷逐题解析

Question 1 分组交换 vs 电路交换（24 分）

Original question (English) · Consider the two scenarios below:

  1. A circuit-switching scenario in which users, each requiring a bandwidth of 20 Mbps, must share a link of capacity 150 Mbps.
  2. A packet-switching scenario with users sharing a 150 Mbps link, where each user again requires 20 Mbps when transmitting, but only needs to transmit 20 percent of the time.

先把整道题的模型讲清楚，7 个小题都用它：

  • 电路交换：每个用户一上来就预留 20 Mbps，不管用不用，所以能接多少人只看「链路容量 ÷ 每人带宽」。
  • 分组交换：不预留，谁有数据谁发。每个用户独立地有 的概率在发、 的概率空闲。

Q1.1 电路交换最多支持几个用户 → 7

Original question (English) · [2 pts] When circuit switching is used, what is the maximum number of users that can be supported?

  • 1
  • 7
  • 10
  • 100
  • ，人数只能是整数，向下取整 = 7。第 8 个人要 160 Mbps，超了。
  • 10 和 100 是分组交换才能做到的量级；1 明显太少。

English answer (Official): 7 — When circuit switching is used, at most 7 users can be supported. This is because each circuit-switched user must be allocated its 20 Mbps bandwidth, and there is 150 Mbps of link capacity that can be allocated.

Q1.2 13 个用户能不能用电路交换支持 → No

Original question (English) · [3 pts] Suppose packet switching is used. If there are 13 packet-switching users, can this many users be supported under circuit-switching?

  • Yes
  • No
  • 电路交换要给每人都预留： Mbps Mbps，不行。
  • 题干前半句「Suppose packet switching is used」是干扰：问的是换成电路交换还行不行。

English answer (Official): No — Under circuit switching, the 13 users would each need to be allocated 20 Mbps, for an aggregate of 260 Mbps - more than the 150 Mbps of link capacity available.

Question 2 哪个协议有队头阻塞 → TCP（5 分）

Original question (English) · [5 pts] Which of the following protocol is vulnerable to head-of-line blocking?

  • UDP
  • TCP
  • QUIC
  • HTTP

队头阻塞（head-of-line blocking, HOL）：排在队伍前面的东西卡住了，后面所有东西都得等，即使后面的东西本身已经准备好了。

  • TCP ✔：TCP 只提供一条按序交付的字节流。只要中间丢了一个段，接收方后面收到的所有字节（哪怕属于另一个 HTTP 请求）都得留在缓冲区里等这个段重传，不能交给应用。HTTP/2 把多个请求复用到同一条 TCP 连接上，正好把这个问题放大。
  • QUIC ✘：QUIC 跑在 UDP 上，每个 stream 单独做可靠传输。一个 stream 丢包只卡它自己，其他 stream 照常交付。W12 讲 QUIC 时说它的卖点之一就是解决 TCP 的 HOL。
  • UDP ✘：不保证按序、不重传，收到什么交什么，没有「等前面」这回事。
  • HTTP：HTTP/1.1 在应用层确实也有一种 HOL（W03 讲过 FCFS 下小对象排在大对象后面），但这道题官方只认 TCP。考场上看到「协议层面、因丢包重传导致」的 HOL，答 TCP。

知识点：W12 QUIC 与 HOL 阻塞、W03 HTTP/2 分帧

English answer (Official): TCP

Question 3 迭代 DNS 查询（15 分）

Original question (English) · Assume that a user is trying to visit gaia.cs.umass.edu, but his browser doesn't know the IP address of the website. In this example, we examine the iterative DNS query.

样卷配图是课本那张经典图：请求主机 cse.nyu.edu，本地 DNS dns.nyu.edu，权威 DNS dns.umass.edu。8 步对应如下：

sequenceDiagram
    participant H as 请求主机 cse.nyu.edu
    participant L as 本地 DNS dns.nyu.edu
    participant R as 根 DNS
    participant T as TLD DNS (.edu)
    participant A as 权威 DNS dns.umass.edu
    H->>L: ① gaia.cs.umass.edu 的 IP？
    L->>R: ② 问根
    R-->>L: ③ 我不知道，去问 .edu 的 TLD 服务器
    L->>T: ④ 问 TLD
    T-->>L: ⑤ 我不知道，去问 dns.umass.edu
    L->>A: ⑥ 问权威服务器
    A-->>L: ⑦ A 记录：gaia.cs.umass.edu 的 IP
    L-->>H: ⑧ 把 IP 交给主机

迭代 vs 递归一句话区分：迭代查询里，被问到的服务器只回答「我不知道，你去问某某」，跑腿的始终是本地 DNS；递归查询里，每一级都替你往下问，再一路传回来，负担压在根和 TLD 身上。注意主机 → 本地 DNS 这一步（①⑧）本身总是递归的，迭代说的是本地 DNS 往上问的部分。

知识点：W04 DNS 层次结构与查询、W05 Tutorial DNS

Q3.1 第 1、2 步之间，本地 DNS 先去问谁 → DNS Root

Original question (English) · [3 pts] Between steps 1 and 2, where does the Local DNS server check first?

  • User
  • DNS Local
  • DNS Root
  • DNS TLD
  • DNS Authoritative
  • 本地 DNS 缓存里没有，就从层次结构最顶端根服务器开始问（第 ② 步）。
  • 不会直接问 TLD：它还不知道 .edu 的 TLD 服务器在哪，这正是根要告诉它的。

English answer (Official): DNS Root

Q3.2 第 2、3 步之间，根把请求指向谁 → DNS TLD

Original question (English) · [3 pts] Between steps 2 and 3, where does the root DNS forward the request to?

  • DNS Local
  • DNS Root
  • DNS TLD
  • DNS Authoritative
  • 根只认识顶级域，它回复「去问负责 .edu 的 TLD 服务器」。
  • 严格说在迭代查询里根并没有「转发」，而是把 TLD 服务器的名字/地址回给本地 DNS（第 ③ 步），由本地 DNS 自己去问。题目措辞不严谨，答 TLD 就对。

English answer (Official): DNS TLD server

Q3.3 第 4、5 步之间，TLD 没有我们要的 IP，回复指向谁 → DNS Authoritative

Original question (English) · [3 pts] Between steps 4 and 5, assuming the TLD DNS server doesn't have the IP we want, where does the response link?

  • DNS Local
  • DNS Root
  • DNS TLD
  • DNS Authoritative
  • TLD 知道 umass.edu 这个域归哪台权威服务器管（dns.umass.edu），在第 ⑤ 步把它告诉本地 DNS（实际上返回的是一条 NS 记录加上它的 IP）。

English answer (Official): DNS Authoritative server

Q3.4 第 6–8 步返回的是什么类型的记录 → A

Original question (English) · [3 pts] In steps 6-8, the response is sent back in the reverse direction until it reaches the user. What type of DNS record is returned?

  • A
  • CNAME
  • NS
  • MX

四种记录都要背（RR 格式 (name, value, type, ttl)）：

类型 name value 例子
A 主机名 IP 地址 gaia.cs.umass.edu → 128.119.245.12
NS 域名 该域权威 DNS 服务器的主机名 umass.edu → dns.umass.edu
CNAME 别名 规范名（真名） www.ibm.com → servereast.backup2.ibm.com
MX 域名 邮件服务器的名字 umass.edu → mail.umass.edu

用户要的是主机名 → IP，所以是 A 记录。NS 是第 ③⑤ 步返回的东西；CNAME 和 MX 跟这题无关。

English answer (Official): A

Q3.5 哪种查询算最佳实践 → Iterative

Original question (English) · [3 pts] Which type of query is considered best practice?

  • Iterative
  • Recursive
  • 递归查询让根和 TLD 替每个人跑完全程，全世界的流量都压在最上层；迭代查询里根和 TLD 只回一句「去问谁」就完事，负担在各自的本地 DNS 上。

English answer (Official): Iterative — Iterative is considered 'best practice' because it puts less strain on the Root and TLD DNS servers.

1. Internet 与分组交换（W1）

  • Internet 是「网络的网络」：端系统（hosts）在边缘，分组交换机（路由器、交换机）在中间，链路有光纤、铜线、无线、卫星；接入网 → 区域 ISP → 全球 ISP，ISP 之间在 IXP 互联，内容提供商（Google、Akamai）自己建网络靠近用户。
  • 存储转发：路由器要整个分组收完才能往下一条链路发。一跳的传输时延 ，例： Kbits、 Mbps → 0.1 ms。
  • 排队：到达速率暂时超过输出链路速率时分组排队，缓冲区满了就丢包。
  • 电路交换：端到端资源预留，性能有保证，但没用的时候也不能给别人（no sharing）。复用方式：
    • FDM：按频率切，每个通话一个窄频带，一直能发但速率低；
    • TDM：按时间切，每个通话周期性拿到时隙，时隙内用整条带宽。
  • 分组交换适合突发（bursty）数据：资源共享、无需建立连接；代价是可能拥塞、需要可靠传输和拥塞控制协议。样卷 Q1 就是这一页的定量版本。

知识点：W01 总结

2. 性能：四种时延与吞吐量（W2）

时延 含义 公式 / 量级
处理 查比特错误、决定输出链路 通常 < 微秒
排队 在输出链路前排队等发送 取决于拥塞程度
传输 把整个分组「推」上链路
传播 最后一个比特在链路上跑过去 ， m/s

最容易混的是传输时延和传播时延：传输时延只和分组长度、链路速率有关，与距离无关；传播时延只和距离、信号速度有关，与分组长度无关。

Caravan 车队类比（必会，答案 62 分钟）：10 辆车 = 10 bit 的分组，收费站 = 链路，每辆车 12 秒过站（传输），车速 100 km/h 跑 100 km（传播）。

  • 整队过第一个收费站： s = 2 min（传输时延）
  • 最后一辆车跑到第二个收费站：100 km ÷ 100 km/h = 1 h（传播时延）
  • 整队在第二个收费站前排好：2 + 60 = 62 min

吞吐量：端到端吞吐量由瓶颈链路决定。

  • 单条路径：。
  • 10 个连接公平共享主干链路 ：每个连接 。实际中常常是接入链路 或 是瓶颈。

知识点：W02 总结、Lab02 性能题

3. 应用层：HTTP（W3）

  • HTTP 是客户端/服务器模型，跑在 TCP 上。
  • 非持久 HTTP：一条 TCP 连接最多传一个对象，然后关闭；页面有多个对象就要开多条连接，每个对象至少 2 RTT（建连 1 RTT + 请求响应 1 RTT）+ 传输时间。
  • 持久 HTTP：多个对象可以在同一条 TCP 连接上传，省掉重复建连。
  • 状态码（在响应报文第一行）：
码 含义
200 OK 成功，对象在报文后面
301 Moved Permanently 对象永久搬家，新地址在 Location: 头里
400 Bad Request 服务器看不懂请求
404 Not Found 服务器上没有这个文档
505 HTTP Version Not Supported HTTP 版本不支持

知识点：W03 总结

4. DNS（W4）

  • 分布式、层次化数据库：根 → TLD（com、org、edu…）→ 权威服务器。查 www.amazon.com：问根拿到 com 服务器 → 问 com 拿到 amazon.com 服务器 → 问 amazon.com 拿到 IP。

5. 传输层：流水线协议 GBN vs SR（W5–W6）

Go-Back-N Selective Repeat
发送窗口 最多 N 个未确认分组 最多 N 个未确认分组
接收方 ACK 累积 ACK；有空洞时不确认后面的 每个分组单独 ACK
乱序分组 丢弃，重发最后按序收到的 ACK 缓存
计时器 只给最老的未确认分组一个 每个未确认分组一个
超时后 重传窗口内所有未确认分组 只重传超时的那一个

复习课的例子（N = 4，pkt2 丢失）：

  • GBN：接收方收到 pkt3、4、5 都丢掉，每次重发 ack1；pkt2 超时后发送方重发 pkt2、3、4、5 四个。
  • SR：接收方把 pkt3、4、5 缓存并分别回 ack3、4、5；pkt2 超时后只重发 pkt2；pkt2 到达后接收方一次交付 pkt2–5，回 ack2。
  • 复习课留的问题「ack2 到达后会怎样」：发送方窗口基序号直接滑到 6（因为 ack3、4、5 早就记录了），可以发新的分组 6–9。

W6 老师说过 TCP 拥塞控制的完整状态机不会单独考，但慢启动、拥塞避免、3 个重复 ACK 进快速恢复这些行为要懂。

知识点：W05 总结、W06 TCP

6. 多媒体：流媒体播放缓冲（W7–W8）

  • 服务器以恒定码率（CBR）发视频，但网络时延是变化的（抖动），到达客户端的时间参差不齐。
  • 客户端缓冲 + 播放时延：先攒一段再开始播，用来吸收网络时延和抖动。
  • 播放时延太小：某帧到播放时刻还没到 → 缓冲区下溢（buffer underflow），卡顿。
  • 加大播放时延 → 下溢更少；代价是用户等得更久才开始播。这是初始播放时延的取舍。

知识点：W08 多媒体

8. 移动性：蓝牙跳频（W11–W12）

复习课 Mobility 部分只放了一页：蓝牙信道跳频。

  • 蓝牙网络里的发送方在 79 个频道之间「跳」，每个时隙（625 μs）换一个频道；同一个 piconet 里所有设备都知道跳频图案。
  • 不同 piconet 用不同的跳频图案，所以可以在同一空间共存。
  • 为什么要跳：减小干扰。ISM 频段里干扰源很多，但如果干扰设备占着频道 ，跳频序列只是偶尔落到 ；在 上没收到的帧，下一个时隙换频道重传。

知识点：W11 Wi-Fi、蜂窝与移动性、W12 5G、移动性与 QUIC
