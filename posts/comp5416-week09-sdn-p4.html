第一部分：SDN —— 逻辑集中的控制平面

一、两个平面、两个时间尺度（讲义 p5）

数据平面（转发） 控制平面（路由）
范围 本地、每个路由器的功能 全网逻辑
做什么 把分组从输入端口移到输出端口 决定分组走的端到端路径
时间尺度 纳秒级，硬件实现 毫秒到秒级，软件实现
依赖 使用转发表（流表） 计算转发表

讲义类比：转发 = 开车穿过一个立交桥；路由 = 规划整趟行程。

二、两种构建控制平面的方式（讲义 p6）

传统：每路由器控制 SDN：逻辑集中控制
路由算法在哪跑 每个路由器里都跑 远程控制器
转发表怎么来 路由器之间交换路由消息，各自计算（OSPF、BGP） 控制器集中计算，通过南向 API 安装
交换机的职责 转发 + 计算 只转发

讲义的 KEY POINT：SDN 并没有去掉控制平面，而是把它搬出盒子、变成逻辑上集中的。 「逻辑集中」不等于「物理上一台机器」—— 控制器本身通常是分布式系统（见 ONOS、Orion）。

三、为什么要逻辑集中（讲义 p7）

动机 说明
管理更容易 避免逐台路由器的错误配置；流量调度更灵活
基于表的转发 流表 API 让你「编程」路由器而不是「配置」路由器
集中编程 集中计算一次再分发；没有分布式协议需要调试
开放实现 非专有的控制软件促进创新：「let 1000 flowers bloom」

讲义提示：今天「编程网络」有两层含义 —— 编程表项（SDN/OpenFlow），以及编程装这些表的流水线本身（P4）。

四、大型机 → PC 的类比（讲义 p8–9）

大型机时代 / 传统路由器 PC 时代 / SDN
结构 垂直集成：专用应用 + 专用 OS + 专用硬件 水平分层，开放接口
网络对应 专用功能 + 专用控制平面（路由器 OS） + 专用硬件 应用（路由、访问控制、负载均衡）+ 网络 OS（SDN 控制器） + 商用芯片交换机（merchant silicon）
后果 封闭、专有、创新慢、产业小 创新快、产业大

讲者的故事一句话：SKA-Low 买了商用芯片交换机，在上面写了自己的控制层 —— 正是右边那一栈。

五、流量工程：传统路由为什么做不到（讲义 p10–11）

拓扑：u, v, w, x, y, z；当前最短路 u→x→y→z，运营者想要 u→v→w→z。

运营者想做的事 传统路由下怎么办
让 u→z 走 uvwz 只能调链路权重，让路由算法「碰巧」选它
把 u→z 的流量分到两条路上 做不到：需要新的路由算法
在 w 处让红色和蓝色流量走不同路 做不到：基于目的地址的转发 + LS/DV 路由无法区分

这三个例子说明：传统路由只看目的地址，粒度太粗；SDN 的通用转发可以按任意首部字段区分流量。

六、SDN 的四个核心思想（讲义 p12）

# 思想 说明
1 基于流的转发 在多个首部字段上做通用 match + action，由 OpenFlow 编程
2 数据平面与控制平面分离 交换机只转发，控制平面在别处
3 控制功能在交换机之外 跑在能看到全网的控制器（网络 OS）上
4 可编程的控制应用 路由、访问控制、负载均衡都只是应用

讲义的伏笔：思想 1 假设交换机已经知道有哪些字段。OpenFlow 给的是固定字段列表，你的协议不在列表里就无法匹配 —— 这就是 P4 要填的坑，也是望远镜需要 P4 的原因。

七、SDN 分层架构（讲义 p13）

层 职责 SKA-Low 中的对应
网络控制应用 路由、访问控制、负载均衡等「大脑」，可来自第三方 Tango 控制系统 / gRPC 客户端
── 北向 API ── 控制器暴露给应用的抽象（REST、intent） gRPC + Python API
SDN 控制器（网络 OS） 维护全网状态；本身实现为分布式系统 流水线引擎（Connector）
── 南向 API ── 控制器怎么和交换机对话（OpenFlow） NVIDIA Spectrum SDK
数据平面交换机 快、简单、商用；流表由控制器安装 Spectrum 交换芯片

北向 = 控制器 ↔︎ 应用；南向 = 控制器 ↔︎ 交换机。 方向别记反。

八、通用转发：match → actions（讲义 p14）

每个流表项都是「匹配 → 动作」+ 计数器：

MATCH（首部字段） ACTIONS
入端口 forward(port)
源/目的 MAC、EtherType、VLAN drop
源/目的 IP、IP 协议号、ToS modify-field（如改写 IP / MAC）
源/目的 TCP/UDP 端口 send to controller
+ 计数器：分组数、字节数

这一个抽象统一了多种设备（讲义原话，高频考点）：

设备 用 match-action 表示
路由器 匹配目的 IP，转发
交换机 匹配目的 MAC，转发
防火墙 匹配端口，丢弃
NAT 匹配 IP + 端口，改写

讲义标注「REMEMBER THIS SLIDE」 —— 第四部分 NVIDIA 的规则也是完全同样的形状。

九、OpenFlow：南向协议（讲义 p15）

运行在控制器与交换机之间，基于 TCP（可选 TLS）。 三类消息：

控制器 → 交换机 交换机 → 控制器 对称消息
features：查询交换机能力 packet-in：把分组交给控制器 hello：建立连接
configure：读/写参数 flow-removed：某表项过期/被删 echo：存活检测
modify-state：增/删/改流表项 port status：端口状态变化 error：出错
packet-out：从某端口发出分组

实践中：运营者很少手写 OpenFlow 消息，都是通过控制器的北向 API。

packet-in vs packet-out 易混：packet-in 是交换机「上交」给控制器（通常因为没匹配到表项）；packet-out 是控制器「下发」让交换机发出某个分组。

十、链路故障时两个平面如何协作（讲义 p16）

步 动作 跨越哪个 API
1 交换机 S1 发现链路故障，用 OpenFlow port-status 消息上报 南向
2 控制器更新全网状态数据库中的链路状态 —
3 注册了「链路状态变化回调」的 Dijkstra 应用被通知 北向
4 应用用控制器的网络图重新计算路由 北向
5 控制器的流表组件计算出新流表 —
6 控制器通过 OpenFlow 把新表安装到所有受影响的交换机 南向

讲义总结：步骤 1、6 跨南向 API；步骤 3、4 跨北向 API。 这是很好的选择题素材。

十一、生产中的 SDN（讲义 p17）

ONOS Google Orion（NSDI '21）
特点 控制应用与控制器分离；intent 框架（描述「要什么」而非「怎么做」）；强调分布式核心（复制、性能扩展） Jupiter（数据中心）和 B4（广域网）的控制平面；路由和流量工程作为应用跑在 Orion 核心上；intent 驱动，强调大规模下的健壮性
南向 OpenFlow、NETCONF、P4Runtime —

讲义提醒：ONOS 已经支持 P4Runtime —— 业界早已从「编程表项」走向「编程流水线」。

十二、OpenFlow 的软肋（讲义 p18）

问题 说明
只能匹配它已知的字段 每个新首部 = 一版新规范 + 新交换芯片。VXLAN、NVGRE、Geneve 都要等厂商跟进
SKA 的协议在载荷里 SKA 的波束号和频率号在 UDP 载荷（SPEAD）里，任何 OpenFlow 版本都匹配不到

引出下一部分：如果交换机在我们告诉它之前什么协议都不认识呢？

第二部分：P4 —— 编程数据平面本身

十三、P4 的三个设计目标（讲义 p20）

P4（Programming Protocol-independent Packet Processors，Bosshart et al., 2014）是一种描述交换机如何处理分组的领域专用语言。交换机一开始什么都不知道。

目标 含义
可重配置性（Reconfigurability） 部署后仍可在现场改变分组的解析和处理方式
协议无关性（Protocol independence） 没有内建的 Ethernet、IP、TCP；每个首部及其位置都由你声明
目标无关性（Target independence） 编译器把同一个程序映射到 ASIC（Tofino）、FPGA、SmartNIC 或软件交换机

对望远镜的意义：协议无关性让交换机能匹配埋在望远镜分组里的波束号。

十四、OpenFlow vs P4（讲义 p21）

OpenFlow P4
谁定义首部和表 厂商固化在芯片里 程序员声明首部、parser、表
控制器做什么 填写预定义的表 编译器把程序映射到目标
支持新协议 新规范 + 新芯片 改程序、重新编译
思路 自底向上：「我的交换机能做这些」 自顶向下：「我的交换机必须做这些」

二者配合使用：P4 在编译时配置流水线；运行时 API（P4Runtime，类似 OpenFlow）再往表里填项。

十五、PISA：协议无关交换机架构（讲义 p22）

P4 程序面向的抽象流水线：

部件 作用
Parser 状态机，把首部提取成结构化的分组表示（PHV）
Match-action 级 每级在表中查 key、执行动作：改字段、设出端口、丢弃、计数
Traffic manager 固定功能：缓冲、排队、多播复制（Tofino 的 PRE）
Deparser 把（可能被修改的）首部重新序列化，放回载荷前面

十六、P4 程序结构（讲义 p23–25）

块 作用
header 逐比特声明分组格式（如 ethernet_h 的 48 位 dst/src、16 位 ether_type）
parser 状态机：下一个首部是什么
control 表、动作以及它们的应用顺序
deparser 输出哪些首部、按什么顺序
main 把各块接到目标的流水线上

Parser 状态机（讲义 p24）

0x0800 = IPv4；协议号 17 = UDP（6 = TCP）。这两个数字值得记住。

表与动作（讲义 p25，来自 SKA P4 文档）

元素 说明
key 匹配哪些字段、怎么匹配：exact（精确）、ternary（带掩码）、lpm（最长前缀）
actions 带参数的小函数；参数来自表项
default_action 未命中时做什么（这里：丢弃）
apply { } 控制流：哪些表、按什么顺序、在什么条件下执行

十七、先编译流水线，再填表（讲义 p26）

SKA 2020 年的静态规则 spead_table.yaml：beam_no 1 → 端口 132，2 → 133，3 → 134。

十八、网内计算（讲义 p27）

交换机每秒处理数十亿分组、时延确定 —— 还能顺便算什么？

用途 说明
带内遥测（INT） 交换机把队列深度、时延盖章写进分组
负载均衡 线速做每流或每分组决策
缓存与聚合 在网络内部回答或合并请求
科学数据引导 按数据的「含义」路由 —— 本讲座的案例

十九、讲义的三道自测题（p28）与参考答案

# 题目 参考答案（讲义未给，按讲义内容作答）
1 要支持一个新首部，P4 程序的哪部分要改？ header 声明 + parser 状态机（加一个状态和 transition）；若要输出它还要改 deparser；要按它转发再在 control 里加表
2 表项由谁写：P4 程序还是控制器？ 控制器（运行时经 P4Runtime 写入）。P4 程序只定义表的结构
3 为什么 OpenFlow 1.4 不能按 SPEAD 波束号路由？ OpenFlow 只能匹配规范里固定的首部字段（到 L4 端口为止）；波束号在 UDP 载荷里，不在任何 OpenFlow 版本的匹配字段中

第三部分：SKA-Low —— 射电望远镜里的 P4

二十、问题与规模（讲义 p2、p31–33）

数字 含义
131,072 天线数
512 站点数（每站 256 根天线）
~6 Tbps 进入相关器的数据
~65 km 最长基线
50–350 MHz 频率（波长 1–6 m）
  • SKAO 两个望远镜：SKA-Mid（南非，数百个碟形天线，GHz 频段）和 SKA-Low（西澳）
  • SKA-Low 位于 Wajarri Yamaji Country 的 CSIRO Murchison 射电天文台，2025 年 3 月发布第一张图像
  • 真正的难点不是带宽，而是 256k 条信号路径：每根天线两个极化，每个信号要和其他每个信号相遇

信号链：天线（131,072）→ 站点波束形成（512 站）→ ~6 Tbps → 相关器与波束形成器 Perentie（CSIRO） → ~7 Tbps → 科学数据处理器（超算）

组件 做什么
相关器 对每一对站点信号相乘并积分约 1 秒，得到「可见度」，超算再成像
波束形成器 形成数百个窄而高灵敏度的「tied-array」波束：用来给脉冲星计时、搜索暂现源（约 2 Tbps）

讲者团队的工作：Perentie 的网络在站点与数百个 FPGA 之间搬运每一个字节，并送往科学处理。

网络的任务：以线速把每个分组送到需要它的那一个 FPGA，路径上没有 CPU。

二十一、从定制硬件到「原子化 COTS」（讲义 p34–35）

以前：定制板卡和背板（多年设计、一次性制造）；紧耦合（数据路径焊死在硬件里，改一处要重做其他部分）；垂直集成（大型机类比的左列）。

新思路：「Atomic COTS」—— 只用商用现成部件（P4 交换机 + FPGA 加速卡），关键在于数据怎么分发。

阶段 做法
Map 每个站点按粗信道（coarse channel）给分组打 key（每站发 384 个粗信道）
Route 交换机把同一信道的所有分组送到同一个 FPGA（固定映射，由控制平面设定）—— 20 台 P4 交换机
Reduce 该 FPGA 计算该信道的全部乘积 —— 384 个 FPGA，每个一个信道

每个 FPGA 是「原子的」：拿到某粗信道的全部 512 个站点数据后，独立算出所有输出，不依赖任何其他 FPGA。 这就是在网络里做 MapReduce 的 shuffle。

二十二、两个构件（讲义 p36–38）

构件 1：P4 交换机

Barefoot Tofino：6.4 Tbps ASIC，2RU 里 64 × 100 GbE，x86 控制 CPU 运行 ONL + Stratum。

功能 说明
Route SPEAD / CODIF 天文分组，巨帧 2,000–8,500 字节
Replicate 透明复制：一份给波束形成器，一份给相关器
Monitor 流健康：丢包、突发
Time PTP 边界时钟：同步 FPGA 处理
Interface ARP、RDMA…… 对 FPGA 隐藏望远镜的复杂性

为什么非 P4 不可：这些都不是「普通」交换机功能；按 SPEAD 字段路由、按波束复制需要可编程的 parser 和表。

网络设计：两层 fabric —— 第一层 I/O（站点数据 128 × 100G 进，SDP/PSS/PST 产品出）；第二层扇出到 FPGA 服务器（每台 20 张 Alveo 卡）；热备：备用交换机和服务器，通过重新编程路由切入。

构件 2：Alveo FPGA

  • 商用卡、免费工具、标准 Linux 服务器
  • 内置 100 GbE：分组直接进 FPGA，没有 NIC、没有 PCIe 数据传输
  • 每卡 16 GB HBM、约 9k 个 DSP 片
  • 定点流水线：SPEAD 解码 → 滤波器组 → 延迟 → 波束形成 → 打包
  • 监控与控制寄存器走 PCIe；全系统约 420 张 Alveo 卡

二十三、关键技巧：按载荷里的字段路由（讲义 p39）

只加一个 parser 状态：parse_udp → parse_spead，按 UDP 端口选择。 之后 beam_no、frequency_no 就成了普通的匹配 key，和 dst_addr 没区别。

二十五、2021 年概念验证（讲义 p41–42）

  • 链路：Matlab 模型 → 站点模拟器 → 100 GbE P4 交换机（APS BF6064X-T） → 20 × Alveo U50 波束形成器 → 抓包 + PST

  • 结果：脉冲星从噪声里出来了

P4 带来了什么：数据引导、复制、遥测、隐藏复杂性 —— 都在交换机里，线速完成，不需要服务器。

第四部分：让交换机重新「软件定义」—— NVIDIA Spectrum

二十六、从 P4 到 NVIDIA 的路（讲义 p44）

时间 事件

讲义金句：「我们失去的是 P4 芯片，不是 P4 背后的思想。」

二十七、没有 P4 也能按载荷路由：flex parser（讲义 p45）

Spectrum 没有 P4 parser，但有 flex parser：在 UDP 载荷的固定偏移处读字节，作为匹配 key 暴露出来。

偏移例子：SPEAD → subarray @ 42、beam @ 36、frequency @ 38；CODIF → group_id @ 18、secondary_id @ 20。

P4 parser Flex parser
本质 可编程状态机，编译得到 固定偏移集合，每个 SDK 生命周期声明一次
通用性 高 较低，但够用来按数据含义路由

二十八、第一版的痛点与重构（讲义 p46–48）

第一版：4 个并行的协议管理器（SPS、SDP、PSR、PTP），每个都把 dict 翻译成 SDK 结构。

问题
四个管理器大量重复代码
硬编码 region ID 和固定的分发拓扑（17 个手写 GOTO 槽，位于 region 0x20052）
只有 SPEAD 一种 parser，CODIF 根本无法存在
加新协议要在很多地方改 Python
没有一个地方能在下发 SDK 前校验规则

核心思想：用 YAML 文件描述协议，而不是用 Python。控制逻辑变成数据。

重构后三层，单向流动：

讲义：「听起来很熟？」—— YAML → schema → IR → backend 就是一个编译器，和 P4 → p4c → 目标二进制同一个形状；加协议时后端不用改。

二十九、YAML 流水线的五个部分 ≈ P4（讲义 p49–50）

YAML 部分 作用 对应 P4
parsers flex parser + GP 寄存器：哪些字段成为 key ≈ P4 parser
counters 命名遥测，懒分配，被规则引用 ≈ counters / registers
tables match-action ACL region：路由规则 ≈ P4 tables
dispatch 入口流量如何被导向各表 ≈ apply { }
fabric 所有表共享的 L2 行为（VLAN、端口），按部署 —

一条规则的解剖：match l4_destination_port = 36001、group_id、secondary_id → actions SET_VLAN 2、SET_DST_MAC synthetic(port, lane)、FORWARD、COUNTER codif.unicast。

合成 MAC 技巧：把出端口 + lane 编码进目的 MAC，由静态 FDB 解析 —— 一条规则就能导向一个物理端口。 和第一部分的 OpenFlow 流表项、第二部分的 P4 表同一个形状 —— 这个抽象跨越了三代技术。

三十、P4/Tofino vs YAML/Spectrum（讲义 p51）

P4 / Tofino（2020–23） YAML 流水线 / Spectrum（2024–）

四条 Takeaways（讲义 p55）：

  1. SDN 把控制平面搬出盒子：match → action 表，集中编程。
  2. P4 更深一层：编程 parser 和流水线，而不只是表项。
  3. 在 SKA-Low，P4 让交换机按载荷里的字段路由，以 Tbps 速率把每个信道送到它的 FPGA。
  4. P4 芯片消失后，抽象活了下来：NVIDIA Spectrum 上的声明式 YAML 流水线。
